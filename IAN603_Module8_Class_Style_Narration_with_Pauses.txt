Welcome to Module 8, Strings and Dates in PostgreSQL.

Slide 2: Why this module matters

This module is about more than display formatting.

[pause=0.7]

A trailing space can create a different category. Inconsistent case can fragment groups. A date stored as text cannot safely participate in date arithmetic.

[pause=0.7]

Time values also have different meanings. A calendar date is different from a local clock timestamp, and both are different from an instant stored with time-zone meaning.

[pause=0.7]

The goal is to prepare these values without accidentally changing what they mean.

[pause=1.0]

Slide 3: Learning goals

By the end of the module, you should be able to normalize common text problems, choose the right temporal type, change time grain, calculate durations, and separate parsing from formatting.

[pause=0.7]

You should also be able to explain why a transformation is appropriate.

[pause=0.7]

The objective is not to memorize a long list of functions. It is to select the right function based on the meaning of the value and the analytical task.

[pause=1.0]

Slide 4: PostgreSQL-specific correction

One correction is important before we start.

[pause=0.7]

PostgreSQL does not use DATEADD and DATEDIFF as native functions.

[pause=0.7]

Instead, PostgreSQL commonly uses date or timestamp subtraction, INTERVAL values, EXTRACT, DATE_TRUNC, AGE, TO_DATE, TO_TIMESTAMP, and TO_CHAR.

[pause=0.8]

The underlying analytical ideas are portable, but the SQL syntax depends on the database system.

[pause=1.0]

Slide 8: Text cleaning pipeline

Text cleaning is a pipeline, not one magic function.

[pause=0.7]

First inspect the raw value.

[pause=0.7]

Then normalize only known formatting noise.

[pause=0.7]

If the string contains meaningful structure, parse the pieces you need.

[pause=0.7]

[pause=0.7]

Slide 12: BTRIM handles boundaries

BTRIM is excellent for boundary whitespace.

[pause=0.7]

It removes spaces from the start and end of a string.

[pause=0.7]

But it does not collapse repeated spaces inside the value.

[pause=0.7]

That distinction is important.

[pause=0.7]

If you need to normalize internal whitespace, you need a different function such as REGEXP_REPLACE with a repeated-whitespace pattern.

[pause=1.0]

Slide 13: Why LENGTH is useful

LENGTH is useful because text problems are not always visually obvious.

[pause=0.7]

Boundary spaces and repeated internal spaces increase the character count.

[pause=0.7]

Comparing length before and after cleaning can help confirm that your transformation is doing what you expect.

[pause=0.7]

Think of LENGTH as a diagnostic function during data preparation.

[pause=1.0]

Slide 14: Repeated whitespace

Replacing that run with one ordinary space turns values with inconsistent spacing into a more stable representation.

We usually trim boundaries first and then normalize the internal whitespace.

Slide 30: Temporal types

Now we move from text to temporal data.

[pause=0.7]

The first decision is the data type.

[pause=0.7]

DATE represents a calendar date.

[pause=0.7]

TIMESTAMP represents a date and clock time without time-zone interpretation.

[pause=0.7]

TIMESTAMPTZ represents an instant in time.

[pause=0.7]

INTERVAL represents a duration.

[pause=0.7]

Choosing the correct type is more important than choosing a formatting function.

[pause=1.0]

Slide 31: DATE

DATE is appropriate when the calendar day matters but the time of day does not.

[pause=0.7]

Examples include birth date or a reporting date.

[pause=0.8]

A typed date can be sorted chronologically and used in date arithmetic.

[pause=0.7]

A text string that merely looks like a date does not provide the same analytical guarantees.

[pause=1.0]

Slide 32: TIMESTAMP

TIMESTAMP stores a date and local clock time.

[pause=0.7]

It does not carry a time-zone interpretation.

[pause=0.7]

That can be appropriate when the time zone is fixed or irrelevant.

[pause=0.7]

But if records come from multiple regions or you need to compare global instants, a plain timestamp can become ambiguous.

[pause=1.0]

Slide 33: TIMESTAMPTZ

TIMESTAMPTZ is PostgreSQL's timestamp with time zone type.

[pause=0.7]

Conceptually, it represents an instant.

[pause=0.7]

PostgreSQL can display that instant in different time zones.

[pause=0.7]

This is useful for events collected across locations.

[pause=0.7]

The key distinction is between the stored instant and the clock representation shown to a user.

[pause=1.0]

Slide 34: INTERVAL

INTERVAL represents duration.

[pause=0.7]

You can add an interval to a date or timestamp to create a future or past point.

[pause=0.7]

Timestamp subtraction also returns an interval.

[pause=0.7]

Intervals are central to PostgreSQL temporal arithmetic and replace many dialect-specific date-add patterns.

[pause=1.0]

Slide 35: Temporal type decision guide

Choose the type based on meaning.

[pause=0.7]

If only the calendar day matters, DATE may be enough.

[pause=0.7]

If you need a local date and time without global time-zone meaning, TIMESTAMP may fit.

[pause=0.7]

If the value represents an instant, use TIMESTAMPTZ.

[pause=0.7]

If the value is duration, use INTERVAL.

[pause=0.7]

Remember that storage precision and analytical grain are separate decisions.

[pause=1.0]

Slide 36: PostgreSQL date arithmetic

Here is the PostgreSQL-native approach to common temporal tasks.

[pause=0.7]

Subtract timestamps to obtain an interval.

[pause=0.7]

Add INTERVAL values to shift time.

[pause=0.7]

Use EXTRACT to read components.

[pause=0.7]

Use DATE_TRUNC to change analytical grain.

[pause=0.8]

Use AGE when you want a symbolic calendar interval.

[pause=0.7]

These patterns are clearer and more portable within PostgreSQL than borrowing function names from another SQL dialect.

[pause=1.0]

Slide 37: EXTRACT

EXTRACT reads one component from a date or timestamp.

[pause=0.7]

You can extract year, month, day of week, hour, and many other fields.

[pause=0.7]

The result is a component value, not a new grouped timestamp.

[pause=0.7]

This distinction matters when comparing EXTRACT with DATE_TRUNC.

[pause=1.0]

Slide 39: Day-of-week caution

Day-of-week values need documentation.

[pause=0.7]

In PostgreSQL, EXTRACT DOW uses zero for Sunday and six for Saturday.

[pause=0.7]

Slide 40: DATE_TRUNC

DATE_TRUNC changes the analytical grain of a timestamp.

[pause=0.8]

A timestamp can be truncated to day, week, month, quarter, or other levels.

[pause=0.8]

The returned value represents the start of that period.

[pause=0.7]

This makes DATE_TRUNC especially useful for GROUP BY because all timestamps in the same period receive the same bucket value.

[pause=1.0]

Slide 42: EXTRACT vs DATE_TRUNC

EXTRACT and DATE_TRUNC solve different problems.

[pause=0.8]

EXTRACT month gives a number such as three.

[pause=0.7]

DATE_TRUNC month gives a full month bucket such as March first, twenty twenty-six at midnight.

[pause=0.8]

If you group only by month number, March from multiple years can be combined accidentally.

[pause=0.7]

DATE_TRUNC often gives a safer full-period key for time-series aggregation.

[pause=1.0]

Slide 50: AGE vs subtraction

AGE and direct subtraction both compare two temporal values, but their emphasis differs.

[pause=0.7]

For hospital length of stay, direct subtraction is usually easier to interpret.

[pause=0.7]

For calendar-style age differences, AGE may be more natural.

Slide 52: Parsing vs formatting

Parsing and formatting move in opposite directions.

[pause=0.7]

Parsing starts with text and creates a typed date or timestamp.

[pause=0.7]

That typed value can be sorted, compared, grouped, and used in arithmetic.

[pause=0.8]

Formatting starts with a typed temporal value and creates text for human presentation.

[pause=0.7]

For analytics, parse early and format late.

[pause=1.0]

Slide 53: Casting vs parsing

Sometimes a direct cast is sufficient.

[pause=0.7]

If the text is already in a clear date format that PostgreSQL recognizes and you have validated the input, casting to date can be simple.

[pause=0.7]

When the format is different, TO_DATE lets you specify the pattern.

[pause=0.7]

For mixed raw input, first identify the shape and then apply the appropriate parser.

[pause=0.7]

Blindly parsing unknown text can cause errors or incorrect interpretations.

[pause=1.0]

Slide 54: Safe parsing workflow

A safe parsing workflow starts by cleaning boundary whitespace.

[pause=0.7]

Then identify the input shape.

[pause=0.7]

Apply the parser that matches that shape.

[pause=0.7]

If the value does not match an expected format, return NULL or flag it for review instead of guessing.

[pause=0.7]

Parsing converts representation. It does not prove that the underlying business value is accurate.

Slide 58: Why formatting comes late

Typed timestamps are more useful for analysis than display strings.

[pause=0.7]

Slide 59: Time zones

[pause=0.7]

[pause=0.7]

[pause=0.7]

When the same event must be understood consistently across systems, timestamptz is usually the safer model.
