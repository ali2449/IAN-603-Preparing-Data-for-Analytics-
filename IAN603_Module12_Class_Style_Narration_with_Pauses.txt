Slide 1: Start

Welcome to Module 12, Views and Modular Queries.

[pause=0.7]

This module is about turning useful SQL logic into reusable database interfaces.

[pause=0.7]

We will learn standard views, materialized views, updatable views, check options, dependency inspection, freshness policies, and modular query design.

[pause=0.8]

The central idea is that a view is not just saved text. It is an interface with a row grain, a set of columns, and a meaning that downstream users may depend on.

[pause=1.0]

Slide 2: Why views matter

Views solve several problems at once.

[pause=0.7]

They let us centralize shared SQL logic.

[pause=0.7]

They create a stable interface with deliberate columns and row meaning.

[pause=0.7]

They can reduce accidental exposure by omitting unnecessary fields, although actual authorization still depends on database security controls.

[pause=0.7]

And materialized views can store reusable results when freshness does not need to be immediate.

[pause=1.0]

Slide 3: Learning goals

By the end of this module, you should be able to create standard views, inspect their definitions and dependencies, explain when a view is updatable, and use a check option to control writes through a filtered view.

[pause=0.8]

You should also understand materialized-view freshness and be able to decide whether logic belongs in a statement-level CTE, a reusable standard view, or a stored materialized result.

[pause=1.0]

Slide 6: Modular architecture

Modularity works best when each layer has one responsibility.

[pause=0.7]

Base tables store source facts.

[pause=0.7]

A shared view can own stable relational logic.

[pause=0.7]

A report-level CTE can own a temporary threshold, ranking rule, or sequence calculation.

[pause=0.7]

The final query produces the consumer-specific result.

[pause=0.8]

This separation makes each layer easier to test and change.

[pause=1.0]

Slide 7: Three reusable choices

The three main choices in this module differ in lifetime and storage.

[pause=0.7]

A CTE exists for one statement.

[pause=0.7]

A standard view is a persistent database object, but it stores the query definition rather than a result snapshot.

[pause=0.8]

A materialized view is persistent and stores the query result.

[pause=0.8]

Choose among them based on reuse, freshness, and computational cost.

[pause=1.0]

Slide 8: What a standard view stores

A standard view stores a query definition.

[pause=0.8]

It does not normally store a separate snapshot of the result.

[pause=0.7]

When the view is queried, PostgreSQL uses the view definition to access current underlying data.

[pause=0.7]

For consumers, the view behaves like a named relation with columns and rows.

[pause=1.0]

Slide 9: View contract

Think of a view as a contract.

[pause=0.7]

The object name matters.

[pause=0.7]

The exposed columns and types matter.

[pause=0.7]

The row grain matters.

[pause=0.7]

And consumers should understand how fresh the data is.

[pause=0.7]

If you change a shared view in a way that breaks one of these expectations, downstream queries can fail or change meaning.

Slide 13: CREATE OR REPLACE VIEW

CREATE OR REPLACE VIEW lets you update a compatible view definition without first dropping the object.

[pause=0.7]

[pause=0.7]

But compatibility matters.

[pause=0.7]

Changing column names, meanings, types, or grain can still affect downstream users, even if the SQL command succeeds.

Slide 18: Dependency chain

A view can sit in the middle of a dependency chain.

[pause=0.7]

[pause=0.7]

[pause=0.7]

Slide 19: Change management

Change management goes beyond syntax.

[pause=0.7]

A CREATE OR REPLACE command may succeed, but a semantic change can still break analytics.

[pause=0.7]

Consumers may depend on a column name, data type, business definition, or row grain.

[pause=0.7]

Review those contract elements before changing a shared object.

Slide 20: Simple views can be updatable

Some simple PostgreSQL views are automatically updatable.

[pause=0.7]

A write through the view can flow to the underlying table.

[pause=0.7]

But this is not true for every view.

[pause=0.7]

Joins, aggregates, grouping, and other features can make a view non-updatable.

[pause=0.7]

Treat writable views as a deliberate interface and test their behavior.

[pause=1.0]

Slide 22: Filtered updatable view

A filtered view introduces an important write question.

[pause=0.7]

If the view only shows active patients, what should happen when an update through the view sets active to false?

[pause=0.7]

Without a check option, the row may simply disappear from the view after the update.

[pause=0.7]

WITH CHECK OPTION can enforce the view condition for writes performed through the view.

[pause=1.0]

Slide 23: WITH CHECK OPTION

WITH CHECK OPTION enforces the view's filter for writes through the view.

[pause=0.7]

If an update would make a row no longer satisfy the active equals true condition, PostgreSQL rejects the write.

[pause=0.7]

This turns the filtered view into a more controlled write interface.

[pause=0.7]

It does not replace general database constraints or permissions.

[pause=1.0]

Slide 24: CHECK OPTION failure

This example intentionally fails.

[pause=0.8]

The active-patient view shows only active rows and includes a check option.

[pause=0.7]

The update tries to set an active patient to inactive through that view.

[pause=0.7]

Because the resulting row would no longer satisfy the view condition, PostgreSQL rejects the update.

[pause=0.7]

This is expected behavior.

[pause=1.0]

Slide 25: Do not infer writability

Do not assume every view is writable.

[pause=0.7]

A simple one-table view may support automatic updates.

[pause=0.7]

A join or aggregate view does not have the same direct row mapping.

[pause=0.7]

Materialized views are stored query results, not ordinary write-through interfaces.

[pause=0.8]

Always check the actual PostgreSQL behavior for the view definition you are designing.

[pause=1.0]

Slide 26: Views as access boundaries

A view can reduce accidental exposure by publishing only the columns required for an analytical task.

[pause=0.7]

For example, an analytics interface may expose an age band and city instead of direct contact fields.

[pause=0.8]

But hiding columns in a view definition is not the same as granting or denying access.

[pause=0.7]

Actual authorization depends on PostgreSQL privileges and, where appropriate, row-level security or other controls.

[pause=1.0]

Slide 30: Security boundaries

Views are useful security-adjacent interfaces, but they should not be described as secure or compliant simply because they hide columns.

[pause=0.7]

Permissions still matter.

[pause=0.7]

Row-level security may matter.

[pause=0.7]

Application access paths matter.

[pause=0.7]

Compliance depends on a broader system of controls.

[pause=0.7]

Keep the claim proportional to what the view actually does.

Slide 31: Materialized views

A materialized view is fundamentally different from a standard view.

[pause=0.7]

The materialized view stores query results.

[pause=0.8]

That can make repeated reads of an expensive summary convenient.

[pause=0.7]

But the stored result can become stale as base tables change.

[pause=0.7]

Freshness therefore becomes part of the object's contract.

[pause=1.0]

Slide 32: When materialization helps

Materialization is useful when an expensive result is read repeatedly and consumers can tolerate a known refresh lag.

[pause=0.8]

The database object alone is not the whole design.

[pause=0.7]

You also need a refresh schedule, freshness metadata, and a plan for refresh failures.

[pause=0.8]

Without those, consumers may not know how current the snapshot is.

[pause=1.0]

Slide 36: Freshness timeline

Materialized-view freshness is easiest to understand as a timeline.

[pause=0.7]

The snapshot is built.

[pause=0.7]

Later, a new base-table row arrives.

[pause=0.7]

The standard base query can see it immediately, but the materialized view does not.

[pause=0.8]

After a refresh, the stored snapshot catches up.

[pause=0.8]

That delay must be documented for users.

Slide 39: Freshness is a contract

Freshness policy is part of the data product.

[pause=0.7]

Consumers need to know how often the materialized view refreshes.

[pause=0.8]

They need a way to see the last successful refresh.

[pause=0.8]

The team should know what happens when refresh fails.

[pause=0.8]

And the expected maximum latency should be documented rather than assumed.

Slide 41: Concurrent refresh note

Slide 43: CTE vs view vs materialized view

This comparison helps choose the right object.

[pause=0.7]

A CTE is local to one statement.

[pause=0.7]

A standard view is shared and live.

[pause=0.7]

A materialized view is shared and stored.

[pause=0.7]

Temporary business thresholds usually belong close to the report.

[pause=0.7]

Stable shared relational meaning often belongs in a standard view.

[pause=0.7]

Expensive reused summaries may justify materialization if the freshness tradeoff is acceptable.

[pause=1.0]

Slide 44: Promote only stable logic

A useful architecture rule is to promote stable meaning into persistent objects.

[pause=0.7]

If many consumers agree on what a patient-admission row means, that can become a view.

[pause=0.7]

If one report uses a temporary thirty-day threshold, keep that logic in the report.

[pause=0.7]

If a summary is expensive and reused frequently, materialization may be appropriate.

[pause=0.7]

Do not turn every query into a database object.

[pause=1.0]

Slide 55: Freshness checkpoint

Freshness is one of the clearest differences among these objects.

[pause=0.7]

A later CTE statement uses current source data.

[pause=0.7]

A standard view reads through to the current underlying data.

[pause=0.7]

A materialized view stays at its last snapshot until refreshed.

[pause=0.8]

Consumers should never have to guess which freshness model they are using.

[pause=0.7]

[pause=0.7]

[pause=0.7]
