Slide 1: Start

Welcome to Module 4, Aggregating Data with PostgreSQL. In the previous module, we worked mainly with individual rows. Here, we move from detail records to summaries that can answer analytical questions.

[pause=0.7]

The important idea is that aggregation is not only about writing COUNT, SUM, or AVG. Before you calculate anything, decide what one result row should represent. That is the grain of the summary.

[pause=0.7]

Throughout this module, you can run the PostgreSQL examples directly in the browser. On code slides, you can also use Copy and paste the same query into the pgAdmin Query Tool for additional practice.

[pause=0.8]

We will build from simple aggregate functions to GROUP BY, WHERE and HAVING, conditional aggregation, subtotals, and window functions. Keep asking the same question: what does one row in my result mean?

[pause=1.0]

Slide 2: Big picture

Module 3 focused on retrieving, filtering, and changing individual rows. Module 4 changes the perspective. Instead of asking which records should I return, we often ask questions such as how many, how much, what is the average, or which group is largest.

[pause=0.7]

A good aggregation starts with the business question. Then we define the output grain, choose the measures, apply row-level filters, apply group-level filters when needed, and finally validate the result.

[pause=0.7]

A simple way to think about it is detail, grain, measure, filter, and validate. If the final summary does not match the meaning of the question, even perfectly valid SQL can produce a misleading answer.

Slide 3: Learning path

Here is the learning path for this module.

[pause=0.7]

We begin with the core aggregate functions: COUNT, SUM, AVG, MIN, and MAX. Then we use GROUP BY to create one summary row for each category or combination of categories.

[pause=0.7]

After that, we separate WHERE from HAVING. WHERE decides which source rows are allowed into the aggregation. HAVING decides which completed groups stay in the final result.

[pause=0.7]

We then extend the same ideas with conditional aggregation, PostgreSQL FILTER, ROLLUP, CUBE, GROUPING SETS, and window functions.

[pause=0.7]

The practice pattern also becomes gradually more independent. First you run complete examples, then change them, then fill in missing pieces, and finally write short analytical queries yourself.

Slide 5: Five-step workflow

Before writing an aggregation query, use this five-step workflow.

[pause=0.7]

First, ask the decision question. What are we trying to learn from the data?

[pause=0.7]

Second, set the grain. Decide what one output row should represent. One diagnosis? One category? One department?

[pause=0.7]

Third, choose the measures. That might be a count, a total, an average, a minimum, or a maximum.

[pause=0.7]

Fourth, decide which rows qualify and which groups qualify. This is where WHERE and HAVING play different roles.

[pause=0.7]

Finally, validate the summary against the detail data.

[pause=0.7]

The most important step is grain. If you cannot describe one result row in a short sentence, do not rush into GROUP BY yet. Clarify the intended summary first.

[pause=1.0]

Slide 6: Summary functions

Aggregate functions turn many input rows into summary values.

[pause=0.7]

COUNT answers how many. SUM adds numeric values. AVG calculates the mean. MIN finds the smallest value, and MAX finds the largest.

[pause=0.7]

If you use an aggregate without GROUP BY, PostgreSQL normally returns one summary row for the entire input set. Once you add GROUP BY, the same aggregate is calculated separately inside each group.

[pause=0.7]

For example, AVG salary without grouping gives one company-wide average. AVG salary grouped by department gives one average for each department.

[pause=0.8]

Before choosing a function, name the measure in plain language. Are you counting records, counting known values, adding revenue, or averaging completed stays? That language helps you choose the correct expression.

[pause=1.0]

Slide 7: COUNT meanings

COUNT can answer different questions, so it is important to choose the right version.

[pause=0.7]

COUNT star counts input rows. It does not care whether individual columns contain missing values.

[pause=0.7]

COUNT of a specific column counts only rows where that expression is not NULL.

[pause=0.7]

COUNT DISTINCT counts unique non-null values.

[pause=0.7]

The completed-admission count should be smaller because ongoing admissions have no discharge time. The distinct patient count answers a different question again: how many unique patients appear.

[pause=0.8]

If you are using pgAdmin, copy the query into the Query Tool and run the same comparison there. Look at the labels carefully and connect each number to the question it answers.

Slide 9: NULL and averages

NULL values require special attention in aggregation.

[pause=0.7]

In the admissions table, an ongoing admission has no discharge time yet. That means we cannot calculate a completed length of stay for that row.

[pause=0.7]

AVG ignores NULL expressions rather than treating them as zero. That behavior is useful here because an unfinished stay is not a zero-day stay.

[pause=0.7]

Run the example and look at the completed length-of-stay calculation. Think about which admissions actually contribute to the average.

[pause=0.8]

Whenever you report an average, also think about the sample size. An average based on eight completed admissions means something different from an average based on all ten admission rows. Missing values can change which records are included in the measure.

Slide 10: GROUP BY grain

GROUP BY defines the grain of a summary result.

[pause=0.7]

With no GROUP BY, an aggregate can summarize the whole table into one row. If we group by diagnosis, the output becomes one row per diagnosis. If we group by patient and diagnosis, the result becomes more detailed: one row per patient-and-diagnosis combination.

[pause=0.7]

This is why adding grouping columns usually increases the number of output rows.

[pause=0.7]

A beginner-friendly rule is that selected columns that are not inside aggregate functions generally need to appear in GROUP BY.

[pause=0.7]

But the deeper rule is about meaning. Every selected non-aggregate value should be well-defined for the group represented by that output row.

[pause=0.7]

Before writing GROUP BY, finish the sentence: one row in my result represents one...

[pause=1.0]

Slide 14: WHERE vs HAVING

WHERE and HAVING both filter, but they operate at different stages.

[pause=0.7]

WHERE filters individual source rows before grouping happens. For example, keeping only sales where price is at least twenty-five dollars removes rows before the category totals are calculated.

[pause=0.8]

HAVING filters completed groups after aggregation. For example, keeping categories whose total quantity is greater than ten requires the grouped total to exist first.

[pause=0.8]

A simple test is to ask whether the condition refers to an individual row or to a group measure.

[pause=0.7]

If it is a row condition, think WHERE. If it is a condition on COUNT, SUM, AVG, or another grouped measure, think HAVING.

[pause=0.7]

Keeping these roles separate makes aggregation queries much easier to reason about.

[pause=1.0]

Slide 15: Complete aggregation pattern

A complete aggregation query has a natural logical flow.

[pause=0.7]

First, FROM identifies the source. WHERE filters individual rows. GROUP BY forms the groups. HAVING removes groups that do not meet an aggregate condition. SELECT defines the values that appear in the result, and ORDER BY sorts the final rows.

[pause=0.7]

The written SQL order is familiar, but thinking about the logical stages helps explain why certain expressions are valid in one clause and not another.

[pause=0.7]

There is also a practical efficiency lesson here. If a condition can be applied to individual source rows, put it in WHERE so fewer rows reach the grouping stage.

[pause=0.7]

Before running a long summary query, read it as a pipeline: source rows, row filter, groups, group filter, output, sort.

[pause=1.0]

Slide 17: Conditional aggregation

Conditional aggregation lets one grouped query calculate several related metrics from the same input rows.

[pause=0.7]

Suppose we want separate counts for pneumonia and fracture admissions for each patient. We could run separate queries, but conditional aggregation keeps the measures together in one result.

[pause=0.8]

There are two common patterns in this module.

[pause=0.7]

CASE is widely portable and can convert a condition into a value that an aggregate can summarize.

[pause=0.7]

PostgreSQL FILTER attaches a condition directly to an aggregate and is often easier to read when each measure has its own condition.

[pause=0.7]

The important idea is that the group stays the same while different subsets of rows contribute to different measures.

[pause=1.0]

[pause=0.8]

This pattern is flexible because CASE can handle more than simple equality. You can build conditions based on ranges, multiple columns, or more complex business rules.

[pause=0.7]

When using CASE for counting, make sure the values you return are appropriate for the aggregate you apply.

[pause=1.0]

Slide 20: CASE vs FILTER

CASE and FILTER can express similar conditional aggregation logic.

[pause=0.7]

CASE is generally more portable because many SQL systems support conditional expressions inside aggregates.

[pause=0.7]

FILTER is concise and readable in PostgreSQL, especially when several measures each have their own condition.

[pause=0.7]

For this course, you should understand both. If you know the query will run in PostgreSQL, FILTER can be a clean choice. If you expect the SQL to move between different platforms, SUM with CASE is often safer.

[pause=0.8]

Whichever style you choose, validate the measure using a small known example. Conditional metrics can look correct while using slightly different conditions, so checking a few rows manually is still important.

Slide 21: Advanced grouping

So far, GROUP BY has produced one summary grain at a time. Advanced grouping features let one query produce several summary levels.

[pause=0.7]

GROUPING SETS lets you explicitly list the summary combinations you want.

[pause=0.7]

ROLLUP is useful for hierarchical reports, such as category, then product, then a grand total.

[pause=0.7]

CUBE generates every grouping combination of the listed dimensions.

[pause=0.7]

These features reduce the need to write several separate aggregation queries and combine them manually.

[pause=0.7]

The tradeoff is that the output contains different grains in the same result. That means you must understand what each row represents and how subtotal placeholders are displayed.

[pause=0.7]

We will use a small product-sales table so you can see those levels clearly.

[pause=1.0]

Slide 22: Grouping comparison

This comparison is worth learning conceptually.

[pause=0.7]

GROUPING SETS produces only the grouping combinations you request.

[pause=0.7]

ROLLUP of A and B produces detail at A and B, a subtotal at A, and a grand total. It follows a hierarchy.

[pause=0.7]

CUBE of A and B produces detail, subtotals by A, subtotals by B, and the grand total. It generates every combination.

[pause=0.7]

A simple way to choose is to ask what report levels you need.

[pause=0.7]

If you need a hierarchy, ROLLUP is often a natural fit. If you need all cross-dimensional totals, consider CUBE. If you want only specific levels, GROUPING SETS gives you precise control.

[pause=0.7]

The SQL syntax is different, but the same grain reasoning still applies to every row produced.

[pause=1.0]

Slide 23: ROLLUP

[pause=0.8]

Do not interpret every NULL in a subtotal report as missing source data. In advanced grouping output, NULL can be a structural placeholder.

[pause=0.7]

This is why later we will use GROUPING to distinguish a subtotal placeholder from a real NULL value in the source.

[pause=1.0]

Slide 24: CUBE

CUBE expands the idea further by producing every grouping combination.

[pause=0.7]

With category and product, that includes category-and-product detail, category totals, product totals across categories, and the grand total.

[pause=0.7]

Run the example and compare the number and type of rows with the ROLLUP result.

[pause=0.8]

The key difference is that ROLLUP follows a hierarchy, while CUBE creates totals for every dimension combination.

[pause=0.7]

CUBE can be useful for exploratory summary tables, but the number of combinations grows quickly when you add more dimensions.

[pause=0.7]

Before using CUBE in a larger dataset, think about how many grouping combinations you are requesting and whether each one supports a real analytical need.

[pause=1.0]

Slide 25: GROUPING SETS

GROUPING SETS gives you explicit control over which summary levels are returned.

[pause=0.7]

Instead of generating a fixed hierarchy or every possible combination, you list the groupings you actually need.

[pause=0.7]

[pause=0.8]

This feature is useful when a report needs only selected totals, such as category totals and a grand total, but not every product subtotal.

[pause=0.7]

The output still contains rows at different grains, so label or interpret those rows carefully.

[pause=0.7]

Think of GROUPING SETS as a way to ask PostgreSQL for several GROUP BY queries at once, while keeping the requested summary levels under your control.

Slide 26: GROUPING placeholders

Advanced grouping introduces an important NULL question.

[pause=0.7]

Subtotal and grand-total rows often show NULL in grouping columns because that dimension has been rolled up. But source data can also contain genuine NULL values.

[pause=0.7]

GROUPING helps us distinguish those two situations.

[pause=0.7]

A grouping code tells us which expressions are participating in the current row and which have been summarized away.

[pause=0.7]

The exact code is less important than the principle: do not label every NULL with COALESCE before you know why it is NULL.

[pause=0.7]

In a production report, using GROUPING can help you label rows accurately as detail, subtotal, or grand total without confusing structural placeholders with missing data.

[pause=1.0]

Slide 27: Window functions

Window functions solve a different analytical problem from GROUP BY.

[pause=0.7]

GROUP BY collapses many input rows into one row per group.

[pause=0.7]

A window function usually keeps the original detail rows and adds analytical context beside them.

[pause=0.7]

For example, we can keep every employee row while adding a department rank or department average.

[pause=0.8]

PARTITION BY defines groups for the window calculation, while ORDER BY inside OVER can define ranking or running sequence.

[pause=0.8]

This is powerful because you do not have to choose between detail and summary. You can display both in the same result.

[pause=0.7]

When deciding between GROUP BY and a window function, ask whether you want to collapse rows or keep them visible.

[pause=1.0]

Slide 31: Execution order

Logical execution order explains many SQL rules that can otherwise feel arbitrary.

[pause=0.7]

PostgreSQL conceptually begins with FROM and JOIN, then applies WHERE, forms groups with GROUP BY, filters groups with HAVING, evaluates SELECT expressions, performs window calculations, and then applies ORDER BY and LIMIT.

[pause=0.7]

This is why a same-level aggregate is not available in WHERE. The groups do not exist yet at that stage.

[pause=0.7]

HAVING can use aggregate expressions because grouping has already happened.

[pause=0.7]

Window functions are evaluated after grouped filtering, which is why they can add analytical context to the rows that remain.

[pause=0.7]

You do not need to memorize every internal implementation detail. Use this logical order as a reasoning model for understanding which clause can see which values.

[pause=1.0]

Slide 32: Portability

The analytical reasoning in this module transfers across SQL systems, but some syntax changes.

[pause=0.7]

PostgreSQL can subtract timestamps directly in ways that other databases may express with functions such as DATEDIFF.

[pause=0.7]

PostgreSQL FILTER is concise for conditional aggregation, while SUM with CASE is supported more broadly.

[pause=0.7]

ROLLUP, CUBE, GROUPING SETS, and window functions are widely available in modern databases, but exact syntax and supported options can vary.

[pause=0.7]

When moving a query between systems, preserve the reasoning first: filter source rows, define the grain, calculate measures, filter groups, and sort the report.

[pause=0.7]

Then adapt the engine-specific syntax.

[pause=0.7]

That approach is much safer than copying a PostgreSQL query and assuming every database interprets it exactly the same way.

Slide 45: Summary

Let's close Module 4 by connecting the main ideas.

[pause=0.7]

Start with grain. Decide what one output row should represent before choosing GROUP BY columns.

[pause=0.7]

Remember that NULL affects aggregate functions. COUNT star and COUNT of a column answer different questions, and AVG ignores NULL expressions.

[pause=0.7]

Use WHERE for source-row conditions and HAVING for completed group conditions.

[pause=0.7]

Conditional aggregation lets one group produce several measures. CASE is portable, while PostgreSQL FILTER is concise.

[pause=0.7]

ROLLUP, CUBE, and GROUPING SETS let one query produce multiple summary grains, so interpret subtotal rows carefully.

[pause=0.7]

Window functions keep detail rows while adding rank, averages, running totals, and other analytical context.

[pause=0.8]

The habit to carry forward is simple: define the question, define the grain, calculate the measure, filter at the correct stage, and validate the result.
