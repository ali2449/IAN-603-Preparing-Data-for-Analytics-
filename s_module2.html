Running case

A small outpatient clinic

The clinic must track patients, providers, appointments, services, and the services delivered during each appointment.

What the system should support

  • Schedule appointments
  • Assign a patient and provider
  • Record one or more services
  • Store quantities and charges
  • Reconnect records for reporting

What the design must prevent

  • Duplicate patient identifiers
  • Appointments with missing parents
  • Negative service prices
  • End times before start times
  • Comma-separated service lists

A critical habit

State the row grain before choosing columns

Row grain answers: “What does one row represent?” It prevents unrelated subjects from being mixed into the same table.

Clear grain

  • patient: one row per patient
  • appointment: one row per scheduled encounter
  • service: one row per reusable service
  • appointment_service: one row per service used in one appointment

Unclear grain

One row contains patient details, provider details, appointment times, a list of services, and several charges.

Now the row describes several different things at once.

Ask before every table: Could I finish the sentence “one row equals one _____”?
Entities & attributes

Does this concept deserve its own table?

✓ Separate entity

A concept often becomes a table when it:

  • has its own identity
  • has several descriptive facts
  • is reused many times
  • has relationships to other concepts

Example: service has a code, name, price, and active state.

× Simple attribute

A concept usually stays a column when it:

  • describes another entity
  • does not need its own identity
  • has no independent relationships

Examples: birth date, appointment start time, quantity.

Missingness is a design choice

NULL is not zero and not blank

NULL represents unknown, missing, or not-applicable information. Decide column by column whether that state makes sense.

ColumnNullable?Reason
patient.mrnNoEvery operational patient needs an identifier.
patient.emailYesNot every patient supplies email.
appointment.starts_atNoA scheduled appointment needs a start time.
appointment.cancelled_atYesOnly cancelled appointments have a cancellation time.
Data dictionary: document column name, meaning, type, nullability, allowed values, units, keys, and business rules.

Relationships & cardinality

How many rows can connect?

1:1

One-to-one

At most one related row on each side.

Implementation: foreign key + UNIQUE.

1:N

One-to-many

One parent can have many children.

Clinic: one patient → many appointments.

N:M

Many-to-many

Both sides can connect to many rows.

Clinic: appointments ↔ services.

Placement rule: In 1:N, place the foreign key on the many side. In N:M, introduce a junction table.

Translate rules into columns

Business language → relational decisions

Business ruleRelational decision
Every appointment belongs to exactly one patient.appointment.patient_id is a non-null foreign key.
A patient may have no appointments yet.No appointment row is required for every patient.
Every appointment has exactly one provider.appointment.provider_id is a non-null foreign key.
An appointment may have zero or many service lines.appointment_service contains optional child rows.
A service may appear in many appointments.The junction table resolves the many-to-many relationship.
Integrity constraints

Constraints are executable business rules

NOT NULL

A value is required.

mrn text NOT NULL
DEFAULT

Supplies a value when omitted.

DEFAULT 'scheduled'
UNIQUE

Prevents duplicate protected values.

UNIQUE (npi)
CHECK

Requires a Boolean condition to be true.

CHECK (quantity > 0)
PRIMARY KEY

Provides non-null unique row identity.

PRIMARY KEY (appointment_id)
FOREIGN KEY

Requires a matching parent key.

REFERENCES patient
Why constraints matter: application validation improves user experience; database constraints protect the data no matter which app, script, import, or user writes to the table.

Parent deletion behavior

Choose referential actions deliberately

ActionMeaningGood fit
RESTRICT / NO ACTIONReject parent deletion while children depend on it.Patient/provider/service master data referenced by appointments.
CASCADEDelete dependent child rows with the parent.Appointment-service lines that have no meaning without their appointment.
SET NULLKeep the child but remove the reference.Only if the relationship is optional.
SET DEFAULTReplace the reference with its default.Rare; the default must still reference a valid key.
Do not use CASCADE just because it is convenient. Use it when the child truly has no independent meaning.
Normalization

Why normalize a relational design?

Update anomaly

Copies disagree

A provider specialty appears in hundreds of appointment rows. Some copies are updated; others are not.

Insertion anomaly

You cannot add a fact

A new service cannot be added until a fake appointment is created.

Deletion anomaly

You lose unrelated facts

Deleting the only appointment accidentally removes the only copy of patient details.

Normalization goal: store each fact in a place that matches what determines that fact.

1NF

First Normal Form: one value per field

Move each service occurrence to its own row. A possible key is now (appointment_id, service_code).

appointment_idpatient_mrnpatient_nameprovider_npiservice_codeservice_namecharge
A5001P1001Maya Brooks1234567890S101Office Visit95.00
A5001P1001Maya Brooks1234567890L220CBC28.00

✓ Improved

No repeating lists. Each service can be referenced and filtered separately.

× Still a problem

Patient, provider, appointment, and service facts are repeated in many rows.

2NF

Second Normal Form: depend on the whole composite key

When the key is (appointment_id, service_code), ask whether each non-key column depends on both parts.

Depends on appointment_id

start time, patient information, provider information

Depends on service_code

service name, standard price

Depends on both

quantity and the charge captured for that service on that appointment

2NF split: appointment + service + appointment_service.
3NF

Third Normal Form: remove transitive dependencies

Even after 2NF, appointment rows should not carry facts that really depend on patient or provider identifiers.

3NF idea

Non-key facts describe the key, the whole key, and not another non-key attribute.

Final core: patient, provider, appointment, service, appointment_service.

Operational → analytical

A normalized source and an analytical model have different goals

OLTP

Normalized operational core

  • Protect transaction integrity
  • Reduce duplicated facts
  • Support inserts/updates safely
  • Use primary/foreign keys and constraints

Example grain: one appointment-service line.

Analytics

Dimensional reporting model

  • Fast, understandable analytical joins
  • Fact tables store events/measures
  • Dimensions describe who/what/when/where
  • Star schemas may intentionally repeat descriptive values
Key idea: a dimensional model complements the normalized operational source. It does not excuse poor source-system design.
Analytics extension

Star, snowflake, and fact grain

Fact table

Measurements/events

Declare the grain first.

Example: one row per appointment-service line.

Star schema

Direct dimensions

Fact table connects directly to descriptive dimensions. Fewer joins; analyst-friendly.

Snowflake

Normalized dimensions

Some dimensions split into related sub-dimensions. Less redundancy; more joins.

Do not skip this question: What exactly does one row in the fact table represent?

Diagnose before repairing

What is wrong with this “everything table”?

patient_nameprovider_nameappointment_timeservices_csvcharge_text
Maya BrooksJordan Chen09/08/26 9amS101,L220$123.00

Identity

No primary key; names are changeable and non-unique.

Structure

Several subjects share one unclear row grain; services are a list.

Types & rules

Time and money are stored as text; no foreign keys or domain checks.

Show repair direction

Split into patient, provider, appointment, service, and appointment_service. Add stable keys, proper types, foreign keys, unique business identifiers, NOT NULL rules, and CHECK constraints.

Guided practice

Exercise: model a bookstore

A bookstore app tracks customers, books, authors, orders, and the books purchased in each order.

Your design tasks

  1. List the entities.
  2. Choose a row grain for each table.
  3. Propose primary and natural keys.
  4. Identify 1:N and N:M relationships.
  5. Choose useful types and constraints.

Questions to notice

  • Can one book have several authors?
  • Can one order contain several books?
  • Should deleting an order delete its line items?
  • Should deleting a book erase historical order items?
Show one reasonable direction
  • customer(customer_id PK, email UNIQUE, ...)
  • author(author_id PK, author_name, ...)
  • book(book_id PK, isbn UNIQUE, ...)
  • book_author(book_id FK, author_id FK, composite PK)
  • orders(order_id PK, customer_id FK, ...)
  • order_item(order_id FK, book_id FK, quantity, unit_price, composite PK)
Practice business rules

Translate bookstore rules into constraints

1. Customer email must be present and unique.
2. Order-item quantity must be positive.
3. Unit price cannot be negative.
4. Every order item must reference an existing order and book.
5. Deleting an order removes its items; deleting a historical book is restricted.
6. Status must belong to a controlled set.
Show constraint patterns
email text NOT NULL UNIQUE
quantity integer NOT NULL CHECK (quantity > 0)
unit_price numeric(10,2) NOT NULL CHECK (unit_price >= 0)
FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE CASCADE
FOREIGN KEY (book_id) REFERENCES book(book_id) ON DELETE RESTRICT
