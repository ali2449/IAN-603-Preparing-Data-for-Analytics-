Views & Modular Queries

View-design habit

For every reusable object, document four things: grain, columns, freshness, and intended consumers.

Start here

Views are database interfaces, not just saved snippets

A Common Table Expression gives a temporary name to logic inside one statement. A standard view stores a query definition so many statements can reuse the same interface. A materialized view stores the result of a query and therefore introduces a freshness decision. Module 12 is about choosing the right level of persistence and making the resulting contract explicit.

Learning objectives

By the end of this module, you will be able to:

  • Create, query, replace, inspect, and remove PostgreSQL views.
  • Explain how a standard view differs from a CTE, table, and materialized view.
  • Use automatically updatable views and WITH CHECK OPTION appropriately.
  • Design limited-column and limited-row interfaces while recognizing that permissions—not the view definition alone—enforce access.
  • Create and refresh materialized views and explain the performance-versus-freshness trade-off.
  • Inspect view dependencies and organize reusable analytics into documented layers.
  • Combine persistent views with query-specific CTEs and window functions for maintainable analysis.
Core rule: a reusable object should make downstream SQL simpler without hiding its meaning. Users still need to know what one row represents and how current the data are.
Mental model

Modularity works best when each layer has one responsibility

Think of a view as a stable interface between raw storage and downstream analysis. A view can centralize joins, transformations, or approved columns; a CTE can add report-specific logic on top of that interface.

Reusable live interfaces

Create standard views when many queries need the same relational logic

A standard view is especially useful when the same joins, derived columns, or row filters appear repeatedly. Downstream users query the view as a relation, while the definition remains centralized.

Patient-admission analytical interface
CREATE OR REPLACE VIEW analytics.vw_patient_admission_summary AS
SELECT
    p.subject_id,
    p.gender,
    p.city,
    a.hadm_id,
    a.admit_time,
    a.discharge_time,
    a.department,
    a.diagnosis,
    CASE
        WHEN a.discharge_time IS NULL THEN NULL
        ELSE ROUND(EXTRACT(EPOCH FROM (a.discharge_time - a.admit_time)) / 86400.0, 2)
    END AS stay_days
FROM patients AS p
JOIN admissions AS a
  ON a.subject_id = p.subject_id;

The view's grain is one row per admission. That statement is as important as the SQL. If a downstream analyst assumes one row per patient, counts and joins can be wrong even though the query is syntactically valid.

Aggregate a reusable view
SELECT
    department,
    COUNT(*) AS admissions,
    COUNT(DISTINCT subject_id) AS unique_patients,
    ROUND(AVG(stay_days), 2) AS avg_stay_days
FROM analytics.vw_patient_admission_summary
WHERE stay_days IS NOT NULL
GROUP BY department
ORDER BY admissions DESC, department;
Naming convention: this module uses vw_ for standard views and mv_ for materialized views. PostgreSQL does not require these prefixes, but consistent names make object purpose easier to recognize.

Controlled writes

Some simple views are automatically updatable

A simple view over one table can allow INSERT, UPDATE, or DELETE to flow through to the base table. WITH CHECK OPTION can prevent a write through the view from creating a row that no longer satisfies the view's own filter.

Update through an automatically updatable view
BEGIN;

UPDATE analytics.vw_active_patients
SET city = 'High Point'
WHERE subject_id = 1002
RETURNING subject_id, name, city, active;

ROLLBACK;
Intentional CHECK OPTION failure
UPDATE analytics.vw_active_patients
SET active = false
WHERE subject_id = 1002;

This example is expected to raise a PostgreSQL error because the updated row would no longer be visible through the filtered view. The lab automatically rolls back after an error.

Do not infer writability from the word “view.” Joins, aggregates, grouping, set operations, and other features can make a view non-updatable. Treat writable views as a deliberate interface and test their behavior.
Access boundaries

A view can reduce exposure, but the view definition does not grant or revoke access by itself

PostgreSQL security_invoker option
CREATE OR REPLACE VIEW analytics.vw_patient_analytics
WITH (security_invoker = true) AS
SELECT
    subject_id,
    CASE
        WHEN date_of_birth > DATE '1995-06-30' THEN 'Under 30'
        WHEN date_of_birth > DATE '1975-06-30' THEN '30-49'
        WHEN date_of_birth > DATE '1955-06-30' THEN '50-69'
        ELSE '70+'
    END AS age_band,
    city,
    active
FROM patients;
Security distinction: selecting fewer columns is useful abstraction, but actual authorization requires privileges (and, when needed, row-level security or other controls). A view should not be described as “HIPAA compliant” or “secure” merely because it hides columns.
Stored results

Materialized views trade freshness for precomputed results

A materialized view stores query results. This is useful when a query is expensive and consumers can tolerate a defined refresh interval.

Standard view

Reads current base data

Best when users need current results and the underlying query is acceptable to execute at read time.

Materialized view

Reads a stored snapshot

Best when repeated reads justify precomputation and a freshness policy is explicit.

Create a materialized diagnosis summary
DROP MATERIALIZED VIEW IF EXISTS analytics.mv_diagnosis_stats;

CREATE MATERIALIZED VIEW analytics.mv_diagnosis_stats AS
SELECT
    diagnosis,
    COUNT(*) AS total_admissions,
    COUNT(DISTINCT subject_id) AS unique_patients,
    ROUND(AVG(
        CASE WHEN discharge_time IS NULL THEN NULL
             ELSE EXTRACT(EPOCH FROM (discharge_time - admit_time)) / 86400.0
        END
    ), 2) AS avg_stay_days,
    clock_timestamp() AS refreshed_at
FROM admissions
GROUP BY diagnosis;

SELECT *
FROM analytics.mv_diagnosis_stats
ORDER BY total_admissions DESC, diagnosis;

The stored refreshed_at value is recomputed when the materialized view refreshes. It documents when the snapshot was produced; it is not the time of every subsequent read.

Modular architecture

Use persistent views for shared logic and CTEs for report-specific stages

A useful rule is to promote logic into a view when its meaning and grain are stable across multiple consumers. Keep temporary thresholds, ranking rules, and report-specific filters inside the consuming query.

CTE

Lifetime: one statement

Best for: temporary stages, ranking, report-specific transformations.

Standard view

Lifetime: database object

Best for: shared live interfaces and centralized logic.

Materialized view

Lifetime: database object + stored result

Best for: expensive reusable summaries with a known refresh contract.

View + CTE + LAG for readmission analysis
WITH sequenced AS (
    SELECT
        subject_id,
        hadm_id,
        admit_time,
        LAG(discharge_time) OVER (
            PARTITION BY subject_id
            ORDER BY admit_time, hadm_id
        ) AS previous_discharge
    FROM analytics.vw_patient_admission_summary
),
readmissions AS (
    SELECT *,
           admit_time - previous_discharge AS gap
    FROM sequenced
    WHERE previous_discharge IS NOT NULL
)
SELECT
    subject_id,
    hadm_id,
    gap,
    gap <= INTERVAL '30 days' AS within_30_days
FROM readmissions
ORDER BY subject_id, hadm_id;
Layering principle: the view owns the stable admission interface; the CTE owns the report-specific sequence logic. That separation keeps each layer easier to test and reuse.
Practice & project

Build a small reusable analytics layer

The project has three consumers: operations needs employee performance, retention analysts need recent customer activity, and leadership needs a diagnosis dashboard. Your task is to choose the correct reusable object for each need and then write concise consuming queries.

Employee performance

Stable joined/aggregated logic → standard view.

Retention threshold

Shared activity view + report-specific CTE.

Diagnosis dashboard

Repeated summary + acceptable refresh lag → materialized view.

Employee performance view
CREATE OR REPLACE VIEW analytics.vw_employee_performance AS
SELECT
    e.employee_id,
    e.employee_name,
    d.department_name,
    COUNT(o.order_id) AS orders_processed,
    COALESCE(SUM(o.sale_amount),0)::numeric(12,2) AS total_sales
FROM employees AS e
JOIN departments AS d
  ON d.department_id = e.department_id
LEFT JOIN sales_orders AS o
  ON o.employee_id = e.employee_id
GROUP BY e.employee_id, e.employee_name, d.department_name;

SELECT *
FROM analytics.vw_employee_performance
ORDER BY total_sales DESC, employee_id;
Recent customer activity view
CREATE OR REPLACE VIEW analytics.vw_recent_customer_activity AS
SELECT
    customer_id,
    transaction_date,
    amount
FROM customer_transactions
WHERE status = 'completed'
  AND transaction_date >= DATE '2025-06-30' - INTERVAL '6 months';
Retention logic stays query-specific
WITH last_activity AS (
    SELECT customer_id, MAX(transaction_date) AS last_transaction
    FROM analytics.vw_recent_customer_activity
    GROUP BY customer_id
),
at_risk AS (
    SELECT
        customer_id,
        last_transaction,
        DATE '2025-06-30' - last_transaction AS days_inactive
    FROM last_activity
    WHERE last_transaction < DATE '2025-06-30' - 60
)
SELECT *
FROM at_risk
ORDER BY days_inactive DESC, customer_id;

Architecture review questions

  1. What is the grain of each view?
  2. Which columns are intentionally not exposed?
  3. Which object has a freshness contract?
  4. Which thresholds are business rules that might change per report and should therefore remain outside the shared view?
  5. What downstream objects would be affected if a shared view changed?

CREATE OR REPLACE VIEW analytics.vw_employee_department_info AS

    e.employee_name,
    e.salary,
    d.department_name
FROM employees AS e

Key takeaways

  • A CTE is statement-scoped; a view is a reusable database object.
  • A standard view stores a definition; a materialized view stores query results.
  • Materialized views require a documented refresh/freshness policy.
  • A view can limit exposed columns and rows, but access control still depends on database privileges and related security mechanisms.
  • WITH CHECK OPTION can enforce the filter of an updatable view for writes performed through that view.
  • Stable shared logic belongs in reusable objects; report-specific thresholds often belong in CTEs.
