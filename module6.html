Join habit

Define grain → choose preserved rows → join on keys → validate cardinality.

Start here

From separate tables to one analytical question

A normalized database deliberately stores patients, encounters, laboratory results, prescriptions, and staff in separate tables. A join reconstructs the relationships required for a specific question. The goal is not simply to connect tables; it is to preserve the correct population and output grain.

Running case: You are building analytics for a synthetic outpatient and hospital dataset. Every task in this module asks you to decide what a row should represent before choosing the join.

Learning objectives

  • Choose INNER, LEFT, RIGHT, or FULL OUTER JOIN from a business question.
  • Write explicit join conditions with ON or USING and table aliases.
  • Predict which unmatched rows an outer join preserves and where NULLs will appear.
  • Use LEFT JOIN to identify missing related records.
  • Use SELF JOIN and CROSS JOIN for comparison and combination problems.
  • Diagnose one-to-many and many-to-many row multiplication before aggregating.
  • Combine several tables while keeping counts and grain defensible.
  • Validate a join with row counts, distinct keys, and targeted spot checks.

Conceptual foundation

A join is a row-matching rule

Think of a join as three decisions: which two row sets are compared, what makes two rows match, and which unmatched rows must remain. The join type controls preservation; the ON expression controls matching.

INNER JOIN

Keep only matched row combinations.

LEFT JOIN

Keep every left row plus matching right rows.

RIGHT JOIN

Keep every right row plus matching left rows.

FULL OUTER JOIN

Keep unmatched rows from both sides.

Do not rely on Venn diagrams alone. SQL joins combine rows, not just sets of unique IDs. If one patient has two admissions, that patient legitimately appears twice in a patient-to-admission detail join.

CREATE TABLE patients (
    patient_id integer PRIMARY KEY,
    name varchar(100) NOT NULL,
    age integer NOT NULL CHECK (age BETWEEN 0 AND 120),
    gender varchar(20),
    home_city varchar(60) NOT NULL
);

    department varchar(60) PRIMARY KEY,
    floor_no integer NOT NULL,
    service_line varchar(80) NOT NULL
);

CREATE TABLE medical_staff (
    staff_id integer PRIMARY KEY,
    name varchar(100) NOT NULL,
    department varchar(60) REFERENCES departments(department),
    specialization varchar(80) NOT NULL,
    hire_date date NOT NULL
);

CREATE TABLE admissions (
    admission_id integer PRIMARY KEY,
    patient_id integer NOT NULL REFERENCES patients(patient_id),
    admit_date date NOT NULL,
    discharge_date date,
    diagnosis varchar(120) NOT NULL,
    department varchar(60) NOT NULL REFERENCES departments(department),
    attending_staff_id integer REFERENCES medical_staff(staff_id),
    CHECK (discharge_date IS NULL OR discharge_date >= admit_date)
);

    patient_id integer NOT NULL REFERENCES patients(patient_id),

    normal_range varchar(30)
);

    rx_id integer PRIMARY KEY,

);

CREATE TABLE patient_vitals (

    vital_name varchar(50) NOT NULL,

);

CREATE TABLE appointment_slots (

Join type 1

INNER JOIN: require a match

Use an INNER JOIN when the question is specifically about entities that have a related record. A patient with no admission disappears because no patient-admission pair satisfies the join condition.

PostgreSQL
SELECT p.patient_id, p.name, a.admission_id, a.diagnosis, a.department
FROM patients AS p
INNER JOIN admissions AS a ON a.patient_id = p.patient_id
ORDER BY p.patient_id, a.admit_date;
Grain: one row per matching admission, not one row per patient. Alice appears twice because she has two admissions.

Aliases remove ambiguity

When both tables contain patient_id, qualify the column with aliases such as p.patient_id and a.patient_id. Once a table receives an alias, use that alias consistently throughout the query.

Join types 2-4

Outer joins: preserve unmatched rows

How outer joins preserve rows

LEFT JOIN: preserve the analytical population

PostgreSQL
SELECT p.patient_id, p.name, a.admission_id, a.diagnosis
FROM patients AS p
LEFT JOIN admissions AS a ON a.patient_id = p.patient_id
ORDER BY p.patient_id, a.admission_id;

Anti-join pattern: find missing relationships

After a LEFT JOIN, an unmatched right-side key is NULL. Filtering for that NULL returns left rows with no match.

PostgreSQL
SELECT p.patient_id, p.name
FROM patients AS p
LEFT JOIN lab_results AS l ON l.patient_id = p.patient_id
WHERE l.test_id IS NULL
ORDER BY p.patient_id;

RIGHT JOIN: valid, but often rewritable as LEFT JOIN

PostgreSQL supports RIGHT JOIN. In team code, many analysts prefer to swap table order and write the equivalent LEFT JOIN because the preserved population is easier to read from left to right.

PostgreSQL
SELECT d.department, d.floor_no, s.name AS staff_name, s.specialization
FROM medical_staff AS s
RIGHT JOIN departments AS d ON d.department = s.department
ORDER BY d.department, s.name;

FULL OUTER JOIN for reconciliation

The lab includes an intentionally unvalidated staging table so you can see a source row whose patient ID does not exist in the patient master.

PostgreSQL
SELECT COALESCE(p.patient_id, s.patient_id) AS patient_id,
       p.name,
       s.import_row_id,
       s.diagnosis,
       CASE
         WHEN p.patient_id IS NULL THEN 'Staging row has no patient master'
         WHEN s.import_row_id IS NULL THEN 'Patient has no staging row'
         ELSE 'Matched'
       END AS match_status
FROM patients AS p
FULL OUTER JOIN admissions_stage AS s ON s.patient_id = p.patient_id
ORDER BY COALESCE(p.patient_id, s.patient_id);
Join conditions

ON, WHERE, and USING are not interchangeable

For an outer join, predicates on the optional side can change whether unmatched rows survive. Put a filter in ON when it describes which right-side rows may match. Put it in WHERE when it should filter the final result.

Preserves every patient

PostgreSQL
-- Put the right-table filter in ON when you still want every patient.
SELECT p.patient_id, p.name, l.test_id, l.result_value
FROM patients AS p
LEFT JOIN lab_results AS l
  ON l.patient_id = p.patient_id
 AND l.test_name = 'Glucose'
ORDER BY p.patient_id;

Accidentally removes unmatched patients

PostgreSQL
-- Moving the filter to WHERE removes NULL-extended rows.
SELECT p.patient_id, p.name, l.test_id, l.result_value
FROM patients AS p
LEFT JOIN lab_results AS l ON l.patient_id = p.patient_id
WHERE l.test_name = 'Glucose'
ORDER BY p.patient_id;
Outer-join trap: a condition such as WHERE l.test_name = 'Glucose' rejects the NULL-extended rows created by the LEFT JOIN. The query then behaves like an INNER JOIN for that condition.

USING when the join key has the same name

PostgreSQL can collapse duplicate join-key columns with USING (patient_id). Prefer ON when the key names differ or the relationship needs a more complex expression.

PostgreSQL
SELECT patient_id, p.name, a.admission_id, a.diagnosis
FROM patients AS p
JOIN admissions AS a USING (patient_id)
ORDER BY patient_id, a.admission_id;
Specialized joins

SELF JOIN and CROSS JOIN

SELF JOIN: compare rows from the same table

A self join is not a separate keyword. It is an ordinary join where the same table receives two aliases. For colleague pairs, use an ordering condition such as s1.staff_id < s2.staff_id to avoid both A-B and B-A duplicates.

PostgreSQL
SELECT s1.department,
       s1.name AS staff_member,
       s2.name AS colleague
FROM medical_staff AS s1
JOIN medical_staff AS s2
  ON s1.department = s2.department
 AND s1.staff_id < s2.staff_id
ORDER BY s1.department, s1.name;

Readmissions as a self join

The admissions table can also be paired with itself to compare an earlier encounter to a later encounter for the same patient.

PostgreSQL
SELECT a1.patient_id, p.name,
       a1.admission_id AS earlier_admission,
       a2.admission_id AS later_admission,
       a2.admit_date - a1.discharge_date AS days_between
FROM admissions AS a1
JOIN admissions AS a2
  ON a1.patient_id = a2.patient_id
 AND a1.admission_id < a2.admission_id
JOIN patients AS p ON p.patient_id = a1.patient_id
WHERE a1.discharge_date IS NOT NULL
  AND a2.admit_date - a1.discharge_date BETWEEN 1 AND 90
ORDER BY days_between;

CROSS JOIN: deliberately generate combinations

A CROSS JOIN creates every possible pair. If the left side has N rows and the right side has M rows, the result contains N x M rows before later filtering.

PostgreSQL
SELECT d.department, s.slot_label
FROM departments AS d
CROSS JOIN appointment_slots AS s
WHERE d.department IN ('Cardiology','Internal Medicine')
ORDER BY d.department, s.slot_label;
Use CROSS JOIN deliberately. It is useful for schedules, scenario grids, and completeness checks, but it can grow extremely quickly.
The most important join diagnostic

Cardinality and row multiplication

Before joining, identify whether each side has zero, one, or many matches per key. A one-to-many join expands rows by design. Joining several one-to-many child tables at the same time can create a many-to-many multiplication inside each patient.

1 patientx2 admissionsx2 labsx2 prescriptions=8 joined detail combinations

The bars are illustrative counts for one patient: 2 x 2 x 2 detail records create 8 combinations unless you pre-aggregate or join at a more specific key.

PostgreSQL
-- Alice has multiple admissions, labs, and prescriptions.
-- Joining all detail tables at patient grain multiplies combinations.
SELECT p.patient_id, p.name,
       COUNT(*) AS joined_rows,
       COUNT(DISTINCT a.admission_id) AS admissions,
       COUNT(DISTINCT l.test_id) AS labs,
       COUNT(DISTINCT pr.rx_id) AS prescriptions
FROM patients AS p
LEFT JOIN admissions AS a ON a.patient_id = p.patient_id
LEFT JOIN lab_results AS l ON l.patient_id = p.patient_id
LEFT JOIN prescriptions AS pr ON pr.patient_id = p.patient_id
GROUP BY p.patient_id, p.name
ORDER BY joined_rows DESC, p.patient_id;
Why COUNT(*) can be wrong: after a multi-child join, it counts joined combinations rather than the original business events. COUNT(DISTINCT event_id) can protect simple counts, but pre-aggregating each child table to the target grain is usually clearer.

Safer pattern: aggregate each child first

PostgreSQL
WITH admission_counts AS (
  SELECT patient_id, COUNT(*) AS admissions
  FROM admissions
  GROUP BY patient_id
),
lab_counts AS (
  SELECT patient_id, COUNT(*) AS labs
  FROM lab_results
  GROUP BY patient_id
),
rx_counts AS (
  SELECT patient_id, COUNT(*) AS prescriptions
  FROM prescriptions
  GROUP BY patient_id
)
SELECT p.patient_id, p.name,
       COALESCE(a.admissions,0) AS admissions,
       COALESCE(l.labs,0) AS labs,
       COALESCE(r.prescriptions,0) AS prescriptions
FROM patients AS p
LEFT JOIN admission_counts AS a USING (patient_id)
LEFT JOIN lab_counts AS l USING (patient_id)
LEFT JOIN rx_counts AS r USING (patient_id)
ORDER BY p.patient_id;

Validation checklist

  • Count rows before and after the join.
  • Count distinct primary keys on each side.
  • Inspect keys with unusually many matches.
  • Confirm the expected grain in plain language.
  • Spot-check a known patient with multiple related records.
Applied integration

Multiple joins in one clinical query

Join paths should follow documented relationships. This query moves from patient to admission and then to the attending staff member. Each join has a clear key and a clear reason.

PostgreSQL
SELECT p.name, a.admission_id, a.diagnosis, a.department,
       ms.name AS attending_clinician, ms.specialization
FROM patients AS p
JOIN admissions AS a ON a.patient_id = p.patient_id
LEFT JOIN medical_staff AS ms ON ms.staff_id = a.attending_staff_id
ORDER BY a.admit_date, p.name;
Join path: patients.patient_id → admissions.patient_id, then admissions.attending_staff_id → medical_staff.staff_id.

Keep the target grain visible

If the desired output is one row per admission, adding a one-to-many table such as lab results by patient_id can destroy that grain. Ask whether the lab is linked to the patient, the admission, or a specific encounter before joining.

Guided practice

Apply the join decision process

Practice 1 - Department performance

Return every department, including departments with zero admissions or zero staff. Report distinct admissions, patients, staff, average stay length, and available specializations.

PostgreSQL
SELECT d.department,
       COUNT(DISTINCT a.admission_id) AS admissions,
       COUNT(DISTINCT a.patient_id) AS patients,
       COUNT(DISTINCT s.staff_id) AS staff_count,
       ROUND(AVG(a.discharge_date - a.admit_date),1) AS avg_stay_days,
       string_agg(DISTINCT s.specialization, ', ' ORDER BY s.specialization) AS specializations
FROM departments AS d
LEFT JOIN admissions AS a ON a.department = d.department
LEFT JOIN medical_staff AS s ON s.department = d.department
GROUP BY d.department
ORDER BY admissions DESC, d.department;

Practice 2 - Explain the result grain

Run the row-multiplication preset for Alice Smith. In one sentence, explain why the joined row count is larger than each underlying event count. Then run the pre-aggregation solution and compare.

Practice 3 - Outer-join reasoning

Which query should you use to list all patients and only their glucose tests? Compare the ON-filter and WHERE-filter presets and explain why the row counts differ.

Assessment & closure

Can you preserve the right rows and the right grain?

  1. Concept: Explain why a LEFT JOIN followed by WHERE right_table.some_column = ... can eliminate unmatched left rows.
  2. Selection: Choose the best join for each goal: only matched patients/admissions; all patients; all departments; full reconciliation of master and staging IDs.
  3. Cardinality: Explain why directly joining admissions, labs, and prescriptions can inflate counts.
  4. Coding: Produce one row per patient containing admission count, most recent admission date, lab count, and prescription count while preserving inactive/no-activity patients.

PostgreSQL
WITH admission_summary AS (
    SELECT patient_id,
           COUNT(*) AS admission_count,
           MAX(admit_date) AS most_recent_admit
    FROM admissions
    GROUP BY patient_id
),
lab_summary AS (
    SELECT patient_id, COUNT(*) AS lab_count
    FROM lab_results
    GROUP BY patient_id
),
rx_summary AS (
    SELECT patient_id, COUNT(*) AS prescription_count
    FROM prescriptions
    GROUP BY patient_id
)
SELECT p.patient_id,
       p.name,
       COALESCE(a.admission_count, 0) AS admission_count,
       a.most_recent_admit,
       COALESCE(l.lab_count, 0) AS lab_count,
       COALESCE(r.prescription_count, 0) AS prescription_count
FROM patients AS p
LEFT JOIN admission_summary AS a USING (patient_id)
LEFT JOIN lab_summary AS l USING (patient_id)
LEFT JOIN rx_summary AS r USING (patient_id)
ORDER BY p.patient_id;

Each child table is summarized to one row per patient before the joins, so the final grain remains one patient per row.

Key takeaways

  • Start with output grain, not syntax.
  • INNER keeps matches; outer joins preserve designated unmatched rows.
  • ON defines matching, while WHERE filters the joined result.
  • One-to-many joins repeat parent rows; multiple one-to-many joins can multiply events.
  • Validate every analytical join with counts and known examples.
