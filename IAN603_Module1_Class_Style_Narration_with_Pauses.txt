Slide 2: Why this module matters

Why do we spend an entire module on understanding data?

[pause=0.7]

Because the same-looking value can mean very different things. The number 27401 may look numeric, but if it is a ZIP code, subtracting or averaging it makes no analytical sense. A satisfaction score of four is stored as an integer, but it represents an ordered category rather than a true measured distance.

[pause=0.7]

We also need to ask whether the data is trustworthy. If important values are missing, duplicated, stale, or outside the allowed domain, later analysis can become misleading.

[pause=0.7]

The main habit in this module is to separate meaning from representation. Software tells us how a value is stored. We still have to decide what the value means.

Slide 5: Four meanings of data type

The phrase data type is often used too loosely.

[pause=0.7]

In this course, we separate four different questions.

[pause=0.7]

Data organization describes the structure of the dataset as a whole. Measurement scale describes the meaning of one variable. Numeric behavior asks whether a quantitative value comes from counting or measuring. Technical representation describes how software stores the value.

[pause=0.7]

A single variable can have answers at several layers. For example, temperature may appear in a structured table, be interval scale, represent a continuous phenomenon, and be stored as a floating-point number.

[pause=0.8]

Keeping these layers separate prevents many common mistakes.

[pause=1.0]

Slide 6: Data organization layer

The first layer is the organization of the dataset.

[pause=0.7]

Structured data follows a predefined schema. Semi-structured data has labels or keys but allows more flexibility and nesting. Unstructured data does not naturally arrive as a table.

[pause=0.8]

This classification describes the dataset container or record format. It does not tell us whether the values are clean, whether they are numeric, or whether they are appropriate for a particular analysis.

[pause=0.7]

That distinction will matter throughout the module.

[pause=1.0]

Slide 7: Measurement scale layer

The second layer is measurement scale.

[pause=0.7]

Here we are no longer asking how the dataset is organized. We are asking what the values of one variable mean.

[pause=0.7]

Nominal and ordinal are categorical scales. Interval and ratio are numeric scales.

[pause=0.7]

The important differences are whether order exists, whether differences are meaningful and equal, and whether zero represents the absence of the measured quantity.

[pause=0.7]

Those properties determine which arithmetic operations and summaries are defensible.

[pause=1.0]

Slide 8: Numeric behavior layer

The third layer applies to numeric concepts.

[pause=0.7]

Discrete variables usually arise from counting events or units. Continuous variables arise from measurement and can conceptually take values within a range.

[pause=0.7]

Do not classify only by looking at the stored dtype.

[pause=0.7]

Heart rate may be stored as an integer because the device reports whole beats per minute. That does not automatically mean the physiological phenomenon is a discrete count in the same sense as number of visits.

[pause=0.7]

Classify the underlying concept first, then note the recording precision separately.

[pause=1.0]

Slide 9: Technical representation layer

The fourth layer is technical representation.

[pause=0.7]

Software needs a physical or logical representation for each value. pandas uses dtypes. Files use formats such as CSV or JSON. Databases use column types such as text, integer, date, or numeric.

[pause=0.7]

Those choices matter, but they do not define analytical meaning by themselves.

[pause=0.7]

An identifier can be stored as an integer and still be nominal. An ordinal category can be stored as text. A date may arrive as a string and still represent time.

[pause=0.7]

Implementation should preserve and support the meaning we already identified.

[pause=1.0]

Slide 10: Same value different meaning

This table shows why software storage does not tell the whole story.

[pause=0.7]

ZIP codes may contain only digits, but they are labels. Satisfaction values are numeric codes, but they primarily express order. ER visits are true counts. Celsius temperature is numeric, but its zero point is arbitrary.

[pause=0.8]

The analytical meaning comes from the concept and the measurement process, not from whether a column happens to be stored as integer or float.

[pause=0.7]

Whenever you see a numeric-looking column, ask what operations make sense in the real world before you calculate a mean or ratio.

Slide 13: Section: Data organization

We are starting Part 1: how data is organized.

[pause=0.7]

The key question here is about the shape and structure of the dataset as a whole.

[pause=0.7]

We will compare structured, semi-structured, and unstructured data, then connect those forms to the types of work an informatics professional may need to do before analysis.

[pause=1.0]

Slide 14: Structured data

Structured data follows a predefined arrangement.

[pause=0.7]

A relational table is the clearest example. Each row follows the same column structure, and the system can often enforce data types and constraints.

[pause=0.8]

CSV and Parquet files can also contain structured data even though they are not databases.

[pause=0.7]

Structured does not mean perfect. A structured table can still contain missing values, inconsistent labels, duplicates, or implausible measurements.

[pause=0.8]

The word structured only describes organization.

[pause=1.0]

Slide 15: Structured example

Here is a simple structured example.

[pause=0.8]

Every patient record follows the same columns. That makes the table easy to scan, validate, and query.

[pause=0.7]

But look inside the table. Patient ID is an identifier. Date of birth is temporal. Sex and blood type are categorical. ZIP code looks numeric but should usually be treated as a label.

[pause=0.8]

This is another reminder that dataset organization and variable meaning are separate questions.

[pause=1.0]

Slide 16: Semi-structured data

Semi-structured data has some organization, but the schema is more flexible.

[pause=0.7]

JSON is a common example. A record can have named fields and nested objects, yet a second record may add a new key or omit an existing one.

[pause=0.8]

That flexibility is useful for APIs, devices, logs, and rapidly changing applications.

[pause=0.7]

The tradeoff is that analysts may need to flatten nested values, handle optional fields, and manage schema changes before the data behaves like an ordinary table.

[pause=1.0]

Slide 17: JSON example

This JSON record is self-describing because the keys tell us what each value represents.

[pause=0.7]

But it is not a flat table. Heart rate is nested inside metrics. Latitude and longitude are nested inside location.

[pause=0.7]

A second record may contain oxygen saturation, while another may omit sleep hours.

[pause=0.7]

Before analysis, we often normalize or flatten the JSON into columns.

[pause=0.7]

The important point is that flexible structure creates a schema-management task. We still need to decide which fields matter, how to handle missing keys, and what each value means.

[pause=1.0]

Slide 18: Unstructured data

Unstructured data does not arrive with a fixed tabular schema.

[pause=0.7]

A clinical note contains meaningful information, but the meaning is embedded in natural language. An image contains visual information. Audio contains signals over time.

[pause=0.7]

To analyze these sources, we usually need an extraction step.

[pause=0.7]

For text, that may involve NLP. For images, computer vision. For scanned documents, OCR. For audio, speech or signal processing.

[pause=0.7]

After extraction, some of the derived information may become structured features that can be analyzed alongside ordinary tables.

[pause=1.0]

Slide 19: Organization comparison

This comparison summarizes the three forms.

[pause=0.7]

Structured data gives us the clearest predefined schema. Semi-structured data contains labels but allows flexibility. Unstructured data requires more interpretation before it can become analytical features.

[pause=0.8]

Real projects often combine all three.

[pause=0.7]

A health analytics project might use a structured encounter table, JSON device data, and free-text notes at the same time.

[pause=0.7]

The challenge is not choosing one format. It is integrating information from different forms while preserving meaning and quality.

[pause=1.0]

Slide 20: The 3Vs

You may hear modern data described using the three Vs: volume, velocity, and variety.

[pause=0.7]

Volume is about scale. Velocity is about how quickly data arrives or must be processed. Variety is about the mixture of data forms.

[pause=0.7]

Our focus in this section is mostly variety.

[pause=0.7]

An informatics professional may need to integrate relational tables, JSON records, documents, and sensor streams. Understanding the organizational form tells you what kind of preparation is needed before you even begin statistical analysis.

[pause=1.0]

Slide 21: Section: Data quality

Now we move to Part 2: data quality.

[pause=0.7]

A dataset can be perfectly structured and still be poor quality.

[pause=0.7]

The question is not whether the data is absolutely good or bad. The question is whether it is fit for the decision or analysis we want to support.

[pause=0.7]

We will use six practical quality dimensions and a simple workflow for investigating problems.

[pause=1.0]

Slide 22: Why quality comes first

Data quality should be assessed before sophisticated analysis.

[pause=0.7]

If duplicates inflate counts, a better visualization does not solve the problem. If a real-time dashboard uses data that is one month old, a more advanced model does not make the dashboard timely.

[pause=0.7]

Quality work is not always about deleting bad rows.

[pause=0.7]

Sometimes we correct a value. Sometimes we flag it. Sometimes we keep it but document uncertainty. Sometimes we exclude it for one analysis but retain it for another.

[pause=0.7]

The correct response depends on the intended use and the evidence available.

[pause=1.0]

Slide 23: Six quality dimensions

These six dimensions give us a practical checklist.

[pause=0.7]

Accuracy asks whether the value reflects reality. Completeness asks whether required information is present. Consistency asks whether the same concept is represented in compatible ways.

[pause=0.7]

Timeliness asks whether the data is current enough for the task. Uniqueness looks for unintended duplicate representations. Validity checks whether a value conforms to the documented domain or rule.

[pause=0.7]

These dimensions can overlap. A blank required field is incomplete and may also be invalid.

[pause=0.7]

Use the dimensions to organize your investigation rather than treating them as perfectly separate boxes.

[pause=1.0]

Slide 24: Accuracy

Accuracy is about correspondence with reality.

[pause=0.7]

A value of five hundred kilograms may be suspicious, but we should not automatically replace it without investigation.

[pause=0.7]

Maybe the units were entered incorrectly. Maybe a decimal point was misplaced. Maybe the patient really has an extreme value.

[pause=0.7]

Accuracy often requires more than a simple rule. It may require comparison with the source system, domain knowledge, or another measurement.

[pause=0.7]

Automated rules are useful for flagging records. They do not always tell us the final truth.

[pause=1.0]

Slide 25: Completeness

Completeness measures whether the information needed for the intended use is present.

[pause=0.7]

The percentage of missing values alone does not tell the whole story.

[pause=0.7]

An optional email field can be incomplete without breaking an analysis. A missing patient identifier may make a record impossible to link safely.

[pause=0.7]

You should examine missingness by field, by source, by time, and sometimes by subgroup.

[pause=0.7]

Also ask why data is missing. Random missingness and systematic missingness can have very different analytical consequences.

[pause=1.0]

Slide 26: Consistency

Consistency is about representing the same concept in compatible ways.

[pause=0.7]

Different date formats are a simple example. Category labels may also vary because of capitalization, abbreviations, or source-system conventions.

[pause=0.8]

Unit inconsistency can be especially dangerous. A number without a clear unit can look valid while representing something completely different.

[pause=0.7]

Consistency work often includes standardization, shared definitions, mapping tables, and referential integrity.

[pause=0.7]

The goal is not just making values look the same. The goal is making sure they mean the same thing after standardization.

[pause=1.0]

Slide 27: Timeliness

Timeliness is about whether data is current enough for the task.

[pause=0.7]

A monthly report may be perfectly acceptable when refreshed once per month. An emergency operations dashboard may require updates within minutes.

[pause=0.7]

That means timeliness is not a single universal threshold.

[pause=0.7]

Document source timestamps, load times, refresh schedules, and expected latency.

[pause=0.7]

When a user sees a dashboard, they should be able to understand how current the information actually is.

[pause=1.0]

Slide 28: Uniqueness

Uniqueness asks whether an entity appears the intended number of times.

[pause=0.7]

An exact duplicate row is relatively easy to detect.

[pause=0.7]

Entity duplication is harder. The same patient may appear under different identifiers because two systems created separate records.

[pause=0.7]

That problem may require entity resolution using names, dates, addresses, or other identifiers.

[pause=0.7]

Database UNIQUE constraints can prevent some duplicate keys, but they cannot solve every real-world identity problem.

[pause=0.7]

Always distinguish duplicate records from duplicate representations of the same entity.

[pause=1.0]

Slide 29: Validity

Validity asks whether a value conforms to the allowed domain or rule.

[pause=0.7]

This is often easier to automate than accuracy.

[pause=0.7]

We can test whether a status belongs to an approved list, whether a count is nonnegative, or whether a date follows an expected format.

[pause=0.7]

But the rule itself must be justified.

[pause=0.7]

A temperature range of thirty to forty-five degrees Celsius may be useful as a teaching validation rule, but a real clinical system would need domain-approved thresholds and careful handling of edge cases.

[pause=0.8]

Validity rules should be explicit, documented, and reviewed.

[pause=1.0]

Slide 30: Quality workflow

A practical quality workflow has five steps.

[pause=0.7]

First, profile the data. Understand distributions, missingness, ranges, categories, and uniqueness.

[pause=0.7]

Second, detect potential problems. Third, investigate the source and context rather than immediately changing values.

[pause=0.7]

Fourth, decide what to do. You may correct, retain, exclude, impute, or flag a record.

[pause=0.7]

Finally, document the decision.

[pause=0.7]

That last step matters because cleaning changes the analytical dataset. Future users should be able to understand what rules were applied and what uncertainty remains.

[pause=1.0]

Slide 31: Heart-rate scenario

The heart-rate scenario shows why unusual does not always mean wrong.

[pause=0.7]

A value of minus one is clearly incompatible with an ordinary heart-rate measurement and should be flagged.

[pause=0.7]

A blank value is a completeness issue.

[pause=0.7]

A value of two hundred is extreme, but it may be physiologically possible in some contexts. That means we investigate before deleting it.

[pause=0.7]

Quality rules should help us find records that deserve attention. They should not replace domain reasoning.

[pause=1.0]

Slide 32: Quality decisions

After detecting a quality issue, we still need a decision.

[pause=0.7]

Correction is appropriate when we have evidence for the correct value. Exclusion may be appropriate for one analysis but should not mean silently destroying the source record.

[pause=0.7]

Imputation can be useful, but it introduces assumptions and should be justified.

[pause=0.7]

Sometimes the best choice is simply to retain the value and attach a quality flag.

[pause=0.7]

Good data preparation is transparent. The goal is not to make the dataset look perfect. The goal is to make analytical limitations explicit and manageable.

[pause=1.0]

Slide 33: Section: Variable meaning

We are moving to Part 3: measurement meaning.

[pause=0.7]

Now we focus on individual variables rather than the organization of the dataset.

[pause=0.7]

The central question is: what operations are meaningful for this variable?

[pause=0.7]

Measurement scales give us a framework for answering that question.

[pause=1.0]

Slide 34: Categorical or numeric

The first split is categorical versus numeric.

[pause=0.7]

Categorical variables represent labels or ordered levels. Nominal and ordinal variables live on this side.

[pause=0.8]

Numeric variables represent quantities. Interval and ratio variables live on this side.

[pause=0.7]

Do not decide only from the symbols in the file.

[pause=0.7]

A ZIP code contains digits but is categorical. A satisfaction score contains numbers but is usually ordinal.

[pause=0.7]

Start with the meaning of the values.

[pause=1.0]

Slide 35: Measurement decision tree

This decision tree gives you a simple reasoning process.

[pause=0.7]

First ask whether the values are labels or quantities.

[pause=0.8]

If they are labels, ask whether a meaningful order exists. No order suggests nominal. Meaningful order suggests ordinal.

[pause=0.8]

If they are quantities, ask whether the scale has a meaningful true zero. If not, interval may be appropriate. If yes, ratio may be appropriate.

[pause=0.7]

This framework works well for many common variables, but domain context still matters.

[pause=0.7]

When you are unsure, explain what arithmetic or comparison would be meaningful in the real world.

[pause=1.0]

Slide 36: Nominal scale

Nominal variables distinguish categories without placing them in an inherent order.

[pause=0.7]

Blood types are different, but one blood type is not greater than another.

[pause=0.7]

ZIP codes and patient IDs are common traps because they may contain digits. Those digits identify categories or records rather than measuring an amount.

[pause=0.7]

Counts and proportions are natural summaries for nominal variables.

[pause=0.7]

A bar chart is often a good starting visualization because bar length represents how common each category is without implying a numeric distance between category labels.

[pause=1.0]

Slide 37: Nominal visualization

Here is an example of a nominal-variable visualization.

[pause=0.8]

The bars show counts for blood-type categories. The length of the bars is quantitative, but the category labels themselves are not measured on a numeric scale.

[pause=0.8]

We can reorder the bars by frequency or use a conventional category order without changing the meaning of the variable.

[pause=0.7]

The chart helps compare prevalence without pretending that O minus A or B divided by AB is meaningful.

[pause=1.0]

Slide 38: Ordinal scale

Ordinal variables have a meaningful order.

[pause=0.7]

Urgent is more severe than non-urgent, and emergent is more severe than urgent.

[pause=0.7]

But the distance between those levels is not necessarily equal.

[pause=0.7]

That is why assigning codes zero, one, and two can be convenient for storage while still requiring care in analysis.

[pause=0.7]

Medians, percentiles, and ordered category displays are often useful. The key is to preserve rank without automatically inventing equal numerical spacing.

[pause=1.0]

Slide 39: Likert caution

Likert-style responses are a useful example of ordinal data.

[pause=0.8]

A response of five is higher than a response of four. But we cannot automatically assume that the difference between one and two is psychologically identical to the difference between four and five.

[pause=0.7]

Means are commonly reported in practice, especially for multi-item scales, but the decision should be justified.

[pause=0.7]

For a single coarse item, medians, distributions, and rank-based methods may provide a more defensible description, especially when responses are skewed.

[pause=1.0]

Slide 40: Interval scale

Interval scales support meaningful differences.

[pause=0.7]

A change of five degrees Celsius has the same size anywhere on the scale.

[pause=0.7]

But zero Celsius is not the absence of temperature.

[pause=0.7]

Because the zero point is arbitrary, ratios are not meaningful in the same way they are for a true ratio scale.

[pause=0.7]

This is why twenty degrees Celsius should not be described as twice as hot as ten degrees Celsius.

[pause=1.0]

Slide 41: Ratio scale

Ratio scales have equal differences and a meaningful zero.

[pause=0.7]

Zero ER visits means no visits. Zero elapsed seconds means no elapsed time.

[pause=0.7]

Because the zero point represents absence, ratios can be meaningful when the context supports them.

[pause=0.7]

Four visits are twice two visits. Ten kilograms is twice five kilograms.

[pause=0.7]

Ratio scales support the broadest range of arithmetic operations, but you still need to consider distribution, units, and whether a particular summary is appropriate.

[pause=1.0]

Slide 42: Interval vs ratio

Interval and ratio variables can look very similar because both are numeric and have meaningful differences.

[pause=0.7]

The key difference is the zero point.

[pause=0.7]

Celsius zero is a reference point, not the absence of temperature. Zero visits means no visits occurred.

[pause=0.7]

That difference determines whether ratio statements are meaningful.

[pause=0.7]

When classifying a numeric variable, ask what zero means in the real-world measurement process.

[pause=1.0]

Slide 43: Discrete counts

Discrete numeric variables often come from counting.

[pause=0.7]

A patient can have zero, one, two, or three emergency visits.

[pause=0.7]

For the individual count, values such as two point four visits usually do not make sense.

[pause=0.7]

Counts are usually ratio-scale variables because zero means none.

[pause=0.7]

They are often skewed and may contain many zeros, so later analytical methods should respect that distribution rather than assuming every numeric variable behaves like a symmetric continuous measurement.

[pause=1.0]

Slide 44: Continuous measurements

Continuous variables arise from measurement.

[pause=0.7]

Temperature, duration, height, and laboratory values are common examples.

[pause=0.8]

A device may report temperature to one decimal place or heart rate to a whole number, but that recording precision does not automatically change the underlying phenomenon into a discrete count.

[pause=0.7]

Think about how the value is generated.

[pause=0.7]

Was it counted as separate events, or measured along a scale?

[pause=0.7]

That conceptual distinction can matter later when choosing distributions, models, and transformations.

[pause=1.0]

Slide 45: Discrete vs continuous

This comparison is simple but important.

[pause=0.7]

Discrete variables come from counting. Continuous variables come from measurement.

[pause=0.7]

Storage does not always reveal the difference.

[pause=0.7]

A continuous variable may be rounded to an integer. A count may be stored as a floating-point value because of software defaults.

[pause=0.7]

Classify the concept first.

[pause=0.7]

Ask how the observation was generated in the real world.

[pause=1.0]

Slide 46: Classification traps

These classification traps are worth reviewing carefully.

[pause=0.7]

The visual appearance of a value often tempts us to classify it too quickly.

[pause=0.7]

ZIP code and patient ID are labels. Satisfaction is ordered but not necessarily equally spaced. Heart rate may be stored as an integer while representing a measured phenomenon.

[pause=0.8]

ER visits is a true count. Celsius temperature is interval rather than ratio.

[pause=0.7]

When in doubt, describe the variable in a sentence and ask what mathematical operations would make real-world sense.

[pause=1.0]

Slide 47: Section: From type to decision

Now we move from classification to decision-making.

[pause=0.7]

Knowing that a variable is nominal, ordinal, interval, or ratio should change what we do with it.

[pause=0.7]

We will connect measurement meaning to summaries, visualizations, and encoding choices.

[pause=0.7]

The goal is not to create rigid rules. It is to make choices that can be defended based on the variable's meaning.

[pause=1.0]

Slide 48: Decision guide

This decision guide connects classification to practical choices.

[pause=0.7]

Nominal variables naturally support counts and percentages. Ordinal variables add order, so medians and ordered displays can be useful.

[pause=0.7]

Continuous numeric variables often use histograms, box plots, means, or medians depending on distribution.

[pause=0.7]

Counts deserve special attention because they are numeric but may be heavily skewed or contain many zeros.

[pause=0.7]

Use this guide as a starting point. Distribution, study design, and analytical goals still matter.

[pause=1.0]

Slide 49: Visualization guide

Visualization should respect the structure of the variable.

[pause=0.7]

Bar charts are natural for nominal categories. Ordered bars preserve the sequence of ordinal categories.

[pause=0.7]

Histograms show the distribution of continuous numeric variables. Scatterplots show relationships between two numeric variables.

[pause=0.7]

A chart should make the intended comparison easier to see without implying structure that the data does not contain.

[pause=0.7]

For example, connecting unordered categories with a line can accidentally suggest continuity or progression where none exists.

[pause=1.0]

Slide 50: Summary statistics guide

Choosing a summary is also a conceptual decision.

[pause=0.7]

Counts and proportions work naturally for categories.

[pause=0.7]

Median and interquartile range are robust summaries for skewed numeric data and can also be useful with ordinal variables.

[pause=0.7]

Mean and standard deviation can be informative for numeric variables when the mean is meaningful and the distribution supports that description.

[pause=0.7]

Do not apply the same summary mechanically to every column in a dataframe.

[pause=0.7]

A data dictionary should help explain what each variable represents before the summary is chosen.

[pause=1.0]

Slide 51: Membership tier

Membership tier is an ordered category, but there is more than one way to represent it technically.

[pause=0.7]

An ordinal code preserves the rank from Bronze through Platinum.

[pause=0.7]

A one-hot representation creates separate indicators and avoids representing the category as a single numeric distance.

[pause=0.7]

Neither representation changes the underlying business meaning.

[pause=0.7]

The right choice depends on what the analytical method will infer from the values.

[pause=1.0]

Slide 52: One-hot encoding

One-hot encoding creates indicator columns.

[pause=0.7]

With Bronze as the reference category, Silver, Gold, and Platinum each receive their own column. Bronze is represented by zeros across those generated indicators.

[pause=0.7]

This is a common choice for nominal variables because a single integer code could cause some models to infer a false order or distance.

[pause=0.7]

One-hot encoding can also be used for ordered categories when you do not want the model to assume a simple linear spacing between ranks.

[pause=0.7]

The cost is that variables with many categories can create many columns.

[pause=1.0]

Slide 53: Ordinal encoding

Ordinal encoding maps ordered categories to ordered numbers.

[pause=0.7]

The advantage is that the representation is compact and preserves rank.

[pause=0.7]

The caution is that some analytical methods may treat the codes as if the distance from Bronze to Silver is the same as the distance from Gold to Platinum.

[pause=0.7]

That assumption may or may not be appropriate.

[pause=0.7]

Whenever you use ordinal codes, document the intended order and understand how the downstream model will interpret the values.

[pause=1.0]

Slide 54: Why integer codes can mislead

Integer codes are convenient, but they can introduce unintended meaning.

[pause=0.7]

If mobile, tablet, and desktop are nominal categories, assigning zero, one, and two creates a numerical order that does not exist conceptually.

[pause=0.7]

For membership tiers, a numeric order is more defensible because the business defines a rank.

[pause=0.7]

Even then, equal numeric spacing is an additional assumption.

[pause=0.7]

Before encoding a category with numbers, ask what the downstream method might infer from those numbers.

[pause=1.0]

Slide 55: Data leakage

One important idea to look ahead to is data leakage.

[pause=0.7]

Suppose we standardize numeric variables using the mean and standard deviation of the full dataset before evaluating a predictive model.

[pause=0.7]

Information from the validation or test set has influenced the transformation.

[pause=0.7]

A safer workflow fits encoders, scalers, and other learned preprocessing steps on the training data, then applies those fitted transformations to validation and test data.

[pause=0.7]

Module 1 is not a machine-learning module, but this habit is worth establishing early because preprocessing choices can affect the fairness of model evaluation.

Slide 66: Storage choices

Storage type is a practical engineering decision.

[pause=0.7]

Identifiers may use text, UUID, or integer keys depending on the system. Counts usually use integer types. Currency often uses exact numeric types rather than floating point.

[pause=0.7]

[pause=0.7]

The important point is that storage and measurement scale are related but not identical.

[pause=0.7]

A nominal identifier can be stored as a number. A ratio-scale measurement can be stored as text in a poorly designed file.

[pause=0.7]

Good implementation tries to preserve meaning and support appropriate validation.
