Slide 1: Start

Welcome to Module 3, PostgreSQL in Action. In Module 2, we focused on how a relational database is organized. Now we start using that database by reading rows, filtering results, and making controlled changes.

[pause=0.7]

The main goal is not to memorize a long list of SQL commands. Instead, I want you to develop a safe working pattern: understand the question, write the smallest useful statement, run it, inspect the result, and verify any change before keeping it.

[pause=0.8]

Many slides include PostgreSQL code that runs directly in your browser. You can test the examples here first, then use Copy and paste the same SQL into the pgAdmin Query Tool for more practice.

[pause=0.8]

We will begin with SELECT and filtering, then move carefully into INSERT, UPDATE, DELETE, transactions, and JSONB.

[pause=1.0]

Slide 2: Big picture

Module 2 was mostly about structure: tables, keys, relationships, and constraints. Module 3 is where we begin interacting with the data inside that structure.

[pause=0.7]

When we only read data, a mistake may return the wrong rows. When we start changing data, a mistake can also modify or remove rows. That is why we will use a repeatable safety process.

[pause=0.7]

First, define what you need. Then preview the rows that match. Use a stable identifier when possible. Execute the smallest correct statement, and inspect what PostgreSQL returns.

[pause=0.7]

For write operations, verification is especially important. If you are not sure what an UPDATE or DELETE will touch, run a SELECT with the same condition first.

[pause=1.0]

Slide 3: Learning path

We will approach SQL gradually.

[pause=0.7]

The first part is about reading data. You will use SELECT, choose columns, create aliases, apply filters, sort rows, and limit results.

[pause=0.7]

The second part is about changing data with INSERT, UPDATE, and DELETE. Here we add stronger safety habits such as previewing target rows, using unique keys, and using RETURNING to see what changed.

[pause=0.7]

The third part is about protection and control. Transactions let us test changes and either keep them with COMMIT or undo them with ROLLBACK.

[pause=0.7]

The exercises follow the same progression. First run complete examples, then change one piece, then complete missing parts, and finally write short statements yourself. Focus on understanding the pattern before trying to memorize syntax.

Slide 5: SQL language map

SQL commands are often grouped by the type of work they perform.

[pause=0.7]

DDL defines structure. Commands such as CREATE, ALTER, and DROP change the database schema. You saw much more of this in Module 2.

[pause=0.7]

DQL is commonly used to describe reading data, especially with SELECT.

[pause=0.7]

DML changes stored rows. INSERT adds rows, UPDATE changes existing rows, DELETE removes rows, and newer PostgreSQL versions also support MERGE for synchronization patterns.

[pause=0.7]

Transaction-control commands decide whether a group of changes should be kept or undone.

[pause=0.7]

The labels are useful, but the practical idea is simpler: know whether your statement is only reading data, changing rows, changing structure, or controlling a transaction. That tells you how carefully you need to verify the result.

[pause=1.0]

Slide 6: SELECT pattern

A SELECT query can be read almost like a sentence.

[pause=0.8]

SELECT tells PostgreSQL what columns or expressions should appear in the result. FROM tells it which table supplies the rows. WHERE can remove rows that do not meet a condition. ORDER BY controls presentation order, and LIMIT can keep only a chosen number of rows.

[pause=0.7]

You do not need every clause in every query. Start with the smallest version that answers the question.

[pause=0.8]

A good beginner habit is to list the columns you actually need. SELECT star is useful while exploring, but explicit columns make the result clearer and more predictable.

[pause=0.7]

Before writing a query, try saying the request in plain English. Then map each part of the sentence to the appropriate SQL clause.

[pause=0.7]

An alias changes the label shown in the result. It does not rename the stored database column.

[pause=0.7]

An expression can calculate a new value for the result without changing the table. For example, you might derive a value from age or combine text into a more readable label.

[pause=0.8]

Slide 10: WHERE basics

WHERE controls which source rows stay in the result.

[pause=0.7]

Different questions need different kinds of conditions. For direct comparisons, we can use equals, not equal, greater than, greater than or equal to, less than, or less than or equal to.

[pause=0.7]

BETWEEN is convenient for ranges. IN is useful when a value may belong to a short list. LIKE and PostgreSQL ILIKE support text patterns. Missing values need IS NULL or IS NOT NULL.

[pause=0.7]

We can also combine conditions with AND, OR, and NOT.

[pause=0.7]

A useful habit is to read the condition naturally. Age greater than or equal to sixty-five means sixty-five is included. When conditions become longer, use parentheses to make the intended grouping obvious rather than depending on memory of operator precedence.

BETWEEN is helpful for a continuous range. When we say age between thirty and sixty, both endpoints are included.

[pause=0.7]

IN is useful when a column may match one of several listed values. Instead of writing several OR conditions, we can list the allowed values together.

Slide 13: ILIKE

PostgreSQL provides ILIKE for case-insensitive text pattern matching.

[pause=0.7]

The percent sign represents any sequence of characters. A pattern such as C followed by percent means starts with C. Percent followed by son means ends with son. Percent on both sides searches for text appearing anywhere inside the value.

[pause=0.7]

[pause=0.8]

Then try changing the search pattern. Before each run, predict what kind of names should appear.

[pause=0.8]

ILIKE is useful when capitalization should not matter. LIKE is similar, but case behavior can differ depending on the database and collation.

[pause=0.7]

Pattern matching is convenient, but broad patterns can also return many rows. Use a pattern that reflects the actual search requirement.

Slide 14: NULL

NULL represents missing or unknown information, and it does not behave like an ordinary value.

[pause=0.7]

A common beginner mistake is to write a condition that says a column equals NULL. That does not correctly test for missing information.

[pause=0.7]

Instead, use IS NULL when you want rows where a value is missing, and IS NOT NULL when you want rows where a value is present.

[pause=0.7]

In this example, a missing discharge date means the admission is still open.

[pause=0.8]

Run the query and inspect the rows that are returned. Look specifically at the discharge-date column.

[pause=0.8]

A simple way to remember this is that NULL is not a normal value such as zero or an empty string. It represents the absence of a known value, so SQL gives it special predicates.

Slide 15: Sort limit distinct

Three common tools help organize query results.

[pause=0.8]

ORDER BY controls the row order. LIMIT keeps only a chosen number of result rows. DISTINCT removes repeated result rows.

[pause=0.7]

The important point is that LIMIT by itself does not mean latest, oldest, highest, or best. Without a deterministic ORDER BY, PostgreSQL is free to return any qualifying subset.

[pause=0.7]

Run the example that asks for the three most recent admissions. Notice that the date is sorted in descending order before the limit is applied.

[pause=0.8]

Now imagine removing ORDER BY. You may still get three rows, but you would no longer have a reliable reason to call them the three most recent.

[pause=0.7]

Use sorting to define what top or recent actually means before applying a limit.

Slide 16: Logical order

SQL is written in one order, but it is useful to think about its logical processing in another order.

[pause=0.7]

For a simple query, PostgreSQL first identifies the source in FROM, then applies WHERE to filter rows. SELECT defines the result expressions. DISTINCT can remove repeated result rows. ORDER BY sorts the remaining result, and LIMIT keeps the requested number of rows.

[pause=0.8]

This mental model helps explain why filtering happens before sorting.

[pause=0.7]

It also helps explain why an alias created in SELECT is not always available in earlier logical stages.

[pause=0.7]

You do not need to memorize database-engine internals. Use this as a reasoning model. When a query behaves differently from what you expected, ask which stage creates or removes the value you are trying to use.

Slide 18: DML safety

Now we move from reading data to changing stored rows, so our safety habits become more important.

[pause=0.7]

Before an UPDATE or DELETE, preview the target rows with SELECT. Use the same WHERE condition you intend to use in the write statement.

[pause=0.7]

Whenever possible, identify rows with a stable primary key or unique key rather than a name or other value that may repeat.

[pause=0.7]

A transaction can provide another layer of protection because you can inspect a change before deciding whether to keep it.

[pause=0.7]

RETURNING is also very useful in PostgreSQL because it immediately shows the rows that were inserted, updated, or deleted.

[pause=0.7]

The most important warning is simple: an UPDATE or DELETE without an appropriate WHERE clause can affect every row in the table.

Slide 22: DELETE

DELETE physically removes rows, so we need to distinguish it from a soft-delete pattern.

[pause=0.7]

A soft delete keeps the row but changes a status field such as is active. That can preserve history while excluding the record from normal active views.

[pause=0.7]

A hard delete removes the row from the table.

[pause=0.7]

Run the soft-delete example and inspect the row after the change. Notice that the patient still exists but the active flag has changed.

[pause=0.8]

Whether a system should use soft or hard deletion depends on retention requirements, audit needs, and business rules.

[pause=0.7]

Before any hard delete, preview the exact target rows. Also remember that foreign-key constraints may block a deletion when related records depend on that row.

Slide 24: Transactions

Transactions let us group changes into a controlled unit of work.

[pause=0.7]

BEGIN starts the transaction. After that, changes are visible inside the transaction but have not yet been permanently kept.

[pause=0.7]

COMMIT keeps the changes. ROLLBACK discards them.

[pause=0.7]

In this example, we change a value, inspect the changed row, and then roll the transaction back.

[pause=0.8]

Before running it, note the original age. Then run the code and follow the output. You should see the temporary changed value, and after the rollback the final SELECT should show the original value again.

[pause=0.8]

This is a safe way to practice write statements. In pgAdmin, transactions are also useful when testing a change before deciding whether the result should be committed.

[pause=1.0]

Slide 25: ACID

ACID is a common way to describe important transaction properties.

[pause=0.7]

Atomicity means a related group of changes is treated as one unit. Either the intended transaction succeeds or its work can be undone.

[pause=0.7]

Consistency means database rules and constraints should still hold when a valid transaction finishes.

[pause=0.7]

Isolation deals with concurrent work so transactions do not incorrectly interfere with each other's intermediate states.

[pause=0.7]

Durability means that once a transaction is committed in a durable database system, the committed result is intended to persist even after failures.

[pause=0.7]

For this beginner module, the practical takeaway is not to memorize definitions word for word. Understand why transactions are useful: they give us a controlled boundary around related changes and a clear choice between keeping them and undoing them.

Slide 30: MERGE optional

MERGE is an optional advanced topic in this module.

[pause=0.7]

It can synchronize a source dataset with a target table. If a source record matches an existing target record, one action such as UPDATE can run. If there is no match, another action such as INSERT can run.

[pause=0.8]

The most important part is the matching condition because it defines what PostgreSQL considers the same record.

[pause=0.7]

If your browser engine supports the example, run it and inspect how matched and unmatched rows are handled.

[pause=0.8]

Do not worry if MERGE feels more complex than the earlier DML statements. The core skills are still SELECT, INSERT, UPDATE, and safe matching.

[pause=0.7]

Before using MERGE in important workflows, check for duplicate source keys and verify the match logic very carefully.

Slide 31: Common mistakes

This slide collects several mistakes that are easy to make when learning SQL.

[pause=0.7]

Use IS NULL rather than equality when testing missing values.

[pause=0.7]

When AND and OR appear together, add parentheses so the intended logic is visible.

[pause=0.7]

Do not use LIMIT to claim you have the top or latest rows unless ORDER BY defines what top or latest means.

[pause=0.7]

Avoid updating records by a name when a stable unique key is available.

[pause=0.7]

And before DELETE, preview the target rows with SELECT.

[pause=0.7]

These habits may look small, but they prevent large errors.

[pause=0.7]

When debugging, do not change many parts of the query at once. Read the requirement, identify the specific clause that is responsible, change one thing, run it again, and inspect what changed.

Slide 43: Summary

Let's summarize Module 3.

[pause=0.7]

SELECT defines the data you want to retrieve. WHERE and related predicates decide which rows qualify. ORDER BY, LIMIT, and DISTINCT help organize the result.

[pause=0.7]

INSERT adds rows. UPDATE changes rows. DELETE can remove rows. Because those commands change stored data, previewing targets and using stable keys are important safety habits.

[pause=0.7]

Constraints protect data rules and relationships. Transactions give you a boundary where changes can be committed or rolled back. RETURNING helps you inspect what PostgreSQL changed.

[pause=0.7]

JSONB extends PostgreSQL to semi-structured values, while INSERT INTO SELECT connects query results to data-preparation workflows.

[pause=0.8]

The habit to carry forward is simple: understand the request, preview the target, make the smallest correct change, inspect the result, and verify before you keep it.
