Cleaning habit

Profile → preserve raw values → normalize explicit representations → validate → resolve duplicates → prevent recurrence.

Start here

Data cleaning is evidence-based decision making

Cleaning is not the act of making every field look complete. It is a controlled process for identifying defects, distinguishing formatting differences from true errors, preserving source evidence, and creating an analytical representation whose rules can be explained and reproduced.

Learning objectives

  • Profile missingness, blanks, placeholders, and invalid values.
  • Standardize text, categorical, and contact fields without hiding uncertainty.
  • Detect duplicate groups and define explicit survivor rules.
  • Build validation queries and quarantine questionable rows for review.
  • Use PostgreSQL constraints to prevent known defects from recurring.
  • Apply transactions, views, and RETURNING for safer cleaning workflows.
  • Create transparent completeness, validity, and uniqueness metrics.

Core principle

Invalid does not mean “replace with a plausible value.” A negative price, malformed email, impossible date, or missing phone number is evidence about source quality.

Do not silently repair uncertainty. For example, converting a negative price to ABS(price) changes a value without proving what the correct price should be.
Conceptual foundation

A six-stage cleaning workflow

1. ProfileCount missing, invalid, duplicate, and unusual values.
2. PreserveKeep raw values or immutable source tables.
3. NormalizeStandardize representation only where rules are known.
4. ValidateTest values against documented domains and constraints.
5. ResolveDeduplicate or quarantine using explicit rules.
6. PreventAdd constraints and monitoring after the data is understood.

Source record

name' JANE SMITH '
email' JANE.SMITH@EMAIL.COM '
phone'336.555.1202'
→

Analytical representation

name'Jane Smith'
email'jane.smith@email.com'
phone'3365551202'
Keep the transformation rule and the source value. A cleaned field is an interpretation of the source, not a replacement for provenance.

Missing data

NULL, blank text, sentinel values, and unknown are different states

NULL

No SQL value is present. Use IS NULL.

'' / ' '

Text exists but may carry no useful content.

'0000000000'

A placeholder may look valid syntactically while being semantically missing.

'3365551201'

A candidate value still needs domain validation.

COALESCE supplies a fallback representation; it does not recover the missing fact. Keep fallback labels distinguishable from observed values.
Standardization

Normalize representation without pretending to know the truth

Standardization improves comparability: case, spacing, punctuation, and category labels can often be normalized by documented rules. The operation should be deterministic and reviewable.

Names

Trim boundaries, collapse repeated whitespace, and optionally apply presentation case.

REGEXP_REPLACE + INITCAP

Emails

Trim and lowercase for comparison. Validate shape separately.

LOWER(BTRIM(email))

Phone numbers

Strip formatting punctuation, then validate digit count; do not fabricate missing digits.

REGEXP_REPLACE(...)
PostgreSQL
SELECT id, name AS raw_name,
       INITCAP(REGEXP_REPLACE(BTRIM(name), '[[:space:]]+', ' ', 'g')) AS clean_name
FROM customers
ORDER BY id;
PostgreSQL
SELECT id, phone AS raw_phone,
       NULLIF(REGEXP_REPLACE(COALESCE(phone,''), '[^0-9]', '', 'g'),'') AS digits_only,
       CASE
         WHEN LENGTH(REGEXP_REPLACE(COALESCE(phone,''), '[^0-9]', '', 'g')) = 10
         THEN REGEXP_REPLACE(COALESCE(phone,''), '[^0-9]', '', 'g')
         ELSE NULL
       END AS valid_10_digit_phone
FROM customers
ORDER BY id;

Categorical mapping is a business rule

PostgreSQL
SELECT id, product_name, category AS raw_category,
       CASE
         WHEN NULLIF(BTRIM(category),'') IS NULL THEN NULL
         WHEN LOWER(BTRIM(category)) IN ('electronics','electronic','tech') THEN 'Electronics'
         WHEN LOWER(BTRIM(category)) IN ('audio','headphones') THEN 'Audio'
         WHEN LOWER(BTRIM(category)) IN ('stationery','office supplies') THEN 'Stationery'
         WHEN LOWER(BTRIM(category)) IN ('home office','home & garden') THEN 'Home Office'
         ELSE INITCAP(BTRIM(category))
       END AS standard_category
FROM products
ORDER BY id;
Do not repair an invalid numeric value by assumption. The source module used ABS(price) for negative prices. A negative price should normally be flagged for investigation because its intended value is unknown.
PostgreSQL
SELECT id, product_name, price,
       CASE
         WHEN price IS NULL THEN 'missing'
         WHEN price <= 0 THEN 'invalid - review'
         ELSE 'valid candidate'
       END AS price_status
FROM products
ORDER BY id;
Duplicate resolution

Find duplicate groups first; choose survivors second

Duplicate detection and duplicate resolution are separate decisions. Normalize the matching key, inspect the group, then define which row survives using completeness, recency, source priority, or another documented rule.

A heuristic signal should create a review candidate, not an automatic delete.

PostgreSQL
SELECT LOWER(BTRIM(email)) AS email_key,
       INITCAP(REGEXP_REPLACE(BTRIM(name), '[[:space:]]+', ' ', 'g')) AS name_key,
       COUNT(*) AS row_count,
       ARRAY_AGG(id ORDER BY id) AS source_ids
FROM customers
WHERE NULLIF(BTRIM(email),'') IS NOT NULL
GROUP BY LOWER(BTRIM(email)), INITCAP(REGEXP_REPLACE(BTRIM(name), '[[:space:]]+', ' ', 'g'))
HAVING COUNT(*) > 1;
PostgreSQL
WITH scored AS (
  SELECT c.*,
         (CASE WHEN NULLIF(BTRIM(name),'') IS NOT NULL THEN 1 ELSE 0 END +
          CASE WHEN NULLIF(BTRIM(email),'') IS NOT NULL THEN 1 ELSE 0 END +
          CASE WHEN NULLIF(BTRIM(phone),'') IS NOT NULL THEN 1 ELSE 0 END +
          CASE WHEN NULLIF(BTRIM(address),'') IS NOT NULL THEN 1 ELSE 0 END) AS completeness_score
  FROM customers AS c
), ranked AS (
  SELECT *, ROW_NUMBER() OVER (
      PARTITION BY LOWER(BTRIM(email)), INITCAP(REGEXP_REPLACE(BTRIM(name),'[[:space:]]+',' ','g'))
      ORDER BY completeness_score DESC, signup_date DESC NULLS LAST, id
  ) AS survivor_rank
  FROM scored
)
SELECT id, name, email, completeness_score, survivor_rank
FROM ranked
WHERE LOWER(BTRIM(email)) = 'duplicate@test.com'
ORDER BY survivor_rank;
A first-five-characters name rule is not reliable duplicate proof. Use fuzzy matching only as a candidate-generation technique and keep human/business review in the loop when false matches matter.
Validation

Separate detection from correction with a quarantine pattern

Source rows

Observed values as received.

→
Rule checks

Required fields, regex shape, ranges, allowed categories.

→
Candidate clean + review queue

Valid-looking rows continue; questionable rows retain evidence.

PostgreSQL
SELECT id, email,
       CASE
         WHEN NULLIF(BTRIM(email),'') IS NULL THEN 'missing'
         WHEN LOWER(BTRIM(email)) ~ '^[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}$' THEN 'valid shape'
         ELSE 'review'
       END AS email_status
FROM customers
ORDER BY id;
PostgreSQL
WITH issues AS (
  SELECT id, 'customer' AS entity, 'invalid_email' AS issue
  FROM customers WHERE NULLIF(BTRIM(email),'') IS NOT NULL AND LOWER(BTRIM(email)) !~ '^[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}$'
  UNION ALL
  SELECT id, 'customer', 'invalid_phone'
  FROM customers WHERE NULLIF(BTRIM(phone),'') IS NOT NULL AND LENGTH(REGEXP_REPLACE(phone,'[^0-9]','','g')) <> 10
  UNION ALL
  SELECT id, 'product', 'invalid_price'
  FROM products WHERE price IS NULL OR price <= 0
)
SELECT entity, issue, COUNT(*) AS issue_count
FROM issues
GROUP BY entity, issue
ORDER BY issue_count DESC, entity, issue;
Validation is not truth verification. A regex can tell you that an email has a plausible shape; it cannot prove that the mailbox exists or belongs to the person.
PostgreSQL
CREATE OR REPLACE VIEW customer_quality_issues AS
SELECT id, name, email, phone,
       CASE WHEN NULLIF(BTRIM(name),'') IS NULL THEN true ELSE false END AS missing_name,
       CASE WHEN NULLIF(BTRIM(email),'') IS NOT NULL AND LOWER(BTRIM(email)) !~ '^[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}$' THEN true ELSE false END AS invalid_email,
       CASE WHEN NULLIF(BTRIM(phone),'') IS NOT NULL AND LENGTH(REGEXP_REPLACE(phone,'[^0-9]','','g')) <> 10 THEN true ELSE false END AS invalid_phone
FROM customers;
SELECT * FROM customer_quality_issues
WHERE missing_name OR invalid_email OR invalid_phone
ORDER BY id;
Prevention

Once the rules are known, move quality checks closer to data entry

NOT NULL

Use when the business process truly requires a value.

CHECK

Enforce ranges, allowed patterns, or cross-column logic.

UNIQUE

Prevent duplicate candidate keys when identity rules support it.

FOREIGN KEY

Protect references to related entities.

Add constraints after profiling and cleaning legacy data; otherwise valid constraints may fail immediately because existing rows violate the new rule.

PostgreSQL
DROP TABLE IF EXISTS validated_contacts;
CREATE TABLE validated_contacts (
  contact_id integer PRIMARY KEY,
  email text NOT NULL,
  phone text,
  CONSTRAINT email_shape_chk CHECK (email ~ '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$'),
  CONSTRAINT phone_digits_chk CHECK (phone IS NULL OR phone ~ '^[0-9]{10}$'),
  CONSTRAINT email_unique UNIQUE (email)
);
INSERT INTO validated_contacts VALUES (1,'student@example.com','3365551212');
SELECT * FROM validated_contacts;
Cleaning repairs historical data; constraints reduce future defects. Mature data-quality workflows need both.
Safe transformations

Preview before you update, and make destructive changes reversible

1. SELECTPreview affected rows.
2. BEGINOpen a transaction.
3. UPDATEApply one explicit rule.
4. RETURNINGInspect changed rows.
5. COMMIT / ROLLBACKKeep or discard deliberately.
PostgreSQL
BEGIN;
UPDATE customers
SET email = LOWER(BTRIM(email))
WHERE email IS NOT NULL
  AND email IS DISTINCT FROM LOWER(BTRIM(email))
RETURNING id, email;
ROLLBACK;

Prefer cleaned views/tables when provenance matters

PostgreSQL
CREATE OR REPLACE VIEW customers_clean_preview AS
SELECT id,
       INITCAP(REGEXP_REPLACE(BTRIM(name),'[[:space:]]+',' ','g')) AS clean_name,
       LOWER(NULLIF(BTRIM(email),'')) AS clean_email,
       CASE WHEN LENGTH(REGEXP_REPLACE(COALESCE(phone,''),'[^0-9]','','g'))=10
            THEN REGEXP_REPLACE(phone,'[^0-9]','','g') ELSE NULL END AS clean_phone,
       NULLIF(BTRIM(address),'') AS clean_address,
       signup_date
FROM customers;
SELECT * FROM customers_clean_preview ORDER BY id;
The original cleaning exercise defaulted invalid dates to the current timestamp. That invents a date and destroys the distinction between “invalid” and “today.” The revised workflow returns NULL plus a review status instead.
Measurement

Measure separate dimensions before collapsing them into one score

C
CompletenessIs a required value present?
V
ValidityDoes it satisfy the documented rule?
U
UniquenessAre duplicate identities controlled?
T
TimelinessIs it current enough for the use case?

A single quality score can be useful for triage, but its weights are policy choices. Keep the component checks visible so stakeholders know what the score means.

PostgreSQL
SELECT id, name,
       (CASE WHEN NULLIF(BTRIM(name),'') IS NOT NULL THEN 25 ELSE 0 END +
        CASE WHEN LOWER(COALESCE(BTRIM(email),'')) ~ '^[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}$' THEN 25 ELSE 0 END +
        CASE WHEN LENGTH(REGEXP_REPLACE(COALESCE(phone,''),'[^0-9]','','g')) = 10 THEN 25 ELSE 0 END +
        CASE WHEN signup_date IS NOT NULL AND signup_date <= DATE '2026-08-12' THEN 25 ELSE 0 END) AS illustrative_quality_score
FROM customers
ORDER BY illustrative_quality_score, id;
PostgreSQL
WITH scored AS (
 SELECT id,
       (CASE WHEN NULLIF(BTRIM(name),'') IS NOT NULL THEN 25 ELSE 0 END +
        CASE WHEN LOWER(COALESCE(BTRIM(email),'')) ~ '^[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}$' THEN 25 ELSE 0 END +
        CASE WHEN LENGTH(REGEXP_REPLACE(COALESCE(phone,''),'[^0-9]','','g')) = 10 THEN 25 ELSE 0 END +
        CASE WHEN signup_date IS NOT NULL AND signup_date <= DATE '2026-08-12' THEN 25 ELSE 0 END) AS score
 FROM customers
)
SELECT CASE WHEN score=100 THEN 'Excellent'
            WHEN score>=75 THEN 'Good'
            WHEN score>=50 THEN 'Fair'
            ELSE 'Poor' END AS quality_band,
       COUNT(*) AS customer_count
FROM scored
GROUP BY 1
ORDER BY MIN(score) DESC;

Apply the workflow

Integrated customer-cleaning project

The staging table intentionally contains inconsistent case, extra whitespace, punctuation differences, missing values, two date formats, one invalid date string, an empty name, and a duplicate customer. Your goal is not to guess missing facts; it is to create a transparent candidate-clean dataset and a review queue.

Deliverable 1

Normalize names, emails, and phone formatting.

Deliverable 2

Parse supported date formats and leave unsupported values as NULL.

Deliverable 3

Rank duplicates and label rows that require review.

PostgreSQL
WITH normalized AS (
 SELECT id,
        NULLIF(REGEXP_REPLACE(BTRIM(full_name),'[[:space:]]+',' ','g'),'') AS name_norm,
        LOWER(NULLIF(BTRIM(email),'')) AS email_norm,
        NULLIF(REGEXP_REPLACE(COALESCE(phone,''),'[^0-9]','','g'),'') AS phone_digits,
        signup_date_raw
 FROM messy_customers
), typed AS (
 SELECT *,
        CASE WHEN signup_date_raw ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$' THEN signup_date_raw::date
             WHEN signup_date_raw ~ '^[0-9]{2}/[0-9]{2}/[0-9]{4}$' THEN TO_DATE(signup_date_raw,'MM/DD/YYYY')
             ELSE NULL END AS signup_date_clean
 FROM normalized
), ranked AS (
 SELECT *, ROW_NUMBER() OVER (
   PARTITION BY email_norm, INITCAP(name_norm)
   ORDER BY (CASE WHEN name_norm IS NOT NULL THEN 1 ELSE 0 END + CASE WHEN email_norm IS NOT NULL THEN 1 ELSE 0 END + CASE WHEN LENGTH(phone_digits)=10 THEN 1 ELSE 0 END + CASE WHEN signup_date_clean IS NOT NULL THEN 1 ELSE 0 END) DESC, id
 ) AS duplicate_rank
 FROM typed
)
SELECT id, INITCAP(name_norm) AS clean_name, email_norm AS clean_email,
       CASE WHEN LENGTH(phone_digits)=10 THEN phone_digits ELSE NULL END AS clean_phone,
       signup_date_clean,
       duplicate_rank,
       CASE WHEN name_norm IS NULL OR email_norm IS NULL OR signup_date_clean IS NULL OR (phone_digits IS NOT NULL AND LENGTH(phone_digits)<>10) THEN 'review' ELSE 'candidate clean row' END AS row_status
FROM ranked
ORDER BY duplicate_rank, id;
A production version would usually persist the cleaned candidate table together with lineage fields such as source ID, cleaning version, rule timestamp, and issue codes.
Assessment and closure

Can you clean data without hiding uncertainty?

Recognition

  1. Why is NULL different from blank text?
  2. Why should invalid numeric values usually be flagged before correction?
  3. What is the difference between duplicate detection and survivor selection?
  4. What does a regex validation rule prove—and what does it not prove?
  5. Why should cleaning updates use a transaction and RETURNING?
  6. When should a quality rule become a database constraint?

Applied challenge

Produce one row per customer with normalized name, email, and phone; a quality status; and a duplicate rank. Preserve source rows and do not overwrite the original table.

Key takeaways

  • Profile before changing data.
  • Distinguish missing, blank, placeholder, invalid, and valid-looking values.
  • Standardization changes representation; correction claims knowledge about the underlying fact.
  • Deduplication requires an identity key plus an explicit survivor rule.
  • Quarantine questionable records rather than inventing replacements.
  • Use constraints to prevent known defects after legacy data has been reconciled.
  • Use transactions, views, and lineage-friendly structures for reproducible cleaning.
  • Measure quality dimensions separately even when a composite score is useful.
