Slide 1: Start

Welcome to Module 7, Subqueries in PostgreSQL.

[pause=0.7]

A subquery is a query used inside another query. The important part is not the parentheses. The important part is understanding what the inner query returns and what the outer query expects.

[pause=0.8]

We will build this gradually, starting with result shapes and then moving through scalar subqueries, membership, existence, ANY and ALL, correlated subqueries, and derived tables.

[pause=0.7]

Every SQL example can run directly in the browser. You can also copy the query into pgAdmin for more practice.

[pause=1.0]

Slide 2: Why subqueries matter

Subqueries become useful when one part of the question depends on the result of another query.

[pause=0.8]

Sometimes the inner query produces one benchmark such as average age.

[pause=0.8]

Sometimes it produces a set of patient IDs.

[pause=0.7]

Sometimes we only need to know whether a matching related row exists.

[pause=0.7]

And sometimes the inner query depends on the current outer row.

[pause=0.8]

These are different contracts, and recognizing the contract is more useful than memorizing syntax.

[pause=1.0]

Slide 8: The main mental model

The best mental model is to treat the inner query as a result producer.

[pause=0.8]

The inner query produces something.

[pause=0.8]

The outer query then uses that result.

[pause=0.8]

The result might be one value, a set of values, or rows that behave like an intermediate table.

[pause=0.7]

Before writing the SQL, ask what shape the outer query needs.

[pause=0.8]

That question prevents many common subquery errors.

[pause=1.0]

Slide 9: Three common result shapes

Three ideas appear repeatedly.

[pause=0.7]

A scalar subquery behaves like one value.

[pause=0.8]

A set subquery returns zero or more values, usually from one column.

[pause=0.8]

A correlated subquery refers to the current outer row, so its result can change as the outer row changes.

[pause=0.8]

When you identify the shape and dependency, the SQL operator becomes easier to choose.

Slide 11: Scalar subquery contract

A scalar subquery has a strict result contract.

[pause=0.8]

It returns one column and at most one row.

[pause=0.7]

One row gives the scalar value.

[pause=0.7]

Zero rows become NULL.

[pause=0.7]

More than one row is an error because the surrounding expression expected one value.

[pause=0.7]

Understanding this contract is more important than remembering where the parentheses go.

[pause=1.0]

Slide 15: Scalar with zero rows

A scalar subquery may return zero rows.

When that happens, PostgreSQL turns the missing scalar into NULL.

[pause=0.8]

Slide 18: IN means membership

IN is a membership operator.

[pause=0.7]

The inner query should return a one-column set.

[pause=0.8]

The outer value is compared with the values in that set.

[pause=0.7]

If it matches one of them, the membership test succeeds.

[pause=0.7]

Think of IN as asking, is this value in that returned list?

[pause=1.0]

[pause=0.8]

This is a natural use of IN because the business question is membership.

Slide 20: IN is not a JOIN

IN and JOIN may appear to answer similar questions, but they have different semantics.

[pause=0.7]

IN asks whether an outer value belongs to a set.

[pause=0.7]

A join returns matching row combinations.

[pause=0.7]

If one patient has multiple admissions, the join can repeat that patient.

[pause=0.7]

The IN query keeps the patient-level outer grain.

[pause=0.8]

Run both queries and compare the outputs carefully.

[pause=1.0]

Slide 21: NOT IN looks simple

NOT IN looks like a simple anti-membership test.

[pause=0.7]

But if the inner set contains NULL, PostgreSQL cannot prove that an outer value differs from the unknown value.

[pause=0.7]

The condition can become UNKNOWN rather than TRUE.

[pause=0.7]

Because WHERE keeps only TRUE, rows you expected may disappear.

[pause=0.7]

This is one of the most important edge cases in this module.

[pause=1.0]

Slide 22: Three-valued logic

SQL uses three-valued logic.

[pause=0.7]

A condition can be TRUE, FALSE, or UNKNOWN.

[pause=0.7]

Comparing a normal value with NULL gives UNKNOWN, not FALSE.

[pause=0.7]

And NOT UNKNOWN remains UNKNOWN.

[pause=0.7]

Because WHERE returns only rows whose condition is TRUE, UNKNOWN behaves like a filtered-out row.

[pause=0.7]

This explains the NOT IN behavior.

[pause=1.0]

Slide 23: NOT IN + NULL trap

The review queue contains patient 1003 and a NULL.

[pause=0.7]

For another patient such as 1001, PostgreSQL knows 1001 is not equal to 1003.

[pause=0.7]

But it cannot know whether 1001 is different from the NULL value.

[pause=0.7]

That unknown comparison prevents the full NOT IN condition from becoming TRUE.

[pause=0.7]

Run the query and observe the result.

[pause=1.0]

Slide 24: Safer anti-match

NOT EXISTS expresses the anti-match directly.

[pause=0.7]

For each patient, the inner query searches for a review-queue row with the same patient ID.

[pause=0.8]

If no matching row exists, the patient is kept.

[pause=0.7]

The unrelated NULL row does not create the same problem because it does not match the current patient ID.

[pause=0.7]

This is why NOT EXISTS is often the clearer starting point for anti-join questions.

[pause=1.0]

Slide 25: EXISTS means existence

EXISTS asks only whether the inner query returns at least one row.

[pause=0.8]

The actual selected value inside the subquery usually does not matter.

[pause=0.8]

That is why SELECT one is common.

[pause=0.7]

The business meaning is simply: does any related row satisfy this condition?

[pause=0.7]

This makes EXISTS especially natural for relationship checks.

[pause=1.0]

[pause=0.7]

We do not need a count.

[pause=0.7]

Slide 27: NOT EXISTS example

NOT EXISTS asks whether no matching row can be found.

[pause=0.7]

For each patient, the inner query searches prescriptions.

[pause=0.8]

If there is no prescription with that patient ID, the patient is returned.

[pause=0.7]

This pattern appears everywhere: customers with no orders, students with no submissions, devices with no alerts, and patients with no prescription record.

Slide 28: IN vs EXISTS

IN and EXISTS can sometimes be rewritten into equivalent forms.

[pause=0.7]

But when writing the first version, choose the operator that expresses the business question clearly.

[pause=0.7]

Membership suggests IN.

[pause=0.7]

Existence suggests EXISTS.

[pause=0.7]

Absence of a related match suggests NOT EXISTS.

[pause=0.7]

Clear semantics make the query easier to explain, review, and debug.

[pause=1.0]

Slide 29: ANY, SOME, and ALL

ANY and ALL compare one outer value with an entire set.

[pause=0.7]

ANY means at least one comparison must succeed.

[pause=0.7]

ALL means every comparison must succeed.

[pause=0.7]

PostgreSQL also supports SOME as a synonym for ANY.

[pause=0.7]

The difference sounds small, but it can produce very different result sets.

[pause=1.0]

[pause=0.8]

For a nonempty set without NULL complications, a helpful intuition is to compare with the minimum.

[pause=0.7]

If your age is greater than the smallest returned age, at least one comparison succeeds.

Slide 31: ALL example

Greater than ALL is stricter.

[pause=0.7]

The outer age must be greater than every age returned by the inner query.

[pause=0.8]

A useful intuition is to compare with the maximum.

[pause=0.7]

To be greater than all returned ages, the outer value must exceed the largest one.

[pause=0.7]

[pause=1.0]

Slide 32: ANY vs ALL

ANY and ALL can be summarized with a simple contrast.

[pause=0.7]

ANY needs at least one successful comparison.

[pause=0.7]

ALL needs every comparison to succeed.

[pause=0.7]

Equality with ANY behaves much like IN.

[pause=0.7]

These are useful intuitions, but always remember that NULL values and empty sets can affect the formal SQL logic.

[pause=1.0]

Slide 33: Empty set behavior

Empty sets create an important edge case.

[pause=0.7]

ANY needs at least one successful comparison.

[pause=0.7]

If the set is empty, no comparison can succeed, so ANY is FALSE.

[pause=0.7]

ALL asks whether every comparison succeeds. With no values, there is no failing comparison, so ALL is TRUE.

[pause=0.7]

This can feel surprising, but it follows the logic of existential and universal conditions.

[pause=1.0]

Slide 34: Correlated subqueries

A correlated subquery uses a value from the current outer row.

[pause=0.8]

For example, the outer query may define patients as p.

[pause=0.8]

Inside the subquery, a condition may compare a child patient ID with p patient ID.

[pause=0.8]

When the outer patient changes, the inner query's matching value changes too.

[pause=0.8]

This is why correlated subqueries are useful for per-row calculations.

[pause=1.0]

Slide 35: How to spot correlation

To identify correlation, look for an alias that was defined outside the subquery but used inside it.

[pause=0.8]

If the inner query needs p patient ID from the outer patient row, it is correlated.

[pause=0.8]

A quick diagnostic is to ask whether the inner query can run meaningfully by itself unchanged.

[pause=0.8]

If it needs an outer value, the answer is no.

[pause=1.0]

Slide 40: Subquery placement

Subqueries can appear in different clauses because each clause expects a different role.

[pause=0.7]

A subquery in WHERE contributes to filtering.

[pause=0.8]

A scalar subquery in SELECT becomes an output value.

[pause=0.8]

A subquery in FROM becomes an intermediate table.

[pause=0.8]

Choose the placement based on what you need the inner result to do.

[pause=1.0]

Slide 41: Subquery in WHERE

WHERE is the most familiar location for subqueries.

[pause=0.7]

The inner result can become a benchmark, a membership set, an existence condition, or a set comparison.

[pause=0.7]

The final job is always Boolean: should the current outer row remain?

[pause=0.7]

That is why many subquery patterns appear naturally in WHERE.

[pause=1.0]

Slide 42: Subquery in SELECT

A subquery in SELECT must behave like a scalar for each output row.

[pause=0.8]

If it is uncorrelated, the same value may repeat.

[pause=0.7]

If it is correlated, the value can change from row to row.

[pause=0.7]

This placement is useful when you want to enrich each row with one related summary value.

[pause=1.0]

Slide 43: Derived tables

A subquery in FROM is called a derived table.

[pause=0.8]

The inner query produces rows and columns.

[pause=0.8]

The outer query treats those rows like an intermediate table for that statement.

[pause=0.8]

This is especially useful when you want to aggregate first and then join.

[pause=0.7]

Always ask what one row in the derived table represents.

[pause=1.0]

Slide 45: Correlated vs pre-aggregated

A correlated scalar and a pre-aggregated join can sometimes produce the same result.

[pause=0.7]

The correlated form may be simpler to read.

[pause=0.7]

The derived-table form may be convenient when several aggregated features are needed.

[pause=0.7]

Do not assume one form is always faster.

[pause=0.7]

PostgreSQL can transform queries during optimization.

[pause=0.7]

Use correct semantics first, then inspect the plan on representative data.

Slide 48: Performance principles

Performance should come after correctness.

[pause=0.7]

A faster query that changes row grain or NULL behavior is not an improvement.

[pause=0.8]

Write the clearest correct query first.

[pause=0.8]

Then inspect the execution plan and consider rewrites or indexes.

[pause=0.7]

Whenever you rewrite a subquery, compare the result sets carefully.

These are the key contracts.

[pause=0.7]

Scalar means one value.

[pause=0.7]

IN means membership.

[pause=0.7]

EXISTS means existence.

[pause=0.7]

ANY and ALL compare one value with a set.

[pause=0.7]

Correlation means the inner query depends on the current outer row.

[pause=0.8]

A derived table means the inner query produces rows for the outer query to use.

[pause=0.8]

If you understand the meaning, you can rebuild the syntax when needed.

Slide 64: Final decision guide

Use this final guide when you are unsure.

[pause=0.7]

Ask what the outer query needs from the inner query.

[pause=0.8]

One value suggests a scalar.

[pause=0.7]

Membership suggests IN.

[pause=0.7]

A related-row question suggests EXISTS or NOT EXISTS.

[pause=0.7]

A comparison against a set suggests ANY or ALL.

[pause=0.7]

Intermediate rows suggest a derived table.

[pause=0.7]

Then ask whether the inner query depends on the current outer row. If yes, it is correlated.
