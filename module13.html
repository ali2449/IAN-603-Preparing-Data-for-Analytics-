Spark habit

Do not stop at “the query is correct.” Ask what is scanned, what is shuffled, and what one output row represents.

Start here

Same SQL ideas, different execution environment

Spark SQL is Apache Spark's structured-data module. It lets you express transformations using SQL while Spark plans and executes the work over distributed data. The relational ideas from earlier modules still matter—filters, joins, aggregates, windows, grain, and NULL semantics—but the cost model now includes files, partitions, network exchange, and parallel tasks.

Learning objectives

By the end of this module, you will be able to:

  • Explain when distributed processing can be useful and when a conventional database may still be the better tool.
  • Describe the roles of the Spark driver, executors, partitions, stages, and tasks at an introductory level.
  • Explain how Spark SQL and DataFrames use the same structured-data execution engine.
  • Distinguish raw file schema inference from explicit schemas and Delta-table schema enforcement.
  • Run Spark SQL in a Microsoft Fabric notebook or Spark SQL query surface and distinguish that workflow from the lakehouse T-SQL analytics endpoint.
  • Use familiar SQL for aggregation, window analysis, and readmission-style temporal analysis in Spark.
  • Use EXPLAIN and a simple scan/filter/shuffle mental model to reason about distributed query cost.
Important: Spark is not “PostgreSQL, but bigger.” Spark is a distributed compute engine that can query many storage systems. A database and Spark often coexist in the same architecture.
Scale decision

Why distribute a workload?

Distributed processing becomes useful when a workload benefits from dividing data and computation across multiple workers—for example, large lake files, broad ETL pipelines, repeated transformations across many partitions, or workloads that exceed the practical CPU, memory, or I/O envelope of one machine. That does not mean every large dataset automatically belongs in Spark.

A database may be the better fit

  • Transactional workloads and frequent small writes
  • Low-latency point lookups
  • Strong relational constraints and operational workflows
  • Data comfortably handled by the database platform

Spark may be a better fit

  • Large file-based lakehouse transformations
  • Wide scans over many partitions
  • Parallel ETL/ELT and feature preparation
  • Batch analytics spanning diverse sources

Partition

A chunk of a distributed dataset that Spark can process as a unit of parallel work.

Task

A unit of work sent to an executor, commonly operating on one partition for a stage.

Stage

A group of tasks that can execute without needing a new cross-partition data exchange.

Shuffle

Redistribution of data across workers, often introduced by grouping, sorting, or certain joins.

Architecture

From SQL text to distributed tasks

At a high level, the driver coordinates a Spark application while executors perform distributed work. Spark SQL adds structured query planning and optimization before the physical work is scheduled.

1. SQL / DataFrameYou express relational intent.
2. Logical planSpark resolves tables, columns, expressions, and relational operators.
3. Optimized planOptimizer rules can simplify and reorganize work.
4. Physical planSpark chooses executable operators and exchanges.

Structured APIs

Spark SQL and DataFrames share the same structured execution engine

Spark SQL is not a separate storage engine. A table or DataFrame provides Spark with schema and relational structure, and you can express the transformation either as SQL or with the DataFrame API. Both feed the same Spark SQL planning/execution machinery.

Spark SQL
SELECT
    state,
    AVG(satisfaction_score) AS avg_score,
    COUNT(*) AS responses
FROM survey_responses_delta
GROUP BY state
ORDER BY avg_score DESC;
PySpark DataFrame
from pyspark.sql import functions as F

df = spark.table("survey_responses_delta")
result = (
    df.groupBy("state")
      .agg(
          F.avg("satisfaction_score").alias("avg_score"),
          F.count("*").alias("responses")
      )
      .orderBy(F.desc("avg_score"))
)
result.show()
Temporary-view bridge: a DataFrame can be registered with createOrReplaceTempView() and then queried with SQL. This is useful when part of a workflow is easier to express in Python and another part is clearer in SQL.
Storage model

Lakehouse, Delta, and the schema-on-read nuance

The source module contrasts “schema-on-write” databases with “schema-on-read” Spark. That distinction is useful as a first approximation, but production systems are more nuanced. Spark can infer schema from files, you can provide an explicit schema, Parquet carries schema metadata, and Delta tables add schema enforcement/evolution plus transactional metadata.

Infer at read time

Useful for exploration

CSV/JSON ingestion can infer types, but inference can be slow or ambiguous and may vary when source data change.

Explicit schema

Useful for repeatability

Production ingestion often benefits from declaring expected names and types so bad source data fail or can be quarantined deliberately.

Delta table

Managed table contract

Delta extends Parquet storage with transaction metadata and supports schema enforcement/evolution workflows.

Parquet

Self-describing columnar files

Parquet stores schema with the data and supports column-oriented reads that fit analytical scans well.

OneLake / filesCSV, JSON, Parquet, Delta files and folders
Lakehouse tablesDelta tables registered for Spark and other Fabric workloads
Compute enginesSpark notebooks / Spark SQL query explorer for Spark SQL; SQL analytics endpoint for T-SQL over Delta tables
Key distinction: in Fabric, “SQL” can mean different engines. Spark SQL in a notebook/query explorer is not the same dialect or execution path as the lakehouse SQL analytics endpoint, which uses T-SQL.
Microsoft Fabric

Two practical Spark SQL authoring surfaces

Fabric supports Spark development in notebooks and also provides a Spark SQL query experience in the Lakehouse explorer. The SQL itself is Spark SQL; what changes is the authoring surface.

Notebook

Use a SQL cell or the %sql magic in a multi-language notebook. Notebooks are well suited to mixing SQL, PySpark, Markdown, and visual output.

%sql
SELECT
    city,
    state,
    ROUND(AVG(satisfaction_score), 2) AS avg_score,
    COUNT(*) AS num_responses
FROM survey_responses_delta
WHERE state IN ('NC', 'VA', 'SC')
GROUP BY city, state
ORDER BY avg_score DESC;

Spark SQL query explorer

Use Spark SQL directly from the Lakehouse explorer. Do not include notebook magic such as %sql.

SELECT
    city,
    state,
    ROUND(AVG(satisfaction_score), 2) AS avg_score,
    COUNT(*) AS num_responses
FROM survey_responses_delta
WHERE state IN ('NC', 'VA', 'SC')
GROUP BY city, state
ORDER BY avg_score DESC;
Separate surface: the Lakehouse SQL analytics endpoint is designed for T-SQL access to Delta tables. Do not assume every Spark SQL function or Spark-specific statement will run there unchanged.

Data sources

Files become queryable through DataFrames, tables, and temporary views

Spark SQL can work with persistent tables as well as DataFrames loaded from files. A common workflow is to read a file with the DataFrame API, inspect or enforce the schema, register a temporary view, and then continue with SQL.

PySpark · load Parquet
df = spark.read.parquet("Files/survey/")
df.printSchema()
df.createOrReplaceTempView("survey_file")
Spark SQL · query temp view
SELECT
    state,
    COUNT(*) AS responses,
    AVG(satisfaction_score) AS avg_score
FROM survey_file
GROUP BY state;

Pure Spark SQL data-source pattern

CREATE OR REPLACE TEMPORARY VIEW parquet_survey
USING parquet
OPTIONS (path 'path/to/survey.parquet');

SELECT *
FROM parquet_survey
LIMIT 20;
Path portability: the exact path format depends on the Spark environment and attached lakehouse. In Fabric, use the path or table reference supplied by Lakehouse Explorer rather than copying a generic path blindly.
Performance intuition

Scan less, move less, and inspect the plan

Distributed SQL introduces a cost that is easy to overlook: moving data between workers. Many analytical operators can require a shuffle, especially when rows with the same key must be brought together.

Column pruning

Select only columns you need so columnar formats can avoid unnecessary I/O.

Predicate / partition pruning

Filter early and on useful partition keys so fewer files or row groups need to be read.

Shuffle awareness

GROUP BY, global sort, and many joins can redistribute data across workers.

Join strategy

The physical plan may choose broadcast, sort-merge, or other strategies depending on statistics, size, and runtime features.

Inspect instead of guessing

EXPLAIN FORMATTED
SELECT
    state,
    AVG(satisfaction_score) AS avg_score
FROM survey_responses_delta
WHERE response_date >= DATE '2026-01-01'
GROUP BY state;
Plan-reading question: Where does the scan happen, which filters are pushed close to the scan, where is data exchanged, and what operator produces the final aggregate?
Advanced SQL

Window functions transfer naturally to Spark SQL

One advantage of learning SQL concepts before Spark is that many analytical patterns remain recognizable. The distributed engine changes the physical execution, not the business meaning of a partitioned window.

Running totals after monthly aggregation

WITH monthly_sales AS (
    SELECT
        category,
        DATE_TRUNC('month', sale_date) AS sale_month,
        SUM(sale_amount) AS monthly_sales
    FROM sales_data
    GROUP BY category, DATE_TRUNC('month', sale_date)
)
SELECT
    category,
    sale_month,
    monthly_sales,
    SUM(monthly_sales) OVER (
        PARTITION BY category
        ORDER BY sale_month
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_total
FROM monthly_sales
ORDER BY category, sale_month;

Days between admissions

WITH patient_admissions AS (
    SELECT
        patient_id,
        admit_date,
        LAG(admit_date) OVER (
            PARTITION BY patient_id
            ORDER BY admit_date
        ) AS previous_admit
    FROM patient_admissions
)
SELECT
    patient_id,
    admit_date,
    previous_admit,
    DATEDIFF(admit_date, previous_admit) AS days_between_admissions
FROM patient_admissions
WHERE previous_admit IS NOT NULL;
Transfer from Module 11: PARTITION BY still preserves row-level detail; however, the physical plan may need to repartition and sort distributed data to satisfy the window.
Practice

Mini-project: regional experience analytics in a lakehouse

Assume the lakehouse contains survey responses, clickstream events, sales, admissions, and customer transactions. Build a small analytical workflow that demonstrates both relational correctness and distributed-computing awareness.

  1. Inspect: describe the survey table and identify column types, expected grain, and candidate partition/filter columns.
  2. Profile: count rows by state and identify missing satisfaction scores.
  3. Aggregate: calculate average score and response count by city/state.
  4. Behavior: calculate daily unique visitors from clickstream data.
  5. Window: calculate monthly sales and a running total by category.
  6. Healthcare: use LAG to calculate time between admissions.
  7. Plan: run EXPLAIN FORMATTED on one grouped query and identify scan, filter, exchange, and aggregate operators.
  8. Reflection: identify one part of the workflow where Spark's parallelism helps and one part that could be handled adequately by PostgreSQL.
Do not optimize by folklore. Start with correct grain and semantics, inspect the plan, and then change data layout or query strategy when you have evidence of a real bottleneck.
Closure

Assessment and key takeaways

1

Explain

What is a partition, and why can a shuffle be expensive in a distributed query?

2

Compare

Explain the difference between schema inference on raw files and schema enforcement for a managed Delta table.

3

Code

Write Spark SQL that returns unique visitors per day from clickstream_logs(user_id, event_timestamp).

4

Apply

For customer_transactions(customer_id, transaction_date, amount), identify customers whose total purchases exceed $10,000 in the last six months and summarize spend by month.

Show sample assessment SQL
-- Daily unique visitors
SELECT
    CAST(event_timestamp AS DATE) AS event_date,
    COUNT(DISTINCT user_id) AS unique_visitors
FROM clickstream_logs
GROUP BY CAST(event_timestamp AS DATE)
ORDER BY event_date;

-- High-value customers in the last six months
WITH recent AS (
    SELECT
        customer_id,
        DATE_TRUNC('month', transaction_date) AS transaction_month,
        amount
    FROM customer_transactions
    WHERE transaction_date >= ADD_MONTHS(CURRENT_DATE(), -6)
),
customer_totals AS (
    SELECT customer_id, SUM(amount) AS six_month_total
    FROM recent
    GROUP BY customer_id
    HAVING SUM(amount) > 10000
)
SELECT
    r.customer_id,
    r.transaction_month,
    SUM(r.amount) AS monthly_spend,
    MAX(t.six_month_total) AS six_month_total
FROM recent r
JOIN customer_totals t USING (customer_id)
GROUP BY r.customer_id, r.transaction_month
ORDER BY r.customer_id, r.transaction_month;

Key takeaways

  • Spark SQL preserves familiar relational logic while changing how the work is physically distributed.
  • Driver, executors, partitions, tasks, stages, and shuffles form a practical mental model for distributed execution.
  • Spark SQL and DataFrames share the structured Spark execution engine.
  • “Schema-on-read” is a capability, not a recommendation to avoid explicit data contracts.
  • Fabric provides Spark SQL surfaces as well as a separate T-SQL analytics endpoint; know which engine you are using.
  • Correct SQL is only the first step at scale: inspect scans, exchanges, output grain, and plans.
