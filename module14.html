Sample step 1
Sample walkthrough

Profile before changing anything

Profiling establishes the source grain and creates evidence for later cleaning decisions. Keep raw source tables unchanged while you investigate.

-- Example profiling questions for raw ridership
SELECT
    COUNT(*) AS row_count,
    COUNT(DISTINCT ridership_id) AS distinct_ids,
    COUNT(*) FILTER (WHERE route_id IS NULL) AS missing_route_ids,
    COUNT(*) FILTER (WHERE riders IS NULL) AS missing_rider_counts,
    MIN(riders) AS min_riders,
    MAX(riders) AS max_riders
FROM raw_daily_ridership;

-- Inspect date representations before parsing
SELECT
    service_date_raw,
    COUNT(*) AS occurrences
FROM raw_daily_ridership
GROUP BY service_date_raw
ORDER BY occurrences DESC, service_date_raw;

The exact table and column names in a real project depend on the Canvas project and chosen data. The important pattern is to profile first and document what you find.

Project evidence: Save profiling results or summarize them in your documentation. A cleaning decision is easier to defend when you can show the issue it addresses.
Sample step 2
Sample walkthrough

Clean values without inventing facts

In this sample, the date text can be standardized, the accessibility field can be normalized, and the street list can be separated into one row per route/street relationship. Missing accessibility remains unknown rather than being silently converted to “No.”

Standardize date text into a typed date

SELECT
    ridership_id,
    route_id,
    service_date_raw,
    CASE
        WHEN BTRIM(service_date_raw) ~ '^\d{4}-\d{2}-\d{2}$'
            THEN BTRIM(service_date_raw)::date
        WHEN BTRIM(service_date_raw) ~ '^\d{1,2}/\d{1,2}/\d{4}$'
            THEN TO_DATE(BTRIM(service_date_raw), 'MM/DD/YYYY')
        ELSE NULL
    END AS service_date,
    riders
FROM raw_daily_ridership;

Normalize accessibility while preserving uncertainty

SELECT
    stop_id,
    route_id,
    BTRIM(stop_name) AS stop_name,
    CASE LOWER(BTRIM(wheelchair_accessible_raw))
        WHEN 'yes' THEN TRUE
        WHEN 'no'  THEN FALSE
        ELSE NULL
    END AS wheelchair_accessible,
    CASE
        WHEN wheelchair_accessible_raw IS NULL
          OR BTRIM(wheelchair_accessible_raw) = ''
        THEN 'missing_source_value'
        ELSE 'source_value_present'
    END AS accessibility_status
FROM raw_bus_stops;

Normalize the comma-separated street list

SELECT
    r.route_id,
    BTRIM(street_name) AS street_name
FROM raw_bus_routes AS r
CROSS JOIN LATERAL
    REGEXP_SPLIT_TO_TABLE(r.major_streets, '\s*,\s*') AS street_name;
Notice the principle: cleaning should standardize representation and expose uncertainty. It should not manufacture a value merely to eliminate NULLs.

Integrate at the correct grain

Suppose the desired analytical output is one row per route per service date. Joining ridership directly to individual stops would repeat the same ridership value once for every stop. Aggregate the child table first, then join.

Ridership
route × date
Stops
many rows per route
Pre-aggregate stops
one row per route
Final grain
route × date
WITH stop_summary AS (
    SELECT
        route_id,
        COUNT(*) AS stop_count,
        COUNT(*) FILTER (WHERE wheelchair_accessible IS TRUE) AS accessible_stop_count,
        COUNT(*) FILTER (WHERE wheelchair_accessible IS NULL) AS unknown_accessibility_count
    FROM clean_bus_stops
    GROUP BY route_id
)
SELECT
    r.route_id,
    r.route_name,
    d.service_date,
    d.riders,
    s.stop_count,
    s.accessible_stop_count,
    s.unknown_accessibility_count
FROM clean_daily_ridership AS d
JOIN clean_bus_routes AS r
    ON r.route_id = d.route_id
LEFT JOIN stop_summary AS s
    ON s.route_id = d.route_id
ORDER BY d.service_date, r.route_id;
Grain check: before trusting a joined result, state what one row represents and verify that your joins have not changed that grain unintentionally.
Sample step 4
Sample walkthrough

Validation turns “looks clean” into evidence

Validation should test the properties that matter for the final analytical dataset. It is not a single query; it is a set of assertions about completeness, uniqueness, validity, referential integrity, and expected grain.

Uniqueness

SELECT ridership_id, COUNT(*)
FROM clean_daily_ridership
GROUP BY ridership_id
HAVING COUNT(*) > 1;

Referential integrity

SELECT d.*
FROM clean_daily_ridership AS d
LEFT JOIN clean_bus_routes AS r
  ON r.route_id = d.route_id
WHERE r.route_id IS NULL;

Date parsing

SELECT *
FROM clean_daily_ridership
WHERE service_date IS NULL;

Range validity

SELECT *
FROM clean_daily_ridership
WHERE riders < 0;

Validate the intended final grain

-- If one output row should represent one route on one service date:
SELECT
    route_id,
    service_date,
    COUNT(*) AS rows_at_grain
FROM final_route_daily_dataset
GROUP BY route_id, service_date
HAVING COUNT(*) > 1;

An empty result is evidence that no duplicate route/date combinations were found—not proof that every other quality dimension is correct.

Sample step 5

Document decisions, not just code

A professional preparation workflow makes it possible for another person to understand what changed, why it changed, what was preserved, and how the output was validated.

What the source meant

Describe files, fields, collection context, source grain, known limitations, and assumptions.

What you changed

Explain cleaning rules, type conversions, standardization, deduplication, normalization, joins, and derived fields.

What you refused to guess

Record values that remained unknown, invalid, quarantined, or pending review instead of silently imputing them.

How you validated it

Show checks for counts, keys, ranges, NULLs, categories, duplicates, referential integrity, and final output grain.

Reproducibility test: Could another analyst understand the source → transformation → validation path without asking you what each line of SQL was supposed to accomplish?
Before submission

Final-project readiness checklist

This checklist is intentionally general. If the Canvas assignment or rubric says something different or more specific, Canvas takes precedence.

  • I read the complete Canvas project prompt and rubric.
    I am not relying on the sample project as my assignment specification.
  • I can state the grain of each important source and final table.
    I know what one row represents before and after joins/aggregations.
  • I profiled my source before cleaning it.
    My cleaning choices are tied to observed issues.
  • I preserve raw/source values or can trace back to them.
    I can distinguish source facts from transformed values.
  • I validated the final dataset.
    I checked the quality dimensions relevant to my project, including keys and output grain.
  • My code and explanation agree.
    The report does not claim a transformation or result that the SQL does not actually produce.
  • I reviewed Canvas for required files, naming, due date, and submission instructions.
    I will upload the final materials to the Canvas assignment.
  • I verified the Canvas submission after upload.
    I confirmed that the intended files were successfully submitted.
Final module

Course closure: from SQL syntax to defensible data preparation

The goal of IAN 603 is larger than memorizing SQL commands. Across the course, you have practiced making decisions about structure, grain, data quality, transformations, integration, validation, modularity, and scale.

A useful final mental model

Correct syntax is necessary, but it is only the beginning.

A strong data-preparation workflow is correct, explainable, reproducible, validated, appropriately structured, and suitable for the analytical purpose.
