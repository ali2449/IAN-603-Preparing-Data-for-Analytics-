Advanced SQL: CTEs & Window Functions

Build multi-step queries, analyze groups without collapsing rows, and express ranking, sequence, and running calculations directly in PostgreSQL.

Essential question: How can we make sophisticated SQL easier to reason about while preserving the row-level detail needed for analytics?

Advanced-SQL habit

For every window expression, identify its partition, ordering, and frame. For every CTE, identify exactly what one row represents.

Start here

Advanced SQL is mostly about controlling intermediate results and row context

A complex query becomes easier to understand when each stage has a clear purpose and grain. CTEs give names to intermediate result sets. Window functions calculate across related rows while keeping the current row in the output. Used together, they support ranking, sequence analysis, running metrics, top-N problems, and multi-step analytical pipelines.

Learning objectives

By the end of this module, you will be able to:

  • Structure multi-step PostgreSQL queries with one or more Common Table Expressions.
  • Explain when a recursive CTE is appropriate and trace its anchor and recursive terms.
  • Use ROW_NUMBER, RANK, and DENSE_RANK with deterministic ordering.
  • Use LAG and LEAD for sequence and interval analysis.
  • Apply aggregate window functions with explicit PARTITION BY, ORDER BY, and frame clauses.
  • Distinguish GROUP BY from PARTITION BY by their effect on output grain.
  • Combine CTEs and window functions for top-N, percent-of-total, readmission, and trend-analysis workflows.
Core rule: advanced syntax does not excuse unclear grain. At every stage, complete the sentence: “One row represents ___.”
Mental model

A CTE turns a complicated statement into named stages

A Common Table Expression begins with WITH. Think of each CTE as a named intermediate relation that exists for the statement. It can be read by later CTEs or by the final statement.

1. Raw rowspatients + admissions
2. Stageadmission_counts
3. Final resultpatient features
CTEs are a query-organization tool, not a promise of faster execution. PostgreSQL can sometimes fold a non-recursive, side-effect-free CTE into its parent query; multiply referenced CTEs and explicit MATERIALIZED/NOT MATERIALIZED choices can change planning behavior.
Chained CTEs: each stage has a job
WITH admission_counts AS (
    SELECT subject_id, COUNT(*) AS admission_count
    FROM admissions
    GROUP BY subject_id
),
patient_features AS (
    SELECT p.subject_id, p.name, p.age, COALESCE(a.admission_count,0) AS admission_count
    FROM patients AS p
    LEFT JOIN admission_counts AS a USING (subject_id)
)
SELECT *,
       CASE WHEN admission_count >= 2 THEN 'repeat' ELSE 'single_or_none' END AS visit_pattern
FROM patient_features
ORDER BY admission_count DESC, subject_id;

Use a CTE when

  • the same logical stage deserves a name,
  • you want a readable multi-step pipeline,
  • you need recursion,
  • you need to rank first and filter second.

Do not add a CTE just because

  • the query is short already,
  • you assume it automatically caches results,
  • you want to hide an unclear grain,
  • a simple expression would be easier.

Modular queries

CTEs let you name the transformation before you consume it

The first useful CTE pattern is simple staging: filter or derive rows in the CTE, then join, aggregate, or window the named result in the outer query.

Filter first, then aggregate
WITH older_patients AS (
    SELECT subject_id, name, age
    FROM patients
    WHERE age > 50
)
SELECT op.subject_id, op.name, op.age, COUNT(a.hadm_id) AS admission_count
FROM older_patients AS op
LEFT JOIN admissions AS a ON a.subject_id = op.subject_id
GROUP BY op.subject_id, op.name, op.age
ORDER BY op.age DESC;

Multiple CTEs form a dependency chain

Later CTEs can reference earlier ones. That makes a complicated analytical workflow read from top to bottom instead of nesting several anonymous subqueries.

Stage stay length before joining to patients
WITH stay_days AS (
    SELECT hadm_id, subject_id, department,
           EXTRACT(EPOCH FROM (discharge_time - admit_time))/86400.0 AS stay_days
    FROM admissions
    WHERE discharge_time IS NOT NULL
)
SELECT p.name, COUNT(s.hadm_id) AS admissions, ROUND(AVG(s.stay_days),2) AS avg_stay_days
FROM patients AS p
LEFT JOIN stay_days AS s USING (subject_id)
GROUP BY p.subject_id, p.name
ORDER BY admissions DESC, p.subject_id;
Looking ahead: CTE materialization

PostgreSQL can fold some side-effect-free, non-recursive CTEs into the parent query. You can also encounter MATERIALIZED and NOT MATERIALIZED when you need to influence that behavior. Use EXPLAIN to inspect the actual plan rather than treating CTEs as an automatic optimization.

Inspect the plan
EXPLAIN
WITH older_patients AS (
    SELECT * FROM patients WHERE age > 50
)
SELECT * FROM older_patients WHERE subject_id > 1002;
Recursive CTEs

Recursion repeatedly feeds one result back into the next step

A recursive CTE has an anchor term that starts the result and a recursive term that refers to the CTE itself. A common analytics use is traversing organizational, category, referral, or parent-child hierarchies.

Recursive organization traversal
WITH RECURSIVE org AS (
    SELECT employee_id, employee_name, manager_id, 0 AS depth, employee_name::text AS path
    FROM employees
    WHERE manager_id IS NULL
  UNION ALL
    SELECT e.employee_id, e.employee_name, e.manager_id, o.depth + 1,
           o.path || ' > ' || e.employee_name
    FROM employees AS e
    JOIN org AS o ON e.manager_id = o.employee_id
)
SELECT employee_id, employee_name, manager_id, depth, path
FROM org
ORDER BY path;
Safety habit: recursive queries need a relationship that eventually stops producing new rows. Test the anchor, inspect the join condition, and avoid accidental cycles.
Window-function anatomy

The OVER clause defines the rows visible to a calculation

A window function keeps the current row and calculates using a related set of rows. The result depends on four pieces.

Function
AVG(salary)

What is calculated?

Partition
PARTITION BY department

Where does the calculation restart?

Order
ORDER BY salary DESC

What is the sequence?

Frame
ROWS ...

Which nearby rows participate?

Two windows over the same employee rows
SELECT employee_id, employee_name, department, salary,
       AVG(salary) OVER (PARTITION BY department) AS department_avg_salary,
       ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC, employee_id) AS row_num
FROM employees
ORDER BY department, row_num;
Key distinction: the employee rows are still present after calculating the department average. Window functions add context without automatically collapsing the result.

ROW_NUMBER()

Always assigns unique sequence numbers. Add a deterministic tie-breaker when the window's ordering values are not unique.

RANK() vs DENSE_RANK()

Both share ranks for peers. RANK leaves gaps after ties; DENSE_RANK does not.

See the three rankings on the same rows
SELECT employee_name, department, salary,
       ROW_NUMBER() OVER (ORDER BY salary DESC, employee_id) AS row_number,
       RANK() OVER (ORDER BY salary DESC) AS rank,
       DENSE_RANK() OVER (ORDER BY salary DESC) AS dense_rank
FROM employees
ORDER BY salary DESC, employee_id;

Partitions create independent leaderboards

Rank salaries within each department
SELECT employee_name, department, salary,
       RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS salary_rank
FROM employees
ORDER BY department, salary_rank, employee_id;
Sequence analysis

LAG and LEAD connect the current row to neighboring rows

Offset functions are ideal when the question contains words such as previous, next, change, or time between.

Admission 101
Jan 10 → Jan 15
Admission 103
Mar 5 → Mar 12
Admission 105
May 15 → May 20

For each current admission, LAG(discharge_time) can expose the discharge time from the previous admission for the same patient.

Time since the previous discharge
WITH sequenced AS (
    SELECT hadm_id, subject_id, admit_time, discharge_time,
           LAG(discharge_time) OVER (PARTITION BY subject_id ORDER BY admit_time, hadm_id) AS previous_discharge
    FROM admissions
)
SELECT hadm_id, subject_id, admit_time, previous_discharge,
       admit_time - previous_discharge AS time_since_discharge
FROM sequenced
WHERE previous_discharge IS NOT NULL
ORDER BY subject_id, admit_time;

Look forward with LEAD

Time to the next website visit
SELECT user_id, visit_timestamp,
       LEAD(visit_timestamp) OVER (PARTITION BY user_id ORDER BY visit_timestamp, visit_id) AS next_visit,
       LEAD(visit_timestamp) OVER (PARTITION BY user_id ORDER BY visit_timestamp, visit_id) - visit_timestamp AS time_to_next_visit
FROM website_visits
ORDER BY user_id, visit_timestamp;
Ordering is part of the definition. Without an appropriate ORDER BY, “previous” and “next” have no analytical meaning.

For running and moving calculations, write the frame explicitly when its boundaries matter.

Running total by department
WITH daily AS (
    SELECT sale_date, department, SUM(revenue) AS daily_revenue
    FROM sales
    GROUP BY sale_date, department
)
SELECT sale_date, department, daily_revenue,
       SUM(daily_revenue) OVER (
           PARTITION BY department
           ORDER BY sale_date
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_revenue
FROM daily
ORDER BY department, sale_date;
Three-row moving average
WITH daily AS (
    SELECT sale_date, SUM(revenue) AS daily_revenue
    FROM sales
    GROUP BY sale_date
)
SELECT sale_date, daily_revenue,
       ROUND(AVG(daily_revenue) OVER (
           ORDER BY sale_date
           ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
       ),2) AS moving_avg_3_rows
FROM daily
ORDER BY sale_date;

Why explicit frames matter

Functions such as LAST_VALUE can surprise students because the default ordered frame normally ends at the current peer group, not necessarily the final row of the partition.

Default frame vs full-partition LAST_VALUE
SELECT sale_id, sale_date, revenue,
       LAST_VALUE(revenue) OVER (ORDER BY sale_date, sale_id) AS default_frame_last_value,
       LAST_VALUE(revenue) OVER (
           ORDER BY sale_date, sale_id
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS partition_last_value
FROM sales
ORDER BY sale_date, sale_id;
Grain

GROUP BY collapses rows; PARTITION BY does not

GROUP BY

one output row per patient

Admissions are summarized into patient-level rows. Admission-level detail is no longer present in the result.

PARTITION BY

one output row per admission

The patient-level average is repeated beside each admission, so detail and context coexist.

Collapsed patient average
SELECT subject_id,
       ROUND(AVG(EXTRACT(EPOCH FROM (discharge_time-admit_time))/86400.0),2) AS avg_stay_days
FROM admissions
WHERE discharge_time IS NOT NULL
GROUP BY subject_id
ORDER BY subject_id;
Preserved admission detail
SELECT hadm_id, subject_id, admit_time,
       ROUND(EXTRACT(EPOCH FROM (discharge_time-admit_time))/86400.0,2) AS stay_days,
       ROUND(AVG(EXTRACT(EPOCH FROM (discharge_time-admit_time))/86400.0)
             OVER (PARTITION BY subject_id),2) AS patient_avg_stay_days
FROM admissions
WHERE discharge_time IS NOT NULL
ORDER BY subject_id, admit_time;
Count the output rows from both approaches
SELECT 'GROUP BY' AS method, COUNT(*) AS output_rows
FROM (
  SELECT subject_id, AVG(discharge_time-admit_time)
  FROM admissions
  GROUP BY subject_id
) AS g
UNION ALL
SELECT 'PARTITION BY', COUNT(*)
FROM (
  SELECT hadm_id, AVG(discharge_time-admit_time) OVER (PARTITION BY subject_id)
  FROM admissions
) AS w;
Choose by the desired output grain. Do not replace GROUP BY with a window function merely because windows are “advanced.”
Advanced patterns

CTEs and windows become most useful when combined

Percent of total

Use a window aggregate over all returned rows while keeping each fact row.

Top N per group

Rank inside a CTE, then filter the rank in the outer query.

Include ties

Use RANK or DENSE_RANK when equal values should share a position.

Top two rows per department
WITH ranked AS (
    SELECT employee_id, employee_name, department, salary,
           ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC, employee_id) AS rn
    FROM employees
)
SELECT employee_id, employee_name, department, salary, rn
FROM ranked
WHERE rn <= 2
ORDER BY department, rn;

A complete analytical pipeline

This pattern first aggregates product revenue, then ranks products within department, then filters the ranking in the final query. Each stage has a different grain and purpose.

Aggregate → rank → filter
WITH product_totals AS (
    SELECT department, product, SUM(revenue) AS product_revenue
    FROM sales
    GROUP BY department, product
),
ranked AS (
    SELECT department, product, product_revenue,
           DENSE_RANK() OVER (PARTITION BY department ORDER BY product_revenue DESC) AS revenue_rank
    FROM product_totals
)
SELECT department, product, product_revenue, revenue_rank
FROM ranked
WHERE revenue_rank <= 2
ORDER BY department, revenue_rank, product;

Applied project: readmission interval analysis

Use a CTE to sequence admissions, calculate the previous discharge with LAG, derive the interval between encounters, and classify whether the next admission occurred within 30 days.

Readmission interval project
WITH sequenced AS (
    SELECT a.*,
           LAG(discharge_time) OVER (PARTITION BY subject_id ORDER BY admit_time, hadm_id) AS previous_discharge
    FROM admissions AS a
),
intervals AS (
    SELECT hadm_id, subject_id, admit_time, previous_discharge,
           admit_time - previous_discharge AS gap
    FROM sequenced
    WHERE previous_discharge IS NOT NULL
)
SELECT p.name, i.hadm_id, i.admit_time, i.previous_discharge, i.gap,
       CASE WHEN i.gap <= INTERVAL '30 days' THEN 'within_30_days' ELSE 'over_30_days' END AS readmission_flag
FROM intervals AS i
JOIN patients AS p USING (subject_id)
ORDER BY p.name, i.admit_time;

Reflection: Which stage is admission-grain? Which stage exists only to derive an interval? Why is the patient join delayed until the final result?

Portability note: Microsoft Fabric and other SQL engines

CTEs and many window functions are broadly available, but exact data types, date arithmetic, frame defaults, and optimization behavior can differ by engine. Treat the PostgreSQL examples in this module as PostgreSQL syntax and verify dialect-specific behavior before transferring a query elsewhere.

Top-N implementation

Return the two longest stays per department without losing admission-level detail.

Assessment starter: two longest stays per department
-- Task: return the two longest stays for each department.
-- Preserve admission-level detail and break exact ties deterministically.
WITH ranked AS (
    SELECT hadm_id, subject_id, department, admit_time, discharge_time,
           EXTRACT(EPOCH FROM (discharge_time-admit_time))/86400.0 AS stay_days,
           ROW_NUMBER() OVER (
               PARTITION BY department
               ORDER BY (discharge_time-admit_time) DESC, hadm_id
           ) AS rn
    FROM admissions
    WHERE discharge_time IS NOT NULL
)
SELECT *
FROM ranked
WHERE rn <= 2
ORDER BY department, rn;

Key takeaways

  • CTEs name intermediate stages; they do not automatically make queries faster.
  • Window functions preserve detail while adding group or sequence context.
  • ROW_NUMBER, RANK, and DENSE_RANK differ most visibly when ties occur.
  • LAG and LEAD require meaningful ordering.
  • Running and moving calculations depend on the window frame, not only on ORDER BY.
  • Top-N-per-group typically requires a ranking stage followed by an outer filter.
