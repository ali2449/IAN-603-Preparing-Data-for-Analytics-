Subqueries in PostgreSQL

Use one query inside another to answer membership, existence, comparison, and row-specific analytical questions without losing control of semantics.

Essential question: When should a query produce one value, a set of values, or a row-dependent result for another query to use?

Subquery habit

Define the inner result shape → choose the matching operator → check NULL behavior → validate the final grain.

Start here

What this module is really about

A subquery is not just a query inside parentheses. It is a contract between an inner query and an outer query. The outer query must know whether the inner query supplies one scalar value, a set of values, or a result that depends on the current outer row.

Learning objectives

  • Write scalar, set-returning, and correlated subqueries.
  • Use IN, EXISTS, ANY/SOME, and ALL with correct semantics.
  • Explain the NOT IN + NULL trap and use NOT EXISTS when appropriate.
  • Use subqueries in WHERE, SELECT, and FROM.
  • Rewrite selected correlated queries with aggregation or joins.
  • Validate query meaning and inspect plans rather than relying on performance folklore.

Prerequisites

  • SELECT, WHERE, GROUP BY, and aggregate functions
  • Boolean and NULL logic
  • INNER and LEFT joins
  • One-to-many row-grain awareness

Conceptual foundation

Think in result shapes, not parentheses

Before choosing an operator, ask what the inner query returns and what the outer query needs.

Outer questionWhich patients are older than the hospital average?
→
Inner querySELECT AVG(age)
FROM patients

Shape: one row, one column

→
Outer comparisonage > (scalar)

Result: patients above the average

Scalar

One value

Use with ordinary comparison operators such as =, >, or <.

Set

Zero or more values

Use with set-aware operators such as IN, ANY, ALL, or existence tests.

Correlated

Depends on outer row

The inner query references a column from the outer query and is logically evaluated in that row context.

Subquery type 1

Scalar subqueries: one value where an expression is expected

A scalar subquery must return exactly one column and at most one row. One row becomes the scalar value; zero rows become NULL; more than one row is an error.

PostgreSQL
SELECT patient_id, name, age
FROM patients
WHERE age > (SELECT AVG(age) FROM patients)
ORDER BY age DESC;

In WHERE

Compare a row to a single benchmark, such as overall average age.

age > (SELECT AVG(age) ...)

In SELECT

Attach the same scalar benchmark to each outer row.

Important edge cases: Run to see a scalar become NULL, then to see PostgreSQL reject an invalid scalar result.
Set membership

IN and NOT IN: ask whether a value belongs to a set

IN (subquery) compares the left-side value to a one-column subquery result. It is ideal when the question is membership: “Is this patient ID among the patient IDs returned by the inner query?”

PostgreSQL
SELECT patient_id, name, age
FROM patients
WHERE patient_id IN (
  SELECT patient_id
  FROM admissions
  WHERE department = 'Cardiology'
)
ORDER BY patient_id;

A membership test is not the same as a join

IN does not multiply an outer row just because the inner set contains several matching records. A join produces matching row combinations. Compare both outputs directly.

The NOT IN + NULL trap

review_queue

1003NULL

The subquery intentionally returns a NULL in addition to a real patient ID.

What happens?

1001 NOT IN (1003, NULL) cannot be proven TRUE because 1001 <> NULL is UNKNOWN.

UNKNOWN → filtered out by WHERE
PostgreSQL
-- review_queue contains patient 1003 AND a NULL patient_id.
-- Because no comparison is definitively TRUE for many rows, NOT IN becomes UNKNOWN.
SELECT patient_id, name
FROM patients
WHERE patient_id NOT IN (SELECT patient_id FROM review_queue)
ORDER BY patient_id;
Safer anti-match pattern: NOT EXISTS tests whether a matching row exists and does not suffer from the same NULL poisoning pattern.
Existence logic

EXISTS and NOT EXISTS: ask whether a matching row exists

EXISTS cares about row existence, not the values projected by the subquery. A common convention is SELECT 1 because the output columns are irrelevant to the existence test.

PostgreSQL
SELECT p.patient_id, p.name, p.age
FROM patients AS p
WHERE EXISTS (
  SELECT 1
  FROM lab_results AS l
  WHERE l.patient_id = p.patient_id
    AND (l.result_value < l.normal_low OR l.result_value > l.normal_high)
)
ORDER BY p.age DESC;
Outer value / question
patient_id = 1003
→
Inner result
{1003, 1004, 1008}
TRUE

IN is TRUE when the left value equals at least one value returned by the subquery.

Use NOT EXISTS for “find outer rows with no matching inner row.”

PostgreSQL
SELECT p.patient_id, p.name
FROM patients AS p
WHERE NOT EXISTS (
  SELECT 1 FROM prescriptions AS pr
  WHERE pr.patient_id = p.patient_id
)
ORDER BY p.patient_id;
Quantified comparisons

ANY, SOME, and ALL: compare against an entire set

ANY and SOME are synonyms. A comparison such as age > ANY (subquery) is TRUE when at least one comparison is TRUE. age > ALL (subquery) requires every comparison to be TRUE.

PostgreSQL
SELECT p.patient_id, p.name, p.age
FROM patients AS p
WHERE p.age > ANY (
  SELECT p2.age
  FROM patients AS p2
  JOIN admissions AS a ON a.patient_id = p2.patient_id
  WHERE a.department = 'Cardiology'
)
ORDER BY p.age DESC;
PostgreSQL
SELECT p.patient_id, p.name, p.age
FROM patients AS p
WHERE p.age > ALL (
  SELECT p2.age
  FROM patients AS p2
  JOIN admissions AS a ON a.patient_id = p2.patient_id
  WHERE a.department = 'Cardiology'
)
ORDER BY p.age DESC;
Important quantified-comparison edge cases
ExpressionEmpty subqueryInterpretation
x > ANY (empty)FALSENo comparison succeeds.
x > ALL (empty)TRUENo comparison violates the ALL condition.
ANY/ALL with NULLsMay become NULLDepends on whether a decisive TRUE or FALSE exists.
Subquery type 3

Correlated subqueries: let the outer row parameterize the inner query

A correlated subquery references one or more columns from the surrounding query. Conceptually, the current outer-row value becomes an input to the inner query.

Outer rows: lab_results l
203Glucose145
205Cholesterol210
213Hemoglobin10.9
Inner query for current row
SELECT AVG(result_value)
FROM lab_results l2
WHERE l2.test_name = l.test_name

For the highlighted outer row, l.test_name is Glucose. The same inner query is logically parameterized differently for the next outer row.

PostgreSQL
SELECT l.test_id, l.patient_id, l.test_name, l.result_value,
       ROUND((
         SELECT AVG(l2.result_value)
         FROM lab_results AS l2
         WHERE l2.test_name = l.test_name
       ),2) AS test_average
FROM lab_results AS l
WHERE l.result_value > (
  SELECT AVG(l3.result_value)
  FROM lab_results AS l3
  WHERE l3.test_name = l.test_name
)
ORDER BY l.test_name, l.result_value DESC;
Where subqueries can appear

WHERE, SELECT, and FROM answer different kinds of questions

WHERE

Filter with an inner result

Examples: older than average, member of a department cohort, has an abnormal lab.

WHERE age > (SELECT ...)
SELECT

Compute a scalar per output row

Examples: patient admission count or hospital average displayed beside each row.

SELECT ..., (SELECT COUNT(...))
FROM

Treat a subquery as a derived table

Use a subquery to aggregate or reshape before joining to another relation.

LEFT JOIN (SELECT ... GROUP BY ...)
PostgreSQL
SELECT p.patient_id, p.name, COALESCE(ac.admission_count,0) AS admission_count
FROM patients AS p
LEFT JOIN (
  SELECT patient_id, COUNT(*) AS admission_count
  FROM admissions
  GROUP BY patient_id
) AS ac ON ac.patient_id = p.patient_id
ORDER BY admission_count DESC, p.patient_id;
A derived table must have an alias in PostgreSQL when referenced in the surrounding query. This pattern is also a strong bridge to CTEs and modular queries covered later.
Reasoning and performance

Choose semantics first; then inspect the plan

Avoid rules such as “EXISTS is always faster than IN.” PostgreSQL's optimizer can transform logically equivalent forms, and performance depends on data distribution, indexes, statistics, predicates, and the exact query. Start with the construct that states the intended meaning clearly, then verify with EXPLAIN on realistic data.

Correlated expression

Often concise and readable for a value tied to each outer row.

(SELECT COUNT(*) FROM admissions a WHERE a.patient_id=p.patient_id)

Pre-aggregate then join

Often clearer when several precomputed measures must be reused or combined.

LEFT JOIN (SELECT patient_id, COUNT(*) ... GROUP BY patient_id)
PostgreSQL
-- Same goal as a correlated count, expressed with pre-aggregation + join.
SELECT p.patient_id, p.name, COALESCE(a.admission_count,0) AS admission_count
FROM patients AS p
LEFT JOIN (
  SELECT patient_id, COUNT(*) AS admission_count
  FROM admissions
  GROUP BY patient_id
) AS a USING (patient_id)
ORDER BY admission_count DESC, p.patient_id;
Do not benchmark with this tiny teaching dataset. Use the workbench plan only to learn plan structure; real tuning requires representative scale and statistics.
Apply the ideas

Guided practice and health-informatics project

Practice: identify complex patients

Find patients who are above the overall average age, have more than one admission, have at least one abnormal lab, and use more than one distinct medication.

PostgreSQL
SELECT p.patient_id, p.name, p.age
FROM patients AS p
WHERE p.age > (SELECT AVG(age) FROM patients)
  AND (SELECT COUNT(*) FROM admissions AS a WHERE a.patient_id = p.patient_id) > 1
  AND EXISTS (
      SELECT 1 FROM lab_results AS l
      WHERE l.patient_id = p.patient_id
        AND (l.result_value < l.normal_low OR l.result_value > l.normal_high)
  )
  AND (SELECT COUNT(DISTINCT pr.medication)
       FROM prescriptions AS pr
       WHERE pr.patient_id = p.patient_id) > 1
ORDER BY p.age DESC;

Project A: risk-feature table

Build one patient-level feature table from scalar and correlated subqueries, then calculate a simple synthetic teaching score. The score is illustrative, not a clinical model.

PostgreSQL
WITH patient_features AS (
  SELECT p.patient_id, p.name, p.age,
         (SELECT COUNT(*) FROM admissions a WHERE a.patient_id=p.patient_id) AS admissions,
         (SELECT COUNT(*) FROM lab_results l WHERE l.patient_id=p.patient_id AND (l.result_value<l.normal_low OR l.result_value>l.normal_high)) AS abnormal_labs,
         (SELECT COUNT(DISTINCT medication) FROM prescriptions pr WHERE pr.patient_id=p.patient_id) AS medications
  FROM patients p
)
SELECT *,
       (CASE WHEN age >= 65 THEN 3 WHEN age >= 50 THEN 2 ELSE 1 END
        + CASE WHEN admissions >= 2 THEN 2 WHEN admissions = 1 THEN 1 ELSE 0 END
        + LEAST(abnormal_labs,2)
        + LEAST(medications,2)) AS risk_score
FROM patient_features
ORDER BY risk_score DESC, patient_id;

Project B: department dashboard

Summarize patient volume, length of stay, and current open admissions. The correlated subquery supplies a department-specific count.

PostgreSQL
SELECT a.department,
       COUNT(*) AS admissions,
       COUNT(DISTINCT a.patient_id) AS patients,
       ROUND(AVG(a.discharge_date - a.admit_date),1) AS avg_stay_days,
       (SELECT COUNT(*)
        FROM admissions AS x
        WHERE x.department = a.department
          AND x.discharge_date IS NULL) AS current_open_admissions
FROM admissions AS a
GROUP BY a.department
ORDER BY admissions DESC, a.department;
Assessment and closure

Can you choose the right inner-query contract?

Recognition

  1. Which subquery shape is required by age > (...)?
  2. When does NOT IN become dangerous?
  3. What is the semantic difference between IN and EXISTS?
  4. What makes a subquery correlated?

Applied challenge

Return patients whose admission count is above the average admission count among patients with at least one admission. Use a derived table and at least one subquery.

Key takeaways

  • A scalar subquery is an expression contract: one column and at most one row.
  • IN is membership; EXISTS is existence.
  • NOT EXISTS avoids the classic NULL behavior that can make NOT IN unexpectedly filter everything.
  • ANY/SOME requires at least one successful comparison; ALL requires no failed comparison.
  • Correlated subqueries depend on outer-row values and can often be rewritten using aggregation and joins.
  • Correct semantics and row grain come before optimization.
