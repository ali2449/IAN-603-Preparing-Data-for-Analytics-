Slide 1: Start

Welcome to Module 9, Data Cleaning in PostgreSQL.

[pause=0.7]

This module brings together the ideas from earlier modules and turns them into a repeatable cleaning workflow.

[pause=0.7]

We will profile missing and invalid values, standardize representation, validate business rules, identify duplicate groups, quarantine questionable records, preview updates safely, and add constraints when the rules are known.

[pause=0.7]

The most important principle is simple: cleaning should make uncertainty visible, not hide it.

[pause=1.0]

Slide 2: Cleaning is decision making

Cleaning is not a collection of random fixes.

[pause=0.7]

It is a sequence of evidence-based decisions.

[pause=0.7]

First, understand the source problems.

[pause=0.7]

Then apply only rules you can explain.

[pause=0.7]

Keep raw values when provenance matters.

[pause=0.7]

And when the correct value is unknown, do not invent one.

[pause=0.7]

A review flag is often more honest than an automatic replacement.

[pause=1.0]

Slide 3: Core principle

Suppose a product price is negative.

[pause=0.7]

It may be tempting to use ABS and make it positive.

[pause=0.7]

But that silently invents a correction.

[pause=0.7]

The negative value is evidence that something went wrong.

[pause=0.7]

A safer workflow flags the value, preserves the source, and corrects it only when reliable evidence identifies the intended price.

[pause=0.7]

This principle applies to dates, phone numbers, emails, categories, and other fields.

[pause=1.0]

Slide 4: Learning goals

By the end of this module, you should be able to build a cleaning workflow rather than a one-off fix.

[pause=0.7]

You should be able to profile quality problems, normalize representation, validate rules, identify duplicates, and use safer SQL patterns for changes.

[pause=0.7]

You should also be able to explain what your cleaning logic knows and what it does not know.

[pause=1.0]

Slide 5: Six-stage workflow

This six-stage workflow organizes the module.

[pause=0.7]

Profile first.

[pause=0.7]

Preserve the source.

[pause=0.7]

Normalize representation where the rule is known.

[pause=0.7]

Validate values against documented rules.

[pause=0.7]

Resolve duplicates or questionable rows with explicit logic.

[pause=0.7]

Finally, move stable rules closer to data entry through constraints or monitoring.

[pause=0.7]

The order matters because prevention should come after you understand the data and the rules.

[pause=1.0]

Slide 11: NULL is not blank

Missing data can appear in several forms.

[pause=0.7]

NULL is a database null.

[pause=0.7]

Blank text is still a string value.

[pause=0.7]

A sentinel such as all zeros is an ordinary value unless the business rule says it represents missingness.

[pause=0.7]

The word Unknown is also ordinary text unless its meaning is documented.

[pause=0.7]

Do not collapse these states automatically without understanding the source convention.

[pause=1.0]

[pause=0.7]

[pause=0.7]

Slide 13: Normalize blanks to NULL

Sometimes blank strings and NULL represent the same business state.

[pause=0.7]

If that rule is documented, NULLIF can convert a blank-after-trimming string into NULL.

[pause=0.7]

This can make later logic easier because one missing representation is easier to handle than several.

[pause=0.7]

But do this only when blank truly means missing for that field.

Slide 15: Standardization vs correction

Standardization and correction should not be treated as the same operation.

[pause=0.7]

Trimming an email or changing case preserves the intended value.

[pause=0.7]

Mapping tech to Electronics may be appropriate if the business taxonomy explicitly defines that equivalence.

[pause=0.7]

Changing a negative price to a positive price makes a much stronger claim about reality.

[pause=0.7]

That kind of correction needs evidence.

[pause=1.0]

Slide 22: Validation is rule-based

Slide 30: Duplicate detection

Deduplication has two separate problems.

[pause=0.7]

First, detect which rows appear to represent the same entity.

[pause=0.7]

Second, decide which row should survive or how the records should be merged.

[pause=0.7]

Do not jump directly from detection to deletion.

[pause=0.7]

The duplicate key and survivor rule both need to be explicit.

[pause=1.0]

Slide 33: Survivor selection

After detecting duplicates, define a survivor rule.

[pause=0.7]

A row with more useful fields might rank higher.

[pause=0.7]

A more recent record might be preferred when recency is meaningful.

[pause=0.7]

Some systems have a designated authoritative source.

[pause=0.7]

And ties should be broken deterministically.

[pause=0.7]

The important point is that survivor selection is a policy, not an automatic property of SQL.

Slide 36: Detection vs resolution

Duplicate detection and duplicate resolution are different stages.

[pause=0.7]

Detection tries to find plausible candidate groups.

[pause=0.7]

Resolution decides what to do with them.

[pause=0.7]

That could mean choosing a survivor, merging complementary fields, quarantining the group, or sending it for human review.

[pause=0.7]

Separating the stages makes deduplication safer.

[pause=1.0]

Slide 37: Quarantine pattern

[pause=0.7]

Slide 41: Prevent known defects

After you understand the data and reconcile legacy problems, stable rules can move closer to data entry.

[pause=0.7]

NOT NULL protects required values.

[pause=0.7]

CHECK can enforce a pattern or domain.

[pause=0.7]

UNIQUE can protect a field that truly must be unique.

[pause=0.7]

Foreign keys protect relationships.

[pause=0.7]

Constraints prevent known defects from reappearing, but they should reflect real business rules.

Slide 43: When to add constraints

Constraints are powerful, but timing matters.

[pause=0.7]

If you add a strict rule before understanding legacy data, valid historical exceptions may be blocked or the migration may fail.

[pause=0.7]

Profile first.

[pause=0.7]

Resolve existing violations.

[pause=0.7]

Confirm the business rule and its owner.

[pause=0.7]

Then add the constraint and monitor future data.

Slide 44: Safe updates

When a cleaning rule is strong enough to update data, use a controlled workflow.

[pause=0.7]

Preview with SELECT.

[pause=0.7]

Start a transaction.

[pause=0.7]

Run UPDATE with a narrow condition.

[pause=0.8]

Use RETURNING to inspect the changed rows.

[pause=0.8]

Then either commit the change or roll it back.

[pause=0.7]

This makes destructive cleaning much safer.

[pause=1.0]

Slide 46: IS DISTINCT FROM

[pause=0.7]

[pause=0.7]

Slide 47: Do not overwrite uncertainty

Some cleaning shortcuts make a dataset look better while reducing its truthfulness.

[pause=0.7]

A bad date should not become today's date.

[pause=0.7]

A negative price should not become positive without evidence.

[pause=0.7]

A missing phone should remain missing unless a reliable source provides one.

[pause=0.7]

A possible duplicate should not be deleted just because its ID is larger.

[pause=0.7]

Cleaning should preserve uncertainty when the truth is unknown.
