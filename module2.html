Learning Objectives

By the end of this module, you will be able to:

  1. Explain the relational model and distinguish conceptual, logical, and physical design.
  2. Identify entities, attributes, domains, keys, relationships, cardinalities, and optionalities from a scenario.
  3. Select PostgreSQL-oriented data types that match meaning, range, precision, and business rules.
  4. Use primary keys, foreign keys, unique constraints, not-null constraints, defaults, and checks to enforce correctness.
  5. Translate one-to-one, one-to-many, and many-to-many relationships into an ERD and SQL tables.
  6. Normalize a design through first, second, and third normal form and explain when deliberate denormalization may be appropriate.
  7. Create and test a small relational schema with SQL DDL.
  8. Apply naming, documentation, security, versioning, and governance practices to schema design.

The Six-Step Design Workflow

1ScopeDefine the system purpose and boundaries.
2ModelIdentify entities, attributes, and row grain.
3ConnectSpecify relationships, cardinality, and optionality.
4ProtectAdd keys, constraints, and referential actions.
5NormalizeRemove repeating groups and avoid anomalies.
6ValidateTest valid and invalid data against the schema.
Module scope: The examples use PostgreSQL-style SQL so they connect naturally to Module 3. The design ideas, however, apply broadly to relational database systems.

Running Case: A Small Outpatient Clinic

The clinic needs to track patients, providers, appointments, services, and the services delivered during each appointment. The system must prevent duplicate identifiers, orphan records, impossible time ranges, and negative charges.

Entity

Patient

A person receiving care, identified internally and by a unique medical record number.

Entity

Provider

A clinician who conducts appointments and has a unique provider identifier.

Event

Appointment

A scheduled encounter connecting one patient with one provider at a particular time.

Reference

Service

A reusable catalog item such as an office visit, vaccine, test, or procedure.

Junction

Appointment Service

Records which services occurred during an appointment, including quantity and charge.

Rule

Integrity

Every appointment must reference existing patient and provider rows, and every charge must be nonnegative.

  1. What real-world things or events deserve their own tables?
  2. What uniquely identifies each patient, provider, appointment, and service?
  3. Can one appointment contain several services?
  4. What values are mandatory, unique, restricted to a set, or limited to a range?
  5. What should happen to appointment services if their appointment is deleted?

1. Build a Relational Mental Model

Understand the vocabulary and the separation between business meaning and storage implementation.

Database, DBMS, Schema, and Table

Core relational database terms
TermWorking MeaningClinic Example
DatabaseAn organized collection of related data.The clinic's operational data.
DBMSSoftware that stores, protects, retrieves, and manages databases.PostgreSQL.
SchemaThe formal structure and rules of the data; in PostgreSQL, also a namespace within a database.Tables, columns, keys, and constraints for the clinic.
Table / relationA named set of rows sharing the same columns and domains.patient or appointment.

Relation Vocabulary

Relation

Table

A set of rows describing one subject or event type.

Tuple

Row

One instance, such as one patient or one appointment.

Attribute

Column

A property shared by every row, such as birth_date.

Domain

Allowed Values

The type and rules governing a column, such as valid appointment statuses.

Atomic does not mean tiny: A value is atomic when the database treats it as one value for the current design. Do not store lists such as 'S101,S205,S310' in one service column when the items must be searched, constrained, or joined independently.

Logical Design vs. Physical Design

Logical Design

Defines what the data means and how it is related.

  • Tables and columns
  • Primary and foreign keys
  • Constraints and views
  • ER diagrams and business rules

Physical Design

Defines how the DBMS stores and accesses the data.

  • Files, pages, and storage parameters
  • Indexes and partitioning
  • Clustering and tablespaces
  • Hardware and performance configuration

Good logical design should remain meaningful even when the physical implementation changes.

Declarative Querying

SQL is primarily declarative: you describe the result you want, and the database optimizer chooses an execution plan. Schema design therefore defines a stable logical contract that applications and analysts can query without controlling every storage operation.

3. Define Entities, Attributes, and Data Types

Choose columns and technical representations that preserve meaning and support validation.

Entity or Attribute?

A concept usually deserves its own table when it has its own identity, several descriptive facts, repeated use, or relationships to other concepts. A simple property that cannot stand independently is usually an attribute.

Separate Entity

  • service has a code, description, price, and active status.
  • The same service is reused across many appointments.
  • Its price or description may change independently.

Simple Attribute

  • birth_date describes a patient.
  • starts_at describes an appointment.
  • quantity describes an appointment-service line.

4. Design Keys and Identity

Give every important row a stable identity and preserve meaningful real-world identifiers.

A Key Is a Minimal Identifier

A key is one column or a minimal combination of columns whose values uniquely identify a row. The design process may reveal several possible identifiers, but one is selected as the primary key.

Types of relational keys
Key ConceptMeaningClinic Example
SuperkeyAny set of attributes that uniquely identifies a row, even if it contains unnecessary columns.{patient_id, mrn}
Candidate keyA minimal superkey; no included column is unnecessary.patient_id or mrn
Primary keyThe candidate key chosen as the official row identifier.patient_id
Alternate keyA candidate key not selected as primary, usually protected by UNIQUE.mrn
Natural keyAn identifier with meaning outside the database.MRN, NPI, service code
Surrogate keyA system-generated identifier with no business meaning.appointment_id
Composite keyA key made from two or more columns.(appointment_id, service_id)
Foreign keyColumn or columns whose values must match a key in a parent table.appointment.patient_id

Surrogate Key Plus Natural-Key Constraint

A common operational pattern uses a stable generated primary key while preserving a meaningful business identifier with a unique constraint.

CREATE TABLE patient (
  patient_id bigint GENERATED ALWAYS AS IDENTITY,
  mrn        text NOT NULL,
  first_name text NOT NULL,
  last_name  text NOT NULL,

  CONSTRAINT pk_patient PRIMARY KEY (patient_id),
  CONSTRAINT uq_patient_mrn UNIQUE (mrn)
);

An identity column generates values; the primary-key constraint enforces identity and uniqueness.

PRIMARY KEY vs. UNIQUE in PostgreSQL

Comparison of primary key and unique constraints
PropertyPRIMARY KEYUNIQUE
RoleOfficial identifier for rowsProtects additional candidate keys or business rules
NULL valuesNot allowedMultiple NULL values are allowed by default in PostgreSQL because NULLs are treated as distinct
Number per tableAt most one primary-key constraint; it may contain several columnsSeveral unique constraints are allowed
Index supportAutomatically backed by a unique indexAutomatically backed by a unique index
Typical examplepatient_idmrn, npi, service_code
Nullable uniqueness: In PostgreSQL 15 and later, when NULL values must be treated as equal for a uniqueness rule, use UNIQUE NULLS NOT DISTINCT. Do not assume every database system handles NULLs in unique constraints the same way.

Composite Key for a Junction Table

CREATE TABLE appointment_service (
  appointment_id bigint NOT NULL,
  service_id     bigint NOT NULL,
  quantity       smallint NOT NULL DEFAULT 1,
  unit_charge    numeric(10,2) NOT NULL,

  CONSTRAINT pk_appointment_service
    PRIMARY KEY (appointment_id, service_id)
);

This key says that the same service appears at most once per appointment. If repeated lines must be preserved separately, add a line number and include it in the key.

Key Selection Checklist

  • Unique for every row
  • Never NULL
  • Stable over the row's lifetime
  • As small and simple as practical
  • Free of sensitive meaning when used widely as a technical identifier
  • Supported by unique constraints on important natural identifiers

5. Model Relationships and ERDs

Express how entity instances connect, how many connections are allowed, and whether participation is required.

Cardinality and Optionality

Cardinality describes the maximum number of related rows. Optionality describes the minimum: zero means optional, while one means required.

Translate Relationship Rules into Columns

Relationship rules translated to schema decisions
Business RuleRelational Decision
Every appointment belongs to exactly one patient.appointment.patient_id is a non-null foreign key.
A patient may have no appointments yet.No row is required in appointment for a patient.

Foreign-key placement rule: In a one-to-many relationship, place the foreign key in the table on the many side. For a many-to-many relationship, introduce a junction table rather than storing a list in either parent table.

6. Encode Integrity Constraints and Referential Actions

Turn important business rules into database-enforced guardrails.

Constraints Are Executable Rules

Application validation improves the user experience, but database constraints protect the data regardless of which application, script, import process, or user sends a statement.

NOT NULL

Requires a value when missing information is not allowed.

mrn text NOT NULL

DEFAULT

Supplies a value when an insert omits the column; it does not validate explicit values.

status text DEFAULT 'scheduled'

UNIQUE

Prevents duplicate candidate-key or business-rule values.

UNIQUE (npi)

CHECK

Restricts a value or a combination of values to a valid condition.

CHECK (unit_charge >= 0)

PRIMARY KEY

Provides the official non-null unique identity for each row.

PRIMARY KEY (appointment_id)

FOREIGN KEY

Requires a child reference to match an existing parent key.

REFERENCES patient(patient_id)

Constraints and Data Quality

Constraints mapped to data quality dimensions
ConstraintQuality Dimension SupportedExample
NOT NULLCompletenessAn appointment cannot omit its patient.
UNIQUEUniquenessNo duplicate MRN or NPI.
CHECKValidityQuantity must be positive and end time must follow start time.
FOREIGN KEYConsistency and referential integrityEvery service line points to an existing service.
PRIMARY KEYIdentity and uniquenessEvery appointment has one stable identifier.

Cross-Column Checks

CREATE TABLE appointment (
  appointment_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  starts_at      timestamptz NOT NULL,
  ends_at        timestamptz NOT NULL,
  status         text NOT NULL DEFAULT 'scheduled',

  CONSTRAINT chk_appointment_time
    CHECK (ends_at > starts_at),
  CONSTRAINT chk_appointment_status
    CHECK (status IN ('scheduled', 'completed', 'cancelled', 'no_show'))
);

Choose Referential Actions Deliberately

Foreign key referential actions
ActionMeaningAppropriate Use
NO ACTION / RESTRICTReject a parent deletion when child rows still depend on it.Protect patient, provider, and service master data referenced by appointments.
CASCADEApply the parent deletion or key update to dependent child rows.Remove appointment-service lines when their appointment is deleted.
SET NULLKeep the child row but remove the reference.Only when the relationship is optional and the foreign-key column permits NULL.
SET DEFAULTReplace the reference with its default value.Rare; the default must still reference a valid parent key.
Do not choose CASCADE merely for convenience. It is appropriate when a child row has no meaning without its parent. For important historical or master data, restriction, soft deletion, or archival may be safer.

Constraint and Index Interaction

  • PostgreSQL automatically creates unique indexes for primary-key and unique constraints.
  • A foreign key does not automatically create an index on the referencing child columns.
  • Indexing a foreign key is often useful for joins and parent updates or deletes, but the decision should follow actual query and workload patterns.
  • Every index consumes storage and adds write overhead, so use targeted indexes rather than indexing every column.

7. Normalize the Design through Third Normal Form

Reduce redundancy and prevent update, insertion, and deletion anomalies.

Why Normalize?

Update anomaly

A provider specialty appears in hundreds of appointment rows, and only some copies are corrected.

Insertion anomaly

A new service cannot be added to the catalog until a fake appointment exists.

Deletion anomaly

Deleting a patient's only appointment accidentally removes the only copy of the patient's contact information.

Unnormalized Starting Point

Suppose one appointment row stores parallel lists of service codes, names, and charges.

Unnormalized clinic appointment row
appointment_idpatientproviderstarts_atservice_codescharges
A5001P1001 | Ana Rivera1234567890 | J. Chen | Family Medicine2026-08-18 09:00S101, L22095.00, 28.00
Lists in cells make it difficult to enforce one code per service, join to a service catalog, or guarantee that the first charge belongs to the first code.

First Normal Form: One Value per Field, No Repeating Groups

Convert each service occurrence into a separate row. The resulting table has a possible composite key of (appointment_id, service_code).

First normal form appointment service rows
appointment_idpatient_mrnpatient_nameprovider_npiprovider_nameservice_codeservice_namecharge
A5001P1001Ana Rivera1234567890J. ChenS101Office Visit95.00
A5001P1001Ana Rivera1234567890J. ChenL220CBC28.00

The values are atomic, but patient, provider, appointment, and service facts are repeated.

Second Normal Form: Depend on the Whole Composite Key

Second normal form matters when a table has a composite candidate key. Remove attributes that depend on only part of (appointment_id, service_code).

appointment_id → appointment facts service_code → service facts appointment_id + service_code → line facts
  • appointment_2nf(appointment_id, starts_at, patient_mrn, patient_name, provider_npi, provider_name, provider_specialty)
  • service(service_code, service_name, standard_price)
  • appointment_service(appointment_id, service_code, quantity, unit_charge)

Third Normal Form: Remove Transitive Dependencies

In appointment_2nf, patient and provider descriptions depend on identifiers that are not the primary key. Move those facts into their own entity tables.

patient_mrn → patient_name provider_npi → provider_name, specialty
  • patient(patient_id, mrn, first_name, last_name, birth_date)
  • provider(provider_id, npi, provider_name, specialty)
  • appointment(appointment_id, patient_id, provider_id, starts_at, ends_at, status)
  • service(service_id, service_code, service_name, standard_price)
  • appointment_service(appointment_id, service_id, quantity, unit_charge)

Normal-Form Decision Guide

Summary of first, second, and third normal form
Normal FormQuestionTypical ViolationRepair
1NFDoes each field hold one value, with no repeating column groups?Comma-separated service codes or service_1, service_2Create one row per occurrence or a related child table.
2NFDoes every non-key attribute depend on the whole composite key?Service name depends only on service_codeMove partial dependencies to separate tables.
3NFDoes every non-key attribute depend directly on the key rather than another non-key attribute?Provider specialty depends on provider_npi, not directly on appointment IDCreate the provider entity and reference it by key.
Memory aid: A 3NF table describes one subject at one grain, and its non-key attributes depend on the key, the whole key, and nothing but the key.

  • BCNF: Every determinant in a nontrivial functional dependency must be a superkey. It strengthens 3NF in designs with overlapping candidate keys.
  • 4NF: Separates independent multivalued facts that would otherwise create unnecessary combinations.
  • 5NF: Addresses rare join dependencies that cannot be solved by lower normal forms without losing information.

For most introductory OLTP designs, a well-reasoned 3NF design is an appropriate target. Use higher normal forms when the dependency structure demands them.

When to Denormalize

Denormalization may improve specific read-heavy analytics or reporting workloads, but it deliberately reintroduces redundancy. Use documented refresh rules, lineage, tests, and ownership so duplicated facts do not drift apart.

8. Guided SQL DDL Lab

Implement the clinic schema, load a small dataset, and prove that the guardrails work.

Lab goal: Build a five-table PostgreSQL schema in dependency order, then test both valid and invalid statements. Module 3 will expand the execution workflow and PostgreSQL tooling.

Part A: Create the Tables

Run the script from top to bottom. Parent tables are created before child tables so every referenced key already exists.

-- Optional reset for repeated practice
DROP TABLE IF EXISTS appointment_service, appointment,
                     service, provider, patient CASCADE;

CREATE TABLE patient (
  patient_id bigint GENERATED ALWAYS AS IDENTITY,
  mrn        text NOT NULL,
  first_name text NOT NULL,
  last_name  text NOT NULL,
  birth_date date NOT NULL,
  email      text,
  created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,

  CONSTRAINT pk_patient PRIMARY KEY (patient_id),
  CONSTRAINT uq_patient_mrn UNIQUE (mrn),
  CONSTRAINT uq_patient_email UNIQUE (email),
  CONSTRAINT chk_patient_mrn_not_blank CHECK (btrim(mrn) <> '')
);

CREATE TABLE provider (
  provider_id   bigint GENERATED ALWAYS AS IDENTITY,
  npi           text NOT NULL,
  provider_name text NOT NULL,
  specialty     text,
  is_active     boolean NOT NULL DEFAULT TRUE,

  CONSTRAINT pk_provider PRIMARY KEY (provider_id),
  CONSTRAINT uq_provider_npi UNIQUE (npi),
  CONSTRAINT chk_provider_npi CHECK (npi ~ '^[0-9]{10}$')
);

CREATE TABLE service (
  service_id     bigint GENERATED ALWAYS AS IDENTITY,
  service_code   text NOT NULL,
  service_name   text NOT NULL,
  standard_price numeric(10,2) NOT NULL,
  is_active      boolean NOT NULL DEFAULT TRUE,

  CONSTRAINT pk_service PRIMARY KEY (service_id),
  CONSTRAINT uq_service_code UNIQUE (service_code),
  CONSTRAINT chk_service_price CHECK (standard_price >= 0)
);

CREATE TABLE appointment (
  appointment_id bigint GENERATED ALWAYS AS IDENTITY,
  patient_id     bigint NOT NULL,
  provider_id    bigint NOT NULL,
  starts_at      timestamptz NOT NULL,
  ends_at        timestamptz NOT NULL,
  status         text NOT NULL DEFAULT 'scheduled',
  reason         text,
  created_at     timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,

  CONSTRAINT pk_appointment PRIMARY KEY (appointment_id),
  CONSTRAINT fk_appointment_patient
    FOREIGN KEY (patient_id)
    REFERENCES patient (patient_id)
    ON DELETE RESTRICT,
  CONSTRAINT fk_appointment_provider
    FOREIGN KEY (provider_id)
    REFERENCES provider (provider_id)
    ON DELETE RESTRICT,
  CONSTRAINT chk_appointment_time
    CHECK (ends_at > starts_at),
  CONSTRAINT chk_appointment_status
    CHECK (status IN ('scheduled', 'completed', 'cancelled', 'no_show'))
);

CREATE TABLE appointment_service (
  appointment_id bigint NOT NULL,
  service_id     bigint NOT NULL,
  quantity       smallint NOT NULL DEFAULT 1,
  unit_charge    numeric(10,2) NOT NULL,

  CONSTRAINT pk_appointment_service
    PRIMARY KEY (appointment_id, service_id),
  CONSTRAINT fk_appt_service_appointment
    FOREIGN KEY (appointment_id)
    REFERENCES appointment (appointment_id)
    ON DELETE CASCADE,
  CONSTRAINT fk_appt_service_service
    FOREIGN KEY (service_id)
    REFERENCES service (service_id)
    ON DELETE RESTRICT,
  CONSTRAINT chk_appt_service_quantity CHECK (quantity > 0),
  CONSTRAINT chk_appt_service_charge CHECK (unit_charge >= 0)
);

-- PostgreSQL does not automatically index the child side of a foreign key.
CREATE INDEX idx_appointment_patient_time
  ON appointment (patient_id, starts_at);

CREATE INDEX idx_appointment_provider_time
  ON appointment (provider_id, starts_at);

FROM appointment AS a
JOIN patient AS p
  ON p.patient_id = a.patient_id
JOIN provider AS pr
  ON pr.provider_id = a.provider_id
LEFT JOIN appointment_service AS aps
  ON aps.appointment_id = a.appointment_id
LEFT JOIN service AS s
  ON s.service_id = aps.service_id
ORDER BY a.starts_at, s.service_code;

Lab Reflection

  1. Which rules are enforced by data types, and which require constraints?
  2. Why is the natural key still unique when a surrogate primary key exists?
  3. Why does appointment_service use ON DELETE CASCADE while appointment-to-patient uses ON DELETE RESTRICT?
  4. Which query patterns justify the two explicit indexes?
  5. What additional rule would be needed to prevent overlapping appointments for the same provider?

Preserve a reliable operational core while planning controlled analytical and historical views.

Advanced material is a preview, not the core learning target.

The source module includes clinical code systems, temporal history, slowly changing dimensions, star schemas, and materialized views. They are retained below as optional extensions so the foundational design sequence remains clear.

Clinical vocabularies such as ICD-10 and LOINC should live in authoritative reference tables. Operational facts store codes and foreign keys rather than duplicating labels as uncontrolled free text.

CREATE TABLE ref_icd10 (
  icd10_code text PRIMARY KEY,
  long_title text NOT NULL
);

CREATE TABLE appointment_diagnosis (
  appointment_id bigint NOT NULL
    REFERENCES appointment (appointment_id)
    ON DELETE CASCADE,
  icd10_code text NOT NULL
    REFERENCES ref_icd10 (icd10_code),
  diagnosis_rank smallint NOT NULL
    CHECK (diagnosis_rank BETWEEN 1 AND 30),
  PRIMARY KEY (appointment_id, icd10_code)
);

When analysts need the value that was valid at a past time, store effective windows and keep prior versions. A partial unique index can enforce at most one current row per entity while allowing many historical rows.

CREATE TABLE patient_address_history (
  address_version_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  patient_id         bigint NOT NULL
    REFERENCES patient (patient_id),
  street_line        text NOT NULL,
  city               text NOT NULL,
  state_code         text NOT NULL,
  postal_code        text NOT NULL,
  valid_from         timestamptz NOT NULL,
  valid_to           timestamptz,
  is_current         boolean NOT NULL DEFAULT TRUE,
  CHECK (valid_to IS NULL OR valid_to > valid_from)
);

CREATE UNIQUE INDEX uq_patient_one_current_address
  ON patient_address_history (patient_id)
  WHERE is_current;

  • Fact table: Stores events or measurements at a declared grain, such as one row per appointment-service line.
  • Dimension table: Describes who, what, when, where, or why.
  • Star schema: The fact table connects directly to dimensions, simplifying analytical joins.
  • Snowflake schema: Some dimensions are normalized into related sub-dimensions, reducing redundancy but adding joins.

A dimensional model complements rather than replaces the normalized operational source. Build it through documented transformations and maintain lineage to the source tables.

A materialized view stores query results and must be refreshed according to a documented schedule. It can make repeated reporting faster, but the result is only as current as its last refresh.

CREATE MATERIALIZED VIEW mv_appointment_monthly AS
SELECT
  date_trunc('month', a.starts_at) AS month_start,
  count(*) AS appointments
FROM appointment AS a
GROUP BY 1;

-- Refresh according to the documented reporting schedule.
REFRESH MATERIALIZED VIEW mv_appointment_monthly;

Governance and Documentation Checklist

Naming and Documentation

  • Use one consistent naming convention.
  • Name important constraints so errors are understandable.
  • Maintain an ERD and data dictionary.
  • Document table grain, source, owner, and refresh behavior.
  • Add table and column comments where useful.

Change Management

  • Version schema changes with migrations.
  • Review changes before production deployment.
  • Test upgrades and rollback procedures.
  • Keep a changelog and ownership record.
  • Validate downstream reports after schema changes.

Security and Privacy

  • Apply least privilege to roles and service accounts.
  • Separate sensitive identifiers from broad analytical access.
  • Audit access to protected or personally identifiable data.
  • De-identify exports when direct identifiers are unnecessary.
  • Encrypt data in transit and follow institutional requirements for data at rest.

Reliability and Quality

  • Define backup, restore, retention, and recovery procedures.
  • Monitor null rates, duplicates, ranges, and foreign-key coverage.
  • Record lineage from source to analytical output.
  • Use targeted indexes and inspect real query plans.
  • Assign owners for quality failures and remediation.

10. Assessment and Closure

Move from recognition to diagnosis, design, implementation, and explanation.

Checkpoint 1: Recognize the Design Element

  1. A clinic-assigned number such as MRN-1001 identifies a patient in the business. Is it a natural key, surrogate key, or foreign key?
  2. A generated patient_id has no meaning outside the database. What kind of key is it?
  3. One provider may conduct many appointments, while each appointment has one provider. What is the cardinality?
  4. An appointment can include many services, and each service can appear in many appointments. What structure resolves the relationship?
  5. Which constraint prevents an appointment from referencing a nonexistent patient?
  6. Which constraint is best for the rule unit_charge >= 0?

  1. Natural key; if not selected as primary, it is also an alternate candidate key protected with UNIQUE.
  2. Surrogate key.
  3. One-to-many from provider to appointment.
  4. A junction table such as appointment_service.
  5. A foreign-key constraint.
  6. A check constraint.

Checkpoint 2: Diagnose a Weak Design

Review the following table definition:

CREATE TABLE clinic_log (
  id             text,
  patient_name   text,
  patient_phone  text,
  provider_name  text,
  services_csv   text,
  appointment_at text,
  total_charge   text
);

Identify at least six design problems and propose a relational repair.

  • No primary key or uniqueness rule.
  • Patient and provider identities are represented only by changeable names.
  • Patient details will repeat across appointments, creating anomalies.
  • services_csv violates 1NF and cannot enforce service references.
  • Date/time is stored as text instead of a temporal type.
  • Charge is stored as text instead of an exact numeric type.
  • No foreign keys, not-null rules, domain checks, or status rules exist.
  • Several subjects are mixed at an unclear row grain.

Repair the design with patient, provider, appointment, service, and appointment_service tables, then add appropriate keys, types, and constraints.

Prompt: A bookstore app tracks customers, books, authors, orders, and the books purchased in each order. List entities and attributes with proposed types, choose keys, and identify relationship cardinalities.

  • author(author_id PK, author_name, country)
  • book(book_id PK, isbn UNIQUE, title, published_year, list_price)
  • book_author(book_id FK, author_id FK, PRIMARY KEY(book_id, author_id))
  • orders(order_id PK, customer_id FK, ordered_at, status)
  • order_item(order_id FK, book_id FK, quantity, unit_price, PRIMARY KEY(order_id, book_id))

Exercise 2: Write Constraints from Rules

Write table-level or column-level constraints for each rule:

  1. Every customer email must be present and unique.
  2. Order-item quantity must be a positive whole number.
  3. Unit price must be nonnegative.
  4. Every order item must reference an existing order and book.
  5. Deleting an order should remove its order items, but deleting a book that appears in historical orders should be rejected.
  6. Order status must be one of pending, paid, shipped, cancelled, or refunded.

email text NOT NULL UNIQUE,
quantity integer NOT NULL CHECK (quantity > 0),
unit_price numeric(10,2) NOT NULL CHECK (unit_price >= 0),
status text NOT NULL CHECK (
  status IN ('pending', 'paid', 'shipped', 'cancelled', 'refunded')
),
FOREIGN KEY (order_id)
  REFERENCES orders (order_id)
  ON DELETE CASCADE,
FOREIGN KEY (book_id)
  REFERENCES book (book_id)
  ON DELETE RESTRICT

Common Pitfalls

Common database design mistakes and better practices
PitfallWhy It FailsBetter Practice
No foreign keysOrphan rows and inconsistent references become possible.Enforce relationships in the database.
Everything as textDates, numbers, and booleans lose type validation and useful operations.Choose types that match meaning.
Arbitrary varchar(255)The number may express no real business rule.Use text or a meaningful validated maximum.
Business ID as the only keyNatural identifiers may change or be awkward to propagate.Consider a surrogate primary key plus a unique natural key.
Lists in one columnViolates 1NF and blocks independent validation and joins.Create child or junction rows.
Cascade everywhereA single delete can remove important history unexpectedly.Choose delete actions from dependency meaning.
Indexes everywhereIndexes consume storage and slow writes.Index for demonstrated query and integrity workloads.
One giant mixed tableUnclear grain and repeated facts create anomalies.Model one subject at one grain and normalize.
No schema documentationRules become tribal knowledge and changes become risky.Maintain ERDs, dictionaries, migrations, owners, and lineage.

Key Takeaways

1. Begin with business meaning, scope, and row grain before writing SQL.
2. Stable keys and explicit relationships make reliable joins and integrity possible.
3. Constraints turn important rules into protections that apply to every data path.
4. Normalization reduces redundancy and prevents update, insertion, and deletion anomalies.
5. Denormalization, indexing, history, and analytics structures should be intentional, documented responses to specific requirements.
