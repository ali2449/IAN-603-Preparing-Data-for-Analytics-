Module 2: An Expert's Guide to Relational Database Design

A Comprehensive Teaching Module (Lecture, Lab, and Assessment Ready)

Introduction

This module is designed for students with little to no prior database experience, as well as practitioners who need a rigorous "mental model" for designing OLTP (Online Transaction Processing) systems. It provides a foundational understanding of the relational model, from core components to advanced design principles. A solid grasp of these concepts is essential for anyone working with structured data, enabling efficient querying and robust data management.

In practice, consider a hospital system in Greensboro, NC, managing patient records, appointments, and billing. A poorly designed database could lead to errors like duplicate patient entries or mismatched billing records, while a well-structured database ensures accurate and efficient data retrieval for healthcare analytics.

Learning Outcomes

By the end of this module, students will be able to:

  • Explain the relational model and the separation of logical vs. physical design.
  • Identify entities, attributes, keys, and relationships, choosing data types appropriately.
  • Enforce correctness with integrity constraints (NOT NULL, UNIQUE, CHECK, PRIMARY KEY, FOREIGN KEY).
  • Model relationships using ERDs and implement them with SQL DDL.
  • Normalize tables to 1NF → 2NF → 3NF and reason about denormalization tradeoffs.
  • Apply naming, documentation, and governance best practices.

1) Foundational Components of Relational Databases

1.1 Defining the Relational Model

The core idea of the relational model is that data is represented as relations, which we call tables. Each table has a name and is composed of rows and columns.

  • Tuple (row): Represents one record or entity instance.
  • Attribute (column): A property shared by all rows in a table.
  • Key: A minimal set of attributes that uniquely identifies a row.
  • Relational algebra: A set of operations that define how data is manipulated. Declarative querying (e.g., SQL) focuses on what you want, not how to get it.

A key architectural principle is the separation of logical vs. physical design. The logical layer defines the tables, views, columns, constraints, and ER diagrams. The physical layer deals with files, pages, indexes, and storage configuration. This separation allows you to evolve physical storage (e.g., move files, rebuild indexes) without changing the logical contracts used by your applications.

1.2 Tables, Columns, and Rows

For a cohesive design, you should use one table per distinct entity (e.g., Customer, Order, Product). Rows are instances of that entity (e.g., Customer #123), and columns are the attributes that describe them (e.g., FirstName, Email). It's crucial to keep columns atomic, meaning no lists or comma-separated values inside a single cell.

Here's a quick contrast:

Comparator Rows Columns
Description A single record/entity A property common to all records
Orientation Horizontal (left→right) Vertical (top→bottom)
Database name Record / Tuple Attribute / Field

1.3 Data Types

Choosing the right data type is a fundamental step that ensures data integrity and storage efficiency. You should choose types that fit both the domain and any constraints. Common data types include:

  • Integer/Bigint: For IDs and counters.
  • Decimal(N, d): For exact numeric types like currency.
  • Varchar(n): For bounded text strings.
  • Text: For long-form text.
  • Date/Time/Timestamp: For storing temporal data.
  • Boolean: For true/false values.
  • UUID: A universally unique identifier.

A good rule of thumb is to prefer exact numeric types for currency (DECIMAL), bound string lengths where appropriate, and use CHECK constraints for domain rules (e.g., 0 ≤ Discount ≤ 1).

1.4 A Record in Practice

Consider a simple two-table example for an e-commerce store:

customers(customer_id PK, first_name, last_name, email, …)
orders(order_id PK, customer_id FK→customers.customer_id, product_id, qty, size, order_date, …)

To retrieve a buyer's details for a specific order, you would use a JOIN on the customer_id column, linking the orders table to the customers table.

2) Integrity Constraints: Guardrails for Correctness

2.1 Why constraints matter

Constraints encode business rules directly into the database, preventing bad data at the source. This is far more robust than relying solely on application code, which can have bugs or be circumvented.

2.2 NOT NULL — Completeness

The NOT NULL constraint prevents missing values where a value is mandatory. If you try to insert a row without a value for a NOT NULL column, the database will throw an error, protecting the integrity of your data.

CREATE TABLE users (
  user_id      BIGSERIAL PRIMARY KEY,
  email        VARCHAR(255) NOT NULL,
  password_hash TEXT        NOT NULL
);

In this example, both email and password_hash must have a value for every row.

2.3 UNIQUE — No Duplicates

The UNIQUE constraint ensures all values in a column or set of columns are distinct. It's used when a column must be unique but isn't the primary key. Unlike a PRIMARY KEY, a UNIQUE constraint typically allows a single NULL value.

ALTER TABLE users ADD CONSTRAINT uq_users_email UNIQUE (email);

You can also create composite uniqueness, such as UNIQUE (col1, col2). Most RDBMSs automatically create a unique index to enforce this constraint efficiently.

2.4 CHECK — Domain & Business Rules

The CHECK constraint validates that values meet a specified condition, such as being within a certain range or matching a pattern. This is an excellent way to encode business rules directly into your schema.

CREATE TABLE employees (
  emp_id   BIGSERIAL PRIMARY KEY,
  salary   NUMERIC(12,2) NOT NULL,
  grade    INT           NOT NULL,
  CONSTRAINT chk_salary_min  CHECK (salary >= 20000),
  CONSTRAINT chk_grade_range CHECK (grade BETWEEN 1 AND 10)
);

Advanced CHECK (cross-column): You can also use CHECK for more complex, cross-column logic, like ensuring a state field is only 2 characters long when the country is 'USA'.

ALTER TABLE addresses
ADD CONSTRAINT chk_state_if_usa
CHECK (country <> 'USA' OR char_length(state) = 2);

3) Keys — The Structural Backbone

3.1 PRIMARY KEY — The Official Identifier

A PRIMARY KEY is the one official identifier for a table. It must be UNIQUE and NOT NULL, and there can be exactly one per table. Primary keys are often implemented as a surrogate key, such as an auto-incrementing integer or a UUID, for stability.

CREATE TABLE products (
  product_id BIGSERIAL PRIMARY KEY,
  sku        VARCHAR(32) UNIQUE NOT NULL,
  name       VARCHAR(200) NOT NULL
);

In this example, product_id is the primary key, while the sku (stock keeping unit) is a unique natural key.

3.2 FOREIGN KEY — Referential Integrity

A FOREIGN KEY enforces a link between a "child" row and an existing "parent" row in another table. This is how you model relationships and enforce referential integrity.

CREATE TABLE orders (
  order_id    BIGSERIAL PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  order_date  DATE   NOT NULL,
  CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id)
    REFERENCES customers (customer_id)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
);

You can define ON UPDATE and ON DELETE actions to specify how the database should behave when a referenced row is updated or deleted. Common options include CASCADE (delete/update child rows) and RESTRICT (prevent the delete/update).

3.3 Composite Keys

A composite key is a primary key that consists of two or more columns. This is used when a single column isn't sufficient to uniquely identify a row, often in junction tables that resolve many-to-many relationships.

CREATE TABLE enrollment (
  student_id BIGINT NOT NULL,
  class_id   BIGINT NOT NULL,
  PRIMARY KEY (student_id, class_id),
  FOREIGN KEY (student_id) REFERENCES students(student_id),
  FOREIGN KEY (class_id)   REFERENCES classes(class_id)
);

3.4 PRIMARY KEY vs. UNIQUE

While both enforce uniqueness, they serve different purposes. Here's a crisp comparison:

Parameter Primary Key Unique Constraint
Purpose Sole table identifier Prevent duplicates on other columns
Nullability No NULLs allowed Typically one NULL allowed
Count per table Exactly one Many allowed
Indexing Usually clustered (vendor-specific) Non-clustered (typical)
Examples customer_id email, ssn, sku

5) Normalization — Integrity & Efficiency

5.1 Why Normalize? Anomalies & Data Trust

Normalization organizes data to reduce redundancy and prevent anomalies so downstream analytics are accurate and reproducible:

  • Update anomaly: A single fact (e.g., provider specialty) exists in many rows—one update misses others.
  • Deletion anomaly: Deleting an encounter also deletes the only copy of a patient’s demographic detail.
  • Insertion anomaly: Can’t add a new ICD code without a “placeholder” encounter row.
Informatics focus: In healthcare, normalization ensures codes (ICD-10, LOINC, SNOMED CT, RxNorm) live in authoritative lookup tables, preventing free-text drift and enabling consistent analytics and interoperability.

5.2 The Normal Forms (beyond 3NF)

  • 1NF: Atomic columns, no repeating groups (no CSVs in a cell).
  • 2NF: 1NF + every non-key attribute depends on the whole composite key (no partial dependency).
  • 3NF: 2NF + no transitive dependency (non-key depends only on the key, not on another non-key).
  • BCNF (Boyce–Codd): For every non-trivial functional dependency X→Y, X must be a superkey. Tightens 3NF when overlapping candidate keys exist.
  • 4NF: Removes multi-valued dependencies (e.g., independent sets like {instrument} and {technician}).
  • 5NF: Eliminates join dependencies; rarely needed in OLTP but useful in complex reference domains.

Rule of thumb: Target 3NF/BCNF for OLTP. Use 4NF/5NF selectively for highly combinatorial reference models.

5.4 When to Denormalize (with guardrails)

Denormalize for read-heavy analytics (e.g., pre-aggregates, star schemas). Risks: higher write cost, potential inconsistency. Mitigations: refresh policies, materialized views, data quality checks, and lineage docs.

5.5 Informatics Patterns — Code Systems & Reference Integrity

Normalize external clinical vocabularies and link by code. Store human-readable labels in the reference table, not duplicated in facts.

-- ICD-10 diagnoses reference (authoritative list)
CREATE TABLE ref_icd10 (
  icd10_code   VARCHAR(10) PRIMARY KEY,
  long_title   VARCHAR(400) NOT NULL
);

-- LOINC test catalog
CREATE TABLE ref_loinc (
  loinc_code   VARCHAR(20) PRIMARY KEY,
  component    VARCHAR(200),
  property     VARCHAR(50),
  scale        VARCHAR(50)
);

-- Clinical facts reference these codes (no free text duplication)
CREATE TABLE encounter (
  encounter_id BIGSERIAL PRIMARY KEY,
  patient_id   BIGINT NOT NULL,
  start_time   TIMESTAMP NOT NULL,
  end_time     TIMESTAMP,
  CHECK (end_time IS NULL OR end_time >= start_time)
);

-- Many diagnoses per encounter (N:M)
CREATE TABLE encounter_dx (
  encounter_id BIGINT NOT NULL REFERENCES encounter(encounter_id) ON DELETE CASCADE,
  icd10_code   VARCHAR(10) NOT NULL REFERENCES ref_icd10(icd10_code),
  dx_rank      INT NOT NULL CHECK (dx_rank BETWEEN 1 AND 30),
  PRIMARY KEY (encounter_id, icd10_code)
);

-- Lab results normalized to LOINC
CREATE TABLE lab_result (
  lab_result_id BIGSERIAL PRIMARY KEY,
  encounter_id  BIGINT NOT NULL REFERENCES encounter(encounter_id) ON DELETE CASCADE,
  loinc_code    VARCHAR(20) NOT NULL REFERENCES ref_loinc(loinc_code),
  value_num     NUMERIC(12,4),
  value_text    VARCHAR(200),
  unit          VARCHAR(32),
  collected_at  TIMESTAMP NOT NULL
);

Why it matters: clean joins to ref_icd10 / ref_loinc enable robust cohort building and KPI definition without brittle text matching.

5.6 Temporal Normalization & Auditability

Healthcare and finance require time-aware truth. Keep changes with effective windows; don’t overwrite history.

-- Patient demographics with validity (bi-temporal possible)
CREATE TABLE patient_demographics (
  patient_id   BIGINT NOT NULL,
  version_id   BIGSERIAL,
  mrn          VARCHAR(20) NOT NULL,
  first_name   VARCHAR(100) NOT NULL,
  last_name    VARCHAR(100) NOT NULL,
  birth_date   DATE NOT NULL,
  valid_from   TIMESTAMP NOT NULL DEFAULT NOW(),
  valid_to     TIMESTAMP,
  is_current   BOOLEAN NOT NULL DEFAULT TRUE,
  PRIMARY KEY (patient_id, version_id),
  UNIQUE (patient_id, is_current) DEFERRABLE INITIALLY DEFERRED
);

Pattern: insert new version with is_current=TRUE, set previous row’s valid_to and is_current=FALSE.

5.7 Dimensional Modeling for Analytics — Star & Snowflake

For BI/analytics, model facts (events/measures) and conformed dimensions (who/what/when/where). Choose a clear grain for each fact.

  • Star: fact table links directly to all dimensions (simpler joins).
  • Snowflake: some dimensions normalized into sub-dimensions (less redundancy; more joins).
  • Grain: e.g., one row per encounter; per encounter-diagnosis; per lab observation.
-- Dimensions (with SCD2-friendly keys)
CREATE TABLE dim_patient (
  patient_sk   BIGSERIAL PRIMARY KEY,
  patient_id   BIGINT NOT NULL,                 -- business key
  mrn          VARCHAR(20) NOT NULL,
  birth_date   DATE NOT NULL,
  gender       VARCHAR(16),
  effective_from DATE NOT NULL,
  effective_to   DATE,
  is_current     BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE dim_provider (
  provider_sk BIGSERIAL PRIMARY KEY,
  provider_id BIGINT NOT NULL,                  -- business key
  npi         VARCHAR(20) UNIQUE NOT NULL,
  specialty   VARCHAR(100)
);

CREATE TABLE dim_date (
  date_sk     INTEGER PRIMARY KEY,              -- yyyymmdd
  full_date   DATE NOT NULL,
  year        SMALLINT NOT NULL,
  month       SMALLINT NOT NULL,
  day         SMALLINT NOT NULL,
  week        SMALLINT NOT NULL
);

CREATE TABLE dim_icd10 (
  icd10_sk    BIGSERIAL PRIMARY KEY,
  icd10_code  VARCHAR(10) UNIQUE NOT NULL,
  long_title  VARCHAR(400) NOT NULL
);

-- Fact table at encounter grain
CREATE TABLE fact_encounter (
  encounter_id BIGINT PRIMARY KEY,              -- optional surrogate also fine
  patient_sk   BIGINT NOT NULL REFERENCES dim_patient(patient_sk),
  provider_sk  BIGINT NOT NULL REFERENCES dim_provider(provider_sk),
  admit_date_sk INTEGER NOT NULL REFERENCES dim_date(date_sk),
  discharge_date_sk INTEGER,
  total_charges NUMERIC(12,2),
  length_of_stay_days NUMERIC(6,2)
);

-- Bridge table for N:M diagnoses per encounter
CREATE TABLE bridge_encounter_dx (
  encounter_id BIGINT NOT NULL REFERENCES fact_encounter(encounter_id) ON DELETE CASCADE,
  icd10_sk     BIGINT NOT NULL REFERENCES dim_icd10(icd10_sk),
  dx_rank      INT NOT NULL CHECK (dx_rank BETWEEN 1 AND 30),
  PRIMARY KEY (encounter_id, icd10_sk)
);
-- Example analytic query: top 10 diagnoses by encounters in the last 90 days
SELECT d.long_title, COUNT(*) AS encounters
FROM bridge_encounter_dx b
JOIN dim_icd10 d ON d.icd10_sk = b.icd10_sk
JOIN fact_encounter f ON f.encounter_id = b.encounter_id
JOIN dim_date dd ON dd.date_sk = f.admit_date_sk
WHERE dd.full_date >= CURRENT_DATE - INTERVAL '90 days'
GROUP BY d.long_title
ORDER BY encounters DESC
LIMIT 10;

5.8 Slowly Changing Dimensions (SCD) — Type 1 vs Type 2

  • Type 1: Overwrite old attribute (easy, but loses history).
  • Type 2: New row per change with effective_from/to, is_current. Preserves historical truth for time-correct analytics.
  • Type 3: Keep limited prior values in extra columns (rare for clinical data).

Choose SCD strategy per dimension. Patients usually SCD2; code vocab dimensions usually Type 1 (definitions rarely change for the same code).

5.9 Practical Denormalization for Analytics

  • Materialized views: pre-aggregate daily/weekly metrics; refresh nightly.
  • Wide export tables: team-friendly flat tables generated from the normalized core.
  • Snapshots: month-end copies of fact tables for audit-ready reproducibility.
-- Postgres example: monthly encounter summary (materialized)
CREATE MATERIALIZED VIEW mv_encounter_monthly AS
SELECT date_trunc('month', dd.full_date) AS month_start,
       COUNT(*) AS encounters,
       SUM(f.total_charges) AS charges
FROM fact_encounter f
JOIN dim_date dd ON dd.date_sk = f.admit_date_sk
GROUP BY 1;

-- REFRESH MATERIALIZED VIEW mv_encounter_monthly;

5.10 Governance Tips for Health Analytics

  • Lineage: Record source system and transformation notes for each fact/dimension.
  • Quality checks: Null-rate, range checks, foreign key coverage, duplicate code audits.
  • PII handling: De-identify exports; restrict schema access; log queries touching PHI.

6) ERDs — Visualize Before You Implement

An Entity-Relationship Diagram (ERD) is a visual blueprint of a database. It's a critical tool for planning and communicating your design before writing a single line of SQL.

6.1 Components

  • Entity (Rectangle): Represents a table.
  • Attributes (listed in entity): Represents the columns. Always mark the PRIMARY KEY (PK) and FOREIGN KEY (FK).
  • Relationships (Lines): Connect entities to show how they relate.

A simple ERD for a retail system looks like this:

Customer (customer_id PK, email UNIQUE, first_name, last_name)
   |
   | 1:N
   |
Order (order_id PK, customer_id FK→Customer.customer_id, order_date)
   |
   | 1:N
   |
OrderItem (order_id FK, product_id FK, qty, unit_price, PRIMARY KEY(order_id, product_id))
   ^
   |
   N:1
Product (product_id PK, sku UNIQUE, name, price)

6.2 Cardinality

Cardinality defines the number of instances of one entity that can be associated with the number of instances of another entity.

  • 1:1 (One-to-One): Rare, often a sign that you should merge the two tables.
  • 1:N (One-to-Many): The most common relationship. For example, one customer can have many orders.
  • N:M (Many-to-Many): A relationship where many instances of one entity can relate to many instances of another. This is resolved using a junction table. For example, many students can enroll in many classes, so a junction table like enrollment is used.

7) Best-Practice Checklist

This checklist summarizes what database professionals actually do in practice:

  • Planning & modeling:
    • Start with a mission statement and scope.
    • List entities, attributes, and keys.
    • Validate the design with stakeholders using ERDs as a contract.
    • Prefer surrogate keys for stability; keep natural keys with a UNIQUE constraint.
    • Choose tight data types and add CHECK constraints for domain rules.
  • Naming & documentation:
    • Maintain consistent naming conventions.
    • Comment tables and columns where supported.
    • Version your schema (migrations) and keep a changelog.
  • Integrity & performance:
    • Always enforce FOREIGN KEY constraints; never rely solely on app logic.
    • Index foreign keys and frequent search/filter columns.
    • Use composite indexes that match your query patterns.
    • Normalize for OLTP; denormalize for analytics.
  • Security & governance:
    • Apply the principle of least privilege.
    • Protect PII with encryption and auditing.
    • Establish clear backup, restore, and data retention policies.

Exercise 1 — Identify entities, keys, and columns (15–20 min)

Prompt: A bookstore app needs to track customers, books, authors, and purchases. List entities and attributes (with proposed types), choose primary keys, and identify relationships and their cardinalities.

Expected Direction (not unique):

  • Customer(customer_id PK, email UNIQUE, first_name, last_name, created_at)

  • Book(book_id PK, isbn UNIQUE, title, published_year, list_price)
  • BookAuthor(book_id FK, author_id FK, PRIMARY KEY(book_id, author_id))

Exercise 2 — Write the DDL with constraints (20–25 min)

Prompt: Implement the schema for Customer, Order, and OrderItem from Exercise 1 with appropriate constraints: email UNIQUE, qty > 0, unit_price ≥ 0, and meaningful FOREIGN KEY actions.

CREATE TABLE customer (
  customer_id BIGSERIAL PRIMARY KEY,
  email       VARCHAR(255) UNIQUE NOT NULL,
  first_name  VARCHAR(100) NOT NULL,
  last_name   VARCHAR(100) NOT NULL
);

CREATE TABLE "order" (
  order_id    BIGSERIAL PRIMARY KEY,
  customer_id BIGINT NOT NULL
              REFERENCES customer(customer_id) ON DELETE RESTRICT,
  order_date  DATE NOT NULL DEFAULT CURRENT_DATE
);

CREATE TABLE order_item (
  order_id   BIGINT NOT NULL
             REFERENCES "order"(order_id) ON DELETE CASCADE,
  book_id    BIGINT NOT NULL,
  qty        INTEGER NOT NULL CHECK (qty > 0),
  unit_price NUMERIC(10,2) NOT NULL CHECK (unit_price >= 0),
  PRIMARY KEY (order_id, book_id)
);

End-of-Module Project — Design & Implement a Mini OLTP (60–90 min)

Scenario: A small clinic needs a system to track patients, appointments, providers, and billed services.

Deliverables:

  1. An ERD with entities, attributes (types), PKs, FKs, and cardinalities.
  2. DDL to create tables with appropriate constraints: Patients (unique MRN), Providers (unique NPI), Appointments (FK to Patient/Provider), Services (catalog), AppointmentService (junction with qty, charge).
  3. Sample data (a few INSERT statements per table).
  4. Two illustrative queries: one to list upcoming appointments with patient and provider names, and another to calculate total charges per patient.
  5. A short paragraph on normalization choices and any intentional denormalization.

Starter DDL:

CREATE TABLE patient (
  patient_id BIGSERIAL PRIMARY KEY,
  mrn        VARCHAR(20) UNIQUE NOT NULL,
  first_name VARCHAR(100) NOT NULL,
  last_name  VARCHAR(100) NOT NULL,
  dob        DATE NOT NULL
);

CREATE TABLE provider (
  provider_id BIGSERIAL PRIMARY KEY,
  npi         VARCHAR(20) UNIQUE NOT NULL,
  name        VARCHAR(150) NOT NULL,
  specialty   VARCHAR(100)
);

CREATE TABLE appointment (
  appt_id     BIGSERIAL PRIMARY KEY,
  patient_id  BIGINT NOT NULL REFERENCES patient(patient_id) ON DELETE CASCADE,
  provider_id BIGINT NOT NULL REFERENCES provider(provider_id) ON DELETE RESTRICT,
  appt_time   TIMESTAMP NOT NULL
);

CREATE TABLE service (
  service_id  BIGSERIAL PRIMARY KEY,
  cpt_code    VARCHAR(10) UNIQUE NOT NULL,
  description VARCHAR(200) NOT NULL,
  charge      NUMERIC(10,2) NOT NULL CHECK (charge >= 0)
);

CREATE TABLE appointment_service (
  appt_id    BIGINT NOT NULL REFERENCES appointment(appt_id) ON DELETE CASCADE,
  service_id BIGINT NOT NULL REFERENCES service(service_id),
  qty        INTEGER NOT NULL CHECK (qty > 0),
  charge     NUMERIC(10,2) NOT NULL CHECK (charge >= 0),
  PRIMARY KEY (appt_id, service_id)
);

Example Queries:

-- Upcoming appointments (next 7 days)
SELECT a.appt_time,
       p.first_name || ' ' || p.last_name AS patient,
       pr.name AS provider
FROM appointment a
JOIN patient  p  ON p.patient_id  = a.patient_id
JOIN provider pr ON pr.provider_id = a.provider_id
WHERE a.appt_time >= CURRENT_DATE
  AND a.appt_time <  CURRENT_DATE + INTERVAL '7 days'
ORDER BY a.appt_time;

-- Total charges per patient
SELECT p.patient_id,
       p.first_name || ' ' || p.last_name AS patient,
       SUM(asv.qty * asv.charge) AS total_charges
FROM appointment a
JOIN patient p           ON p.patient_id = a.patient_id
JOIN appointment_service asv ON asv.appt_id = a.appt_id
GROUP BY p.patient_id, p.first_name, p.last_name
ORDER BY total_charges DESC;

Quick Reference

Column definitions: column_name DATA_TYPE [NULL | NOT NULL] [DEFAULT expr]

Table constraints:

[CONSTRAINT name] PRIMARY KEY (col[, …])
[CONSTRAINT name] UNIQUE (col[, …])
[CONSTRAINT name] CHECK (boolean_expression)
[CONSTRAINT name] FOREIGN KEY (col[, …])
  REFERENCES parent_table(parent_col[, …])
  [ON UPDATE action] [ON DELETE action]

Actions (common): NO ACTION/RESTRICT, CASCADE, SET NULL, SET DEFAULT.

Indexing (typical patterns):

CREATE INDEX idx_order_customer ON "order"(customer_id);
CREATE INDEX idx_product_sku ON product(sku);
CREATE INDEX idx_appointment_time ON appointment(appt_time);

Common Pitfalls

  • No FKs: This leads to orphan rows. Always declare FOREIGN KEY constraints.
  • Overly wide text types: Use VARCHAR(n) when you know reasonable bounds to save storage and improve performance.
  • Ambiguous names: Inconsistent naming slows everyone down—standardize from the beginning.
  • Everything as TEXT: You lose validation and performance hints. Always pick proper data types.
  • Missing CHECKs: Encode business rules like qty > 0 and charge ≥ 0.
  • Indexes everywhere: Create targeted indexes for specific queries; measure performance with EXPLAIN/ANALYZE.
  • Skipping docs: Add comments to your schema and keep a schema migration log.
