Strings and Dates in PostgreSQL

Turn messy text and raw timestamps into consistent, analyzable features using PostgreSQL-native functions and reproducible transformation patterns.

Essential question: How do we transform text and time without accidentally changing meaning, losing precision, or hiding data-quality problems?

Transformation habit

Inspect raw value → choose a typed representation → transform explicitly → validate output → preserve the original when auditability matters.

Start here

Text and time are analytical data types, not display details

String and date functions are often introduced as syntax lists. In analytics work, the more important skill is deciding what representation you need before transforming a value. A name, email, address, date, timestamp, and interval each carry different semantics.

Learning objectives

  • Standardize case, whitespace, and text presentation.
  • Parse and combine strings with SUBSTRING, POSITION, SPLIT_PART, CONCAT_WS, and related functions.
  • Use REGEXP_REPLACE and pattern checks for controlled text cleaning.
  • Distinguish date, timestamp, timestamptz, and interval.
  • Use EXTRACT, DATE_TRUNC, arithmetic, AGE, and intervals correctly.
  • Separate parsing into typed values from formatting values for display.

PostgreSQL correction

The core temporal vocabulary in this module is PostgreSQL-native: EXTRACT, DATE_TRUNC, timestamp/date subtraction, interval arithmetic, AGE, TO_DATE/TO_TIMESTAMP, and TO_CHAR.

Do not teach DATEADD or DATEDIFF as PostgreSQL functions. Those names belong to other SQL dialects. PostgreSQL normally uses operators and intervals instead.

String fundamentals

Case, whitespace, and length: know exactly what changes

Case

UPPER, LOWER, and INITCAP change presentation. They do not prove identity.

INITCAP(BTRIM(name))

Whitespace

BTRIM/TRIM remove boundary characters; they do not collapse repeated internal spaces.

REGEXP_REPLACE(...)

Length

LENGTH/CHAR_LENGTH count characters and help expose hidden whitespace or malformed fields.

LENGTH(BTRIM(name))
PostgreSQL
SELECT subject_id, name,
       UPPER(name) AS upper_name,
       LOWER(name) AS lower_name,
       INITCAP(BTRIM(name)) AS display_name,
       LENGTH(name) AS raw_length,
       LENGTH(BTRIM(name)) AS trimmed_length
FROM patients
ORDER BY subject_id;
PostgreSQL
SELECT subject_id, name,
       REGEXP_REPLACE(BTRIM(name), '[[:space:]]+', ' ', 'g') AS normalized_name
FROM patients
ORDER BY subject_id;
Common mistake: TRIM('A B') still contains two spaces between A and B. Boundary trimming and internal whitespace normalization solve different problems.
String structure

Parse fields when structure is meaningful; combine fields when the output needs context

Email addresses are useful for demonstrating positions, delimiters, and substrings because the @ character has structural meaning.

Input
alice.smith@email.com
→
User
alice.smith
Domain
email.com
PostgreSQL
SELECT subject_id, email,
       SPLIT_PART(LOWER(BTRIM(email)), '@', 1) AS email_user,
       SPLIT_PART(LOWER(BTRIM(email)), '@', 2) AS email_domain,
       POSITION('@' IN COALESCE(email,'')) AS at_position
FROM patients
ORDER BY subject_id;
PostgreSQL
SELECT subject_id,
       CONCAT_WS(' | ',
         REGEXP_REPLACE(BTRIM(name), '[[:space:]]+', ' ', 'g'),
         NULLIF(BTRIM(email), ''),
         BTRIM(address)
       ) AS contact_line
FROM patients
ORDER BY subject_id;

Create reproducible codes with substrings

PostgreSQL
SELECT product_id, product_name,
       UPPER(SUBSTRING(BTRIM(product_name) FROM 1 FOR 3)) || '-' || LPAD(product_id::text, 3, '0') AS product_code
FROM products
ORDER BY product_id;

A generated display code is not automatically a database key. Keep identifiers and presentation labels conceptually separate.

Pattern-based cleaning

Use regular expressions for controlled normalization and validation

1. BoundariesBTRIM external whitespace.
2. NormalizeReplace only characters or patterns you have defined as noise.
3. ValidateUse a separate pattern check to flag questionable values.
4. ReviewDo not turn every invalid-looking value into a guessed correction.
PostgreSQL
SELECT subject_id, email,
       LOWER(REGEXP_REPLACE(BTRIM(email), '[^[:alnum:]@._+-]', '', 'g')) AS clean_email
FROM patients
WHERE email IS NOT NULL
ORDER BY subject_id;
PostgreSQL
SELECT subject_id, email,
       CASE
         WHEN LOWER(BTRIM(email)) ~ '^[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}$' THEN 'valid shape'
         ELSE 'review'
       END AS email_shape_check
FROM patients
ORDER BY subject_id;
The email pattern here is a teaching-level shape check, not full internet email validation. Real production validation rules should match application requirements.
Temporal foundation

Choose the temporal type before choosing the function

date

Calendar date without time of day. Example: admission date.

timestamp

Date + local clock time, without time-zone interpretation.

timestamptz

An instant in time, displayed according to a time zone.

interval

A duration such as 5 days 6:15:00.

1. What happened?Event or reporting date?
2. Need clock time?If no, a date may be enough.
3. Need an instant?Use timestamptz when zones matter.
4. Need duration?Use subtraction or an interval.
5. Need display text?Format last, after analytics.
Storage precision and analytical grain are different ideas. You can store a full timestamp and later analyze it at day, week, month, or quarter grain.
Temporal grouping

EXTRACT reads a component; DATE_TRUNC changes the analytical grain

Timestamp2026-03-18 14:40
→
DayDATE_TRUNC('day', ...)
→
WeekDATE_TRUNC('week', ...)
→
MonthDATE_TRUNC('month', ...)
→
QuarterDATE_TRUNC('quarter', ...)
PostgreSQL
SELECT hadm_id, admit_time,
       EXTRACT(YEAR FROM admit_time) AS year,
       EXTRACT(MONTH FROM admit_time) AS month,
       EXTRACT(DOW FROM admit_time) AS dow,
       EXTRACT(HOUR FROM admit_time) AS hour
FROM admissions
ORDER BY admit_time;
PostgreSQL
SELECT order_id, order_ts,
       DATE_TRUNC('day', order_ts) AS order_day,
       DATE_TRUNC('week', order_ts) AS order_week,
       DATE_TRUNC('month', order_ts) AS order_month,
       DATE_TRUNC('quarter', order_ts) AS order_quarter
FROM orders
ORDER BY order_ts;

Aggregation at month grain

PostgreSQL
SELECT DATE_TRUNC('month', order_ts)::date AS month,
       COUNT(*) AS order_count,
       SUM(total_amount) AS revenue
FROM orders
GROUP BY DATE_TRUNC('month', order_ts)
ORDER BY month;

Temporal arithmetic

Subtraction answers elapsed time; intervals shift time

Admit
Jan 10, 08:15
Discharge
Jan 15, 14:30
+14 days
Follow-up window
+30 days
Longer follow-up

For timestamps, subtraction returns an interval. Converting that interval to a numeric day value is a separate analytical choice.

PostgreSQL
SELECT hadm_id, subject_id, admit_time, discharge_time,
       discharge_time - admit_time AS stay_interval,
       ROUND(EXTRACT(EPOCH FROM (discharge_time - admit_time))/86400.0, 2) AS stay_days
FROM admissions
WHERE discharge_time IS NOT NULL
ORDER BY stay_days DESC;
PostgreSQL
SELECT hadm_id, discharge_time,
       discharge_time + INTERVAL '14 days' AS followup_14d,
       discharge_time + INTERVAL '30 days' AS followup_30d
FROM admissions
WHERE discharge_time IS NOT NULL
ORDER BY discharge_time;

AGE() versus exact elapsed interval

AGE() expresses a symbolic calendar interval in years/months/days, while direct timestamp subtraction gives the elapsed interval between two instants.

PostgreSQL
SELECT hadm_id,
       AGE(discharge_time, admit_time) AS calendar_interval,
       discharge_time - admit_time AS exact_elapsed_interval
FROM admissions
WHERE discharge_time IS NOT NULL
ORDER BY hadm_id;
Input and output boundaries

Parsing creates typed values; formatting creates text

Raw text'08/05/2026'
→
Typed dateTO_DATE(...)

Safe for sorting and arithmetic

→
Display textTO_CHAR(...)

For reports / labels

PostgreSQL
SELECT row_id, raw_date,
       CASE
         WHEN NULLIF(BTRIM(raw_date),'') IS NULL THEN NULL
         WHEN raw_date ~ '^\d{4}-\d{2}-\d{2}$' THEN raw_date::date
         WHEN raw_date ~ '^\d{2}/\d{2}/\d{4}$' THEN TO_DATE(raw_date,'MM/DD/YYYY')
         WHEN raw_date ~ '^\d{8}$' THEN TO_DATE(raw_date,'YYYYMMDD')
         ELSE NULL
       END AS parsed_date
FROM staging_dates
ORDER BY row_id;
PostgreSQL
SELECT hadm_id, admit_time,
       TO_CHAR(admit_time, 'FMMonth DD, YYYY HH24:MI') AS formatted_admit,
       TO_CHAR(admit_time, 'YYYY-MM-DD') AS iso_date_text
FROM admissions
ORDER BY admit_time;
Do not format dates early. Once a date becomes arbitrary display text, chronological sorting and date arithmetic become harder or unsafe.

Time zones: distinguish stored instant from displayed clock time

Stored

timestamptz represents an instant.

Eastern display

AT TIME ZONE 'America/New_York'

UTC display

AT TIME ZONE 'UTC'

PostgreSQL
SELECT order_id, order_ts,
       order_ts AT TIME ZONE 'America/New_York' AS eastern_local,
       order_ts AT TIME ZONE 'UTC' AS utc_clock
FROM orders
ORDER BY order_id;
Apply the ideas

Practice and integrated data-preparation projects

Practice: combined patient profile

Join patient and admission data, standardize the name, extract the email domain, reduce timestamps to month grain, and calculate length of stay.

PostgreSQL
SELECT p.subject_id,
       INITCAP(REGEXP_REPLACE(BTRIM(p.name), '[[:space:]]+', ' ', 'g')) AS clean_name,
       SPLIT_PART(LOWER(BTRIM(p.email)), '@', 2) AS email_domain,
       a.hadm_id,
       DATE_TRUNC('month', a.admit_time)::date AS admit_month,
       ROUND(EXTRACT(EPOCH FROM (a.discharge_time-a.admit_time))/86400.0,2) AS stay_days
FROM patients AS p
JOIN admissions AS a USING (subject_id)
ORDER BY p.subject_id, a.admit_time;

Project A: contact-data quality view

Create cleaned analytical fields while keeping raw columns available for audit and review.

PostgreSQL
SELECT subject_id,
       name AS raw_name,
       INITCAP(REGEXP_REPLACE(BTRIM(name), '[[:space:]]+', ' ', 'g')) AS clean_name,
       LOWER(BTRIM(email)) AS clean_email,
       SPLIT_PART(LOWER(BTRIM(email)), '@', 2) AS email_domain,
       CASE WHEN email IS NULL THEN 'missing'
            WHEN LOWER(BTRIM(email)) ~ '^[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}$' THEN 'valid shape'
            ELSE 'review' END AS email_status,
       BTRIM(REPLACE(address, 'GSO', 'Greensboro')) AS clean_address
FROM patients
ORDER BY subject_id;

Project B: monthly order features

Transform timestamped orders into month-level measures suitable for dashboards or later modeling.

PostgreSQL
SELECT DATE_TRUNC('month', order_ts)::date AS month,
       COUNT(*) AS orders,
       COUNT(DISTINCT customer_id) AS customers,
       SUM(total_amount) AS revenue,
       ROUND(AVG(total_amount),2) AS avg_order
FROM orders
GROUP BY DATE_TRUNC('month', order_ts)
ORDER BY month;
Assessment and closure

Can you transform text and time without losing meaning?

Recognition

  1. Why does TRIM not fix repeated internal whitespace?
  2. When is SPLIT_PART preferable to arbitrary substring positions?
  3. What is the difference between EXTRACT(MONTH...) and DATE_TRUNC('month'...)?
  4. What type results from timestamp subtraction?
  5. Why should TO_CHAR usually be near the reporting boundary?

Applied challenge

Return one row per admission with a normalized patient name, email domain, admission month, formatted admission label, and length of stay in hours. Preserve rows with missing email.

Key takeaways

  • Text normalization should be explicit, reversible where possible, and separated from validation.
  • TRIM handles boundaries; regular expressions can handle repeated internal patterns.
  • Parsing converts text into typed values; formatting converts typed values into text.
  • EXTRACT reads components, while DATE_TRUNC creates a coarser time grain.
  • Date/timestamp arithmetic and interval values replace many dialect-specific DATEADD/DATEDIFF patterns.
  • Keep timestamps typed for analytics; format only when a human-readable representation is actually needed.
