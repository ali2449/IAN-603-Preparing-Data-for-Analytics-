Slide 1: Start

Welcome to Module 3, PostgreSQL in Action. In this module, we are moving from designing a database to actually using it. In Module 2, the main questions were about structure: what tables should exist, which columns belong in each table, and how tables should relate to one another. Now our focus changes. We will use SQL to ask questions, retrieve useful rows, and make controlled changes to stored data.

If SQL is new to you, do not worry about memorizing every command. I want you to focus on a simple workflow. First, decide what information you need. Second, write the smallest SQL statement that can answer that question. Third, run the query. Fourth, inspect the rows, changes, or error messages that PostgreSQL gives you. Finally, verify the result before you move on.

Throughout this lesson, you can run SQL directly in the browser. We will begin with complete examples. Then you will make small changes, complete partially written statements, and finally write short queries yourself. This gradual approach is intentional. SQL becomes much easier when you learn one pattern at a time.

As you work, remember that reading data and changing data are different responsibilities. A SELECT statement normally reads data without changing the table. Commands such as INSERT, UPDATE, and DELETE can change stored data, so we will be more careful with them. We will also use transactions, keys, constraints, and RETURNING to make those changes safer.

Take your time with the examples. Run them, look at the result, and ask yourself what each clause contributed. That habit is more valuable than simply memorizing syntax.


Slide 2: Big picture

This slide connects Module 2 with what we are doing now. In Module 2, we designed the database. We created tables, chose data types, and defined relationships. In Module 3, we start using that structure to answer questions and manage rows.

A helpful habit is to think of database work as a short sequence. First, define the question. For example, maybe we need a list of active patients who are at least fifty years old. Second, preview the rows that match. This is especially important before changing data. Third, protect the operation by using a stable key and a clear WHERE condition. Fourth, execute the SQL statement. Finally, verify what happened.

That last step is easy to skip, but it is extremely important. A query can run successfully and still produce the wrong result if the condition was not what you intended. SQL does not know your business meaning. It only follows the instructions you write.

So the core habit for this module is: read the request, preview the target rows, run the smallest correct statement, inspect the result, and then keep or undo the change. You will see this same pattern repeated throughout the module.


Slide 3: Learning path

Here is the learning path for this module. We will approach SQL gradually instead of trying to learn everything at once.

We begin with reading data. You will use SELECT to choose columns, FROM to identify the table, WHERE to filter rows, ORDER BY to sort results, and LIMIT to restrict how many rows are displayed. We will also use aliases and simple expressions so the output is easier to understand.

Next, we move to changing data. INSERT adds new rows. UPDATE changes existing rows. DELETE can remove rows. These commands are powerful, so we will combine them with verification steps instead of running them casually.

The third part is protection. We will use stable identifiers such as a primary key or a unique MRN, transactions that can be committed or rolled back, database constraints, and PostgreSQL's RETURNING clause. These tools help us see exactly what was affected.

The coding progression is also gradual. First, run a complete example. Second, change one small part and compare the output. Third, complete a missing operator, value, or clause. Fourth, write a short statement using an earlier example as a pattern.

The goal is understanding, not memorization. If you understand what each clause is doing and can adapt a pattern to a new question, you are learning SQL the right way.


Slide 4: Running case

For the examples in this module, we use a small synthetic healthcare operations database. The data is fictional and designed only for practice.

There are four main tables. The patients table contains information such as a medical record number, a patient name, age, gender, and whether the patient is active. The doctors table stores doctor information, including names and specialties. The admissions table connects patients and doctors with information such as diagnosis, admission date, discharge date, and status. The clinical_notes table stores patient-linked notes in JSONB format, which gives us a chance to work with semi-structured data later in the module.

These tables are intentionally small. A small dataset makes it easier to compare your SQL statement with the result and understand why a row was included or excluded.

You may notice that the patients table stores age directly. Real systems often store a date of birth instead, because age changes over time and depends on the reference date. We keep age as a column here only to make our first SQL examples easier to read.

The important idea is that the same SQL patterns you learn with this small database can be applied to many other domains, such as retail, education, finance, or business operations.


Slide 5: SQL language map

SQL includes different groups of commands, and it helps to know what job each group performs.

DDL stands for Data Definition Language. These commands define or change the structure of the database. CREATE can create a table or another database object. ALTER changes an existing structure. DROP removes an object. TRUNCATE removes rows from a table while keeping the table itself. We worked more with this type of SQL when designing the database.

DQL is commonly used to describe Data Query Language. The key command here is SELECT. SELECT reads data and builds a result set. Most of the first half of this module focuses on querying data with SELECT.

DML stands for Data Manipulation Language. INSERT adds rows, UPDATE changes rows, DELETE removes rows, and MERGE can synchronize source and target data under defined conditions.

We also have transaction control. BEGIN starts a transaction. COMMIT keeps the changes. ROLLBACK discards the changes made inside the transaction.

You do not need to memorize the abbreviations. Focus on the purpose. Some SQL defines structure, some reads data, some changes data, and some controls whether a group of changes is kept or undone. The schema from Module 2 provides the rules, and the statements in this module operate inside those rules.


Slide 6: SELECT pattern

A SELECT query becomes much easier to understand when you read it like a sentence.

Start with SELECT. This answers the question, what do I want to see in the result? You can list one column, several columns, or expressions that calculate new values.

Next is FROM. This answers, where does the data come from? In our early examples, FROM points to one table. Later, when you learn joins, a query can combine data from several related tables.

WHERE is optional. It answers, which rows should stay? If we want only active patients or only patients above a certain age, the WHERE clause defines those conditions.

ORDER BY controls how the final rows are arranged. For example, we can sort age from highest to lowest. LIMIT can then keep only a certain number of rows.

So a useful reading pattern is: SELECT these columns, FROM this table, WHERE these conditions are true, ORDER the rows this way, and LIMIT the result if needed.

A good default is to list the columns you actually need instead of always using SELECT star. Explicit columns make the result clearer and reduce unnecessary data retrieval. You will practice that immediately in the next few slides.

The FROM clause says that the data comes from the patients table. The final clause, ORDER BY patient ID, sorts the result using the patient identifier.

If you are new to SQL, try reading the query aloud in plain language: show these patient fields from the patients table and sort the rows by patient ID. Translating SQL into a normal sentence is a very useful beginner technique.


Slide 8: Choose columns

This slide focuses on choosing only the columns we need.

The query selects MRN, full name, and age from the patients table. It does not return patient ID, gender, or active status because those fields are not needed for this particular question. The ORDER BY clause sorts age in descending order. DESC means the largest value comes first, so the oldest patients should appear at the top of the result.

Using an explicit column list has several benefits. First, it makes the purpose of the query easier to understand. When someone reads the SQL, they can immediately see what the output should contain. Second, it avoids retrieving columns that are not needed. Third, it makes downstream code more predictable because the result has a clear set of fields.

SELECT star can still be useful when you are exploring a small table and want to quickly see all columns. But it should be a deliberate choice, not an automatic habit.

Run the query and inspect the order of ages. Then try changing DESC to ASC. ASC means ascending order, so the youngest patient should move toward the top. This small change is a good way to see how ORDER BY shapes the result without changing the table itself.


Slide 9: Aliases expressions

A SELECT statement can do more than return stored columns. It can also rename output and calculate values.

In this example, full_name AS patient gives the full_name column a temporary label of patient in the result. The stored column in the table is still named full_name. The alias changes only what you see in this query output.

The expression age greater than or equal to sixty-five creates a new Boolean result called is_senior. PostgreSQL evaluates that expression for each row. If the patient's age is sixty-five or higher, the result is true. Otherwise, it is false.

This is an important idea. A SELECT query can derive useful information without changing the stored data. We do not need to add an is_senior column to the table just to answer this question. We can calculate it at query time.

Run the query and compare age with the is_senior result. Look for the boundary around age sixty-five. Then notice that the output is still ordered by age descending.

Aliases are helpful when an original column name is technical or when an expression needs a readable heading. Expressions are helpful when you want to calculate or classify values as part of the result. Both make SQL output more useful for analysis and reporting.


Slide 10: WHERE basics

The WHERE clause decides which rows remain in the result. This is one of the most important ideas in SQL because most real questions apply some kind of condition.

For simple comparisons, we can use equals, not equal, greater than, greater than or equal, less than, and less than or equal. For example, age greater than or equal to sixty-five keeps patients who are at least sixty-five.

BETWEEN is useful for a range. Age BETWEEN thirty AND sixty includes both endpoints, so ages thirty and sixty are included.

IN checks whether a value belongs to a list. For example, a status can be either Admitted or Discharged. Instead of writing two separate equality conditions joined by OR, IN can make the query easier to read.

LIKE and ILIKE are used for text patterns. In PostgreSQL, ILIKE performs case-insensitive matching, which means uppercase and lowercase letters do not have to match exactly.

Missing values need special treatment. We use IS NULL or IS NOT NULL rather than ordinary equality.

Finally, conditions can be combined with AND, OR, and NOT. AND requires all connected conditions to be true. OR requires at least one. When conditions become more complicated, parentheses help make the intended logic clear.


Slide 11: Change a filter

Now you will see how a small change in a WHERE condition can change the result.

The query returns MRN, full name, age, and active status from the patients table. The WHERE clause has two conditions connected with AND. First, is_active must be true. Second, age must be greater than or equal to fifty. Because we use AND, a row must satisfy both conditions to stay in the result.

Run the query once with fifty as the age threshold. Look at which active patients appear. Then change fifty to sixty and run the query again.

The table itself has not changed. We only changed the condition used to select rows. When the threshold becomes more restrictive, fewer rows may qualify.

This is a useful way to think about a predicate, which is another word you may hear for a condition. A predicate acts like a gate. Rows that satisfy the condition pass through. Rows that do not satisfy it are left out of the result.

Also notice that ORDER BY age DESC happens after filtering conceptually, so the qualifying patients are displayed from older to younger.

Small experiments like this are valuable. When learning SQL, change one number or one operator at a time and compare the results. It helps you understand exactly which part of the statement is controlling the output.


Slide 12: BETWEEN and IN

Two common filtering patterns are BETWEEN for ranges and IN for a list of allowed values.

BETWEEN is convenient when you want values inside an interval. For example, age BETWEEN thirty AND sixty includes age thirty, age sixty, and everything between them. It is important to remember that the endpoints are included.

IN is helpful when one column can match any value from a small list. For example, status IN open and pending is often easier to read than writing status equals open OR status equals pending.

The example on this slide combines a category condition with a range. We want female patients whose age is between thirty and sixty. The two conditions are connected with AND, so both must be true. Then ORDER BY age arranges the qualifying rows from lower age to higher age because ascending order is the default.

Run the query and inspect the rows. Then try changing the range. For example, change thirty to forty and see whether the result becomes smaller.

You could also replace the gender condition with a different value and compare the output. The important lesson is that SQL gives us several readable ways to express filtering logic. Choose the pattern that makes the condition easiest to understand.


Slide 13: ILIKE

This slide introduces text pattern matching with PostgreSQL ILIKE.

ILIKE is similar to LIKE, but it is case-insensitive. That means the pattern can match text even if uppercase and lowercase letters are different. This is useful when names or other text values were not entered with perfectly consistent capitalization.

The percent sign is a wildcard. It can represent zero or more characters. If the pattern is c percent, the text must begin with the letter c, followed by anything else. If the pattern is percent son, the text must end with son. If the pattern is percent gar percent, then gar can appear anywhere inside the text.

Our query selects MRN and full name from patients where the full name starts with c, ignoring case.

Run the query and see which names match. Then change the pattern to another letter, such as b percent. You can also experiment with a pattern that searches for text in the middle of a name.

Pattern matching is useful, but remember that broad patterns can return many rows in a large database. In real systems, you should still think carefully about what you are searching for and how selective the condition is.


Slide 14: NULL

NULL is one of the SQL ideas that often surprises beginners. NULL represents a missing or unknown value. It is not the same as zero, an empty string, or the word null stored as text.

Because NULL represents unknown information, ordinary equality does not test it correctly. Writing discharge_date equals NULL is not the right pattern. Instead, SQL provides the special predicates IS NULL and IS NOT NULL.

In our admissions table, a missing discharge date can indicate that an admission is still open. The query selects admission information where discharge_date IS NULL. That gives us the rows that do not currently have a discharge date.

Run the example and inspect the result. Notice that we are asking a clear data question: which admissions have no discharge date recorded?

This pattern is very common in data preparation. Missing values can affect filtering, calculations, and analysis, so you need to identify them correctly.

A simple rule to remember is: when checking whether a SQL value is missing, use IS NULL. When checking that a value is present, use IS NOT NULL. Do not use equals NULL or not-equal NULL as if NULL were an ordinary value.


Slide 15: Sort limit distinct

After choosing and filtering rows, we often need to organize the result. Three useful tools are ORDER BY, LIMIT, and DISTINCT.

ORDER BY controls the order of the returned rows. In this example, admissions are sorted by admission_date descending, which places more recent dates first. We also add admission_id descending as a second sort key. A second key is useful when two rows have the same date because it gives PostgreSQL another rule for ordering them.

LIMIT keeps only a chosen number of rows. Here, LIMIT three returns only the first three rows after sorting.

This is why ORDER BY and LIMIT often belong together. LIMIT three by itself does not mean the three newest records. It only means return three rows from whatever order PostgreSQL produces. If the meaning is newest, oldest, highest, or lowest, define that order explicitly.

DISTINCT is another tool. It removes repeated result rows. For example, if you only wanted a list of unique diagnosis values, SELECT DISTINCT diagnosis could be useful.

Run the current query and confirm that only three rows are returned. Then try changing LIMIT three to LIMIT five. The key idea is that ORDER BY gives meaning to which rows appear first, while LIMIT controls how many of those rows you keep.


Slide 16: Logical order

SQL is written in one order, but it helps to understand the conceptual order in which the parts of a query are resolved.

A simplified mental model is: FROM, then WHERE, then SELECT, then DISTINCT, then ORDER BY, and finally LIMIT.

FROM comes first conceptually because PostgreSQL needs to know the source of the data. WHERE then filters the source rows. SELECT determines the columns or expressions that will appear in the result. DISTINCT can remove repeated result rows. ORDER BY sorts the result. LIMIT keeps only the requested number of rows.

Why should a beginner care about this? Because it explains some behavior that can otherwise feel confusing. For example, WHERE filters rows before the final sorting happens. It also explains why a column alias created in SELECT may not always be available in an earlier logical part of the query.

You do not need to memorize a full database execution engine. Think of this as a reasoning tool. When a query behaves differently than you expected, ask what data exists at each conceptual stage.

For now, remember the basic flow: choose the source, filter the rows, build the result, remove duplicates if needed, sort it, and then limit the number of rows.

Slide 18: DML safety

We are now moving from reading data to changing data. This is where safe habits become especially important.

A SELECT statement normally builds a result without modifying the stored rows. INSERT, UPDATE, and DELETE are different because they can change the database. Before running one of those statements, use a controlled process.

First, preview the target rows with SELECT. If you plan to update a patient identified by an MRN, first run a SELECT using that same MRN in the WHERE clause. Confirm that the row you expected is the row that appears.

Second, use a stable identifier. A name may be repeated, misspelled, or changed. A primary key or a unique MRN is usually safer.

Third, use a transaction when appropriate. A transaction can let you test a change and then roll it back instead of keeping it.

Fourth, use RETURNING when PostgreSQL supports the pattern. RETURNING shows the rows affected by the write operation.

Finally, verify the result. Do not assume that success means correctness.

The most important warning on this slide is about WHERE. An UPDATE or DELETE without a WHERE clause can affect every row in a table. That is why previewing and verifying should become normal habits, not optional extra steps.


Slide 19: INSERT

INSERT adds a new row to a table. In this example, we are adding one fictional patient.

The statement begins with INSERT INTO patients. Inside parentheses, we list the columns that we are providing: MRN, full name, age, and gender. Naming the columns is a good habit because it makes the statement clearer and less dependent on the physical order of columns in the table.

The VALUES section provides one value for each listed column. The order must match the column list. Text values are surrounded by single quotes. The age is numeric, so it does not need quotes.

After the values, we use RETURNING. This is a very useful PostgreSQL feature. Instead of inserting the row and then wondering what happened, RETURNING immediately shows selected fields from the row that was stored. It can also show generated values such as a patient ID.

Run the statement and inspect the returned row. Check that the MRN, name, age, and gender match what you intended.

In a real workflow, you may also run a separate SELECT afterward using the new row's stable identifier. The main idea is simple: add the row, then verify it. Do not treat an INSERT as complete until you have confirmed what was stored.

Slide 21: UPDATE

UPDATE changes values in rows that already exist. Because it modifies stored data, we want to target the correct row as carefully as possible.

The example begins with a SELECT. It looks for the patient whose MRN is MRN one zero zero three. This preview step confirms which row matches before anything is changed.

Then the UPDATE statement targets the same patients table. SET age equals thirty-five describes the new value. The WHERE clause uses the same MRN condition that we just previewed. Finally, RETURNING shows the patient ID, MRN, name, and updated age.

Notice the pattern: preview with SELECT, then update using the same stable predicate, then inspect with RETURNING.

Why do we prefer an MRN or primary key instead of a name? Names are not always unique, and names can change. Stable identifiers make it less likely that we update multiple people accidentally.

Run the example and compare the preview row with the returned updated row. The identifying values should stay the same while the age changes.

Whenever you write an UPDATE, ask two questions before running it: which rows can match this WHERE condition, and how many rows do I expect to change? If the answer is unclear, go back to SELECT and preview first.


Slide 22: DELETE

Deleting data is not always the same as making a row inactive. This slide compares a soft delete with a hard delete.

A soft delete keeps the row in the database but changes a status field. In our example, we use UPDATE to set is_active to false for a specific patient. The row still exists, so its history and relationships can remain available, but the application can treat the record as inactive.

A hard delete uses DELETE FROM and physically removes a row from the table. That may be appropriate in some situations, but it can also remove important history or conflict with related records.

The example on the slide demonstrates a soft delete. We target the patient using a unique MRN and use RETURNING to verify the new active status.

Run the statement and inspect the returned row. Notice that the patient still has an ID, MRN, and name. Only the active flag has changed.

In real systems, the choice between soft and hard delete depends on business rules, retention requirements, audit needs, and privacy policies. The technical SQL command is only part of the decision.

For this course, remember the practical distinction: soft delete preserves the row and changes its status; hard delete removes the row itself.


Slide 23: Constraints protect data

Sometimes an error message is evidence that the database is doing its job correctly.

In this example, patient MRN one zero zero four is connected to an admission record. The relationship is protected by a foreign key that uses ON DELETE RESTRICT. That rule means PostgreSQL should not allow us to delete the patient while a related admission still depends on that patient record.

When you run the DELETE statement, PostgreSQL is expected to reject it. This is not simply bad luck or bad SQL. The database is protecting referential integrity. If the patient disappeared while the admission still pointed to that patient ID, the admission would reference a row that no longer exists.

This kind of rule is one reason we define keys and relationships when designing a database. Application code can make mistakes. A database constraint provides another layer of protection.

Run the example and read the error message. Try to identify the foreign key or related table mentioned in the message.

A useful habit is to interpret database errors instead of immediately trying to bypass them. Ask what rule was violated and why that rule exists. Constraint errors can reveal important information about uniqueness, required values, valid ranges, and relationships between tables.


Slide 24: Transactions

A transaction groups related database operations into one controlled unit of work.

BEGIN starts the transaction. After BEGIN, we can run one or more statements. COMMIT keeps the changes. ROLLBACK discards the changes made since the transaction began.

The example on this slide is designed for safe practice. First, BEGIN starts a transaction. Next, we update the age for MRN one zero zero three and use RETURNING to inspect the changed row. Then ROLLBACK undoes that update. Finally, a SELECT checks the patient again.

When you run the full example, pay attention to the two ages you see. RETURNING should show the temporary updated value inside the transaction. The final SELECT, after ROLLBACK, should show the original value again.

This is a powerful learning pattern because it lets you practice data-changing SQL without permanently keeping the change.

In real applications, transactions are also used when several changes belong together. For example, if one operation succeeds but another related operation fails, we may want to undo the whole unit rather than leave the database in a partial state.

For now, remember the three words: BEGIN starts, COMMIT keeps, and ROLLBACK undoes.


Slide 25: ACID

ACID is a common way to describe important properties of database transactions. You do not need to memorize a textbook definition, but you should understand the general idea behind each letter.

Atomicity means the related work is treated as one unit. If the transaction cannot complete correctly, the changes can be undone together instead of leaving only part of the work completed.

Consistency means the database rules should still hold when the transaction finishes. Constraints, valid relationships, and other rules should not be broken by a completed transaction.

Isolation is about concurrent work. Databases often serve many users or applications at the same time. Isolation controls how transactions interact so that intermediate states do not create incorrect results for other work.

Durability means that once a transaction is committed, the database is expected to preserve that committed change even if the system later restarts or encounters a failure.

A simple way to remember the purpose of ACID is reliability. Transactions are not only about writing BEGIN and COMMIT. They are a mechanism for keeping database changes controlled and dependable.

In this introductory course, focus especially on atomicity and the practical difference between COMMIT and ROLLBACK. The deeper details of isolation levels can come later.

Slide 29: Insert select

This slide introduces a pattern that connects SQL querying with data preparation workflows: INSERT INTO followed by SELECT.

The idea is simple. First, a SELECT query identifies a set of rows. Instead of only displaying those rows, INSERT INTO SELECT can copy the selected values into another table.

The example first creates a table called senior_patients with patient ID, MRN, full name, and age. Then the INSERT statement names the target columns. The SELECT portion retrieves those same fields from patients where age is greater than or equal to sixty-five. Finally, another SELECT displays the derived table.

Run the example and follow the process in three stages: create the destination, populate it from a query, and inspect the result.

This pattern appears in staging workflows, ETL or ELT processes, archives, reporting tables, and data marts. It can be very useful when you need to move or reshape selected data inside a database.

One important detail is that the SELECT output must be compatible with the target columns. The number of values, their order, and their data types should make sense for the destination table.

For now, think of INSERT INTO SELECT as taking the result of a query and using it as the input to another table.


Slide 30: MERGE optional

MERGE is an optional advanced topic, so do not worry if this feels more complex than the earlier commands.

MERGE is useful when you have a source dataset and a target table and you want one statement to decide what should happen for each source row.

The most important part is the ON condition. The ON condition defines when a source row and a target row represent the same record. In this example, the match is based on MRN.

When a source MRN already exists in the target, the WHEN MATCHED branch updates selected fields. When a source MRN does not exist, the WHEN NOT MATCHED branch inserts a new row.

The example first creates a temporary incoming_patients table, adds a couple of source rows, and then merges that source into patients. After the MERGE, a SELECT shows the relevant records.

If your PostgreSQL environment supports MERGE, you can run the example and compare the matched row with the newly inserted row.

The safety lesson is more important than the syntax. Before using MERGE on important data, make sure the source does not contain unexpected duplicates and make sure the ON condition really identifies the same entity. A poor match rule can update the wrong records or create duplicates.


Slide 31: Common mistakes

This slide collects several mistakes that are easy to make when learning SQL. Each one has a simple safer habit.

First, do not test a missing value with equals NULL. Use IS NULL or IS NOT NULL.

Second, be careful when mixing AND and OR. SQL has operator precedence rules, and the database may group conditions differently than you intended. Parentheses are a good way to make the logic explicit and easier for another person to read.

Third, LIMIT without ORDER BY does not create a reliable top, newest, or oldest set. If the order has meaning, define it.

Fourth, avoid updating by a field that is not reliably unique. A name can repeat. A primary key or unique identifier is usually safer.

Fifth, do not delete rows before previewing them. Run a SELECT with the same WHERE condition first and inspect exactly which rows match.

These are small habits, but they prevent large problems. SQL is often used on important shared data, so clarity matters.

When you write a query, do not only ask, will this syntax run? Also ask, is the condition precise, is the result deterministic, and do I know exactly which rows can be affected?

Slide 34: Self-check

Slide 43: Summary

Let us finish Module 3 by reviewing the main ideas.

SELECT builds a result from stored data. An explicit column list helps define exactly what the result should contain.

WHERE chooses which rows remain. You practiced comparisons, BETWEEN for ranges, IN for lists of values, ILIKE for case-insensitive text patterns, and IS NULL for missing values.

ORDER BY controls the result order. LIMIT keeps a chosen number of rows, and DISTINCT can remove repeated result values.

INSERT adds rows. UPDATE changes existing rows. DELETE can remove rows, while a soft-delete pattern can preserve a row and mark it inactive. Because these statements change data, you practiced previewing target rows, using stable keys, and verifying the result with RETURNING.

Transactions give you control over whether a group of changes is kept or undone. BEGIN starts a transaction, COMMIT keeps it, and ROLLBACK discards it. Database constraints provide another layer of protection by enforcing rules and relationships.

You also worked with JSONB and with INSERT INTO SELECT, which connects SQL to broader data preparation and pipeline workflows.
