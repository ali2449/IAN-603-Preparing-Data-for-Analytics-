Reshaping habit

State the output grain first. Then decide which categories become rows, which become columns, and which measure must be aggregated.

Start here

Reshaping changes structure—not the underlying facts

Analytics often needs the same information in different shapes. A dashboard may prefer one row per month with products as columns; a statistical workflow may prefer one row per product-month. The transformation is useful only when you can explain the grain before and after the reshape.

Learning objectives

By the end of this module, you will be able to:

  • Distinguish long and wide data and state the grain of each result.
  • Pivot rows to columns with conditional aggregation using CASE and PostgreSQL aggregate FILTER.
  • Unpivot columns to rows with UNION ALL and CROSS JOIN LATERAL (VALUES ...).
  • Preserve meaningful NULL values rather than automatically replacing absence with zero.
  • Combine joins, pre-aggregation, and reshaping without multiplying facts.
  • Choose a long or wide delivery shape based on the needs of visualization, reporting, or modeling.
Rule: before writing a pivot, complete this sentence: “One output row represents ___.”

Prefer long form when

  • categories change frequently,
  • you need time-series or faceted visualization,
  • you want flexible grouping/filtering,
  • the next step is modeling or tidy analysis.

Prefer wide form when

  • the report needs fixed side-by-side categories,
  • users expect a matrix or scorecard,
  • columns have stable business meaning,
  • the downstream system requires a fixed schema.
Do not confuse reshaping with aggregation. Many pivots require aggregation because several source rows map to one output cell. That aggregation can remove detail permanently.

Rows → columns

Pivot with conditional aggregation

PostgreSQL does not require a dedicated core PIVOT keyword. A transparent pattern is to group by the desired row grain and use a conditional aggregate for each output category.

Row grain
month
Column categories
diagnosis
Cell measure
count

Portable CASE pattern

Conditional aggregation with CASE
SELECT DATE_TRUNC('month', admit_time)::date AS admit_month,
       SUM(CASE WHEN diagnosis = 'Pneumonia' THEN 1 ELSE 0 END) AS pneumonia_count,
       SUM(CASE WHEN diagnosis = 'Fracture' THEN 1 ELSE 0 END) AS fracture_count,
       SUM(CASE WHEN diagnosis = 'Flu' THEN 1 ELSE 0 END) AS flu_count
FROM admissions
GROUP BY 1
ORDER BY 1;

PostgreSQL FILTER pattern

Aggregate FILTER
SELECT DATE_TRUNC('month', admit_time)::date AS admit_month,
       COUNT(*) FILTER (WHERE diagnosis = 'Pneumonia') AS pneumonia_count,
       COUNT(*) FILTER (WHERE diagnosis = 'Fracture') AS fracture_count,
       COUNT(*) FILTER (WHERE diagnosis = 'Flu') AS flu_count
FROM admissions
GROUP BY 1
ORDER BY 1;

Both queries produce the same conceptual shape. FILTER can be easier to read because the aggregate and its category condition stay together.

Missing is not always zero. A count of events may reasonably be zero. A missing survey score is different: use MAX(CASE WHEN ... THEN score END) or a filtered aggregate so absence remains NULL.
Survey scores: preserve missing cells
SELECT respondent_id,
       MAX(score) FILTER (WHERE question = 'Q1') AS q1_score,
       MAX(score) FILTER (WHERE question = 'Q2') AS q2_score,
       MAX(score) FILTER (WHERE question = 'Q3') AS q3_score
FROM survey_responses
GROUP BY respondent_id
ORDER BY respondent_id;
Columns → rows

Unpivot wide tables into a reusable long form

Unpivoting turns repeated measure columns into a category column plus a value column. This is useful when month names, metrics, or survey questions were stored as columns but analysis needs them as rows.

Long result

Reshaping data example table 2

Method 1: UNION ALL

Explicit UNION ALL
SELECT product, DATE '2025-01-01' AS sale_month, jan_revenue AS revenue
FROM monthly_sales
UNION ALL
SELECT product, DATE '2025-02-01', feb_revenue
FROM monthly_sales
UNION ALL
SELECT product, DATE '2025-03-01', mar_revenue
FROM monthly_sales
ORDER BY product, sale_month;

Method 2: CROSS JOIN LATERAL + VALUES

PostgreSQL LATERAL VALUES
SELECT m.product, v.sale_month, v.revenue
FROM monthly_sales AS m
CROSS JOIN LATERAL (
    VALUES
      (DATE '2025-01-01', m.jan_revenue),
      (DATE '2025-02-01', m.feb_revenue),
      (DATE '2025-03-01', m.mar_revenue)
) AS v(sale_month, revenue)
ORDER BY m.product, v.sale_month;

The lateral form keeps all source columns available while generating several rows from each source row. It is especially useful when many related columns share a common output type.

Unpivot patient metrics
SELECT p.patient_id, v.metric, v.value
FROM patient_metrics AS p
CROSS JOIN LATERAL (
    VALUES
      ('heart_rate', p.heart_rate::numeric),
      ('systolic_bp', p.systolic_bp::numeric),
      ('diastolic_bp', p.diastolic_bp::numeric),
      ('oxygen_sat', p.oxygen_sat)
) AS v(metric, value)
ORDER BY p.patient_id, v.metric;
When unpivoted columns have different data types, PostgreSQL must find a common type. Cast explicitly when needed so the output value column has a deliberate type.
The most important safeguard

Grain determines whether a pivot is correct

Source factOne row per sale transaction
GroupOne product-month group
AggregateSUM revenue inside the group
Pivot cellOne total per product × month

The seeded sales table deliberately contains two Laptop rows in January. A pivot cell cannot contain both transaction rows, so you must decide how to combine them.

Inspect source cardinality
SELECT product, sale_month, COUNT(*) AS source_rows, SUM(revenue) AS total_revenue
FROM sales
GROUP BY product, sale_month
ORDER BY product, sale_month;
Validation habit: compare totals before and after reshaping. For additive measures such as revenue, the long-form grand total should equal the sum of all populated pivot cells.
Combine earlier modules

Join first only when the join preserves the intended fact grain

A common report joins descriptive data to facts and then pivots. The safe approach is to know which table defines the measure and whether the join can duplicate that measure.

Patient admissions by month
SELECT p.subject_id, p.name,
       COUNT(a.hadm_id) FILTER (WHERE DATE_TRUNC('month', a.admit_time) = DATE '2025-01-01') AS jan_admissions,
       COUNT(a.hadm_id) FILTER (WHERE DATE_TRUNC('month', a.admit_time) = DATE '2025-02-01') AS feb_admissions,
       COUNT(a.hadm_id) FILTER (WHERE DATE_TRUNC('month', a.admit_time) = DATE '2025-03-01') AS mar_admissions
FROM patients AS p
LEFT JOIN admissions AS a ON a.subject_id = p.subject_id
GROUP BY p.subject_id, p.name
ORDER BY p.subject_id;

Here, patients contributes one descriptive row per patient and admissions contributes the fact rows being counted. The patient table does not multiply admissions.

Pre-aggregate before later reshaping when needed

Pre-aggregate sales to product-month
WITH monthly_product AS (
    SELECT product, category, sale_month, SUM(revenue) AS revenue
    FROM sales
    GROUP BY product, category, sale_month
)
SELECT category,
       SUM(revenue) FILTER (WHERE sale_month = DATE '2025-01-01') AS jan_revenue,
       SUM(revenue) FILTER (WHERE sale_month = DATE '2025-02-01') AS feb_revenue,
       SUM(revenue) FILTER (WHERE sale_month = DATE '2025-03-01') AS mar_revenue
FROM monthly_product
GROUP BY category
ORDER BY category;
If you join two one-to-many child tables before aggregating, you can multiply rows and inflate pivot cells. Apply the cardinality lessons from Module 6 before trusting a reshaped result.
Reason about reversibility

A reshape can be reversible—or lossy

Groupproduct-month
Pivotmonthly columns
Unpivotmonth rows
Long resultmonthly totals

The round trip does not recover original transaction IDs because the pivot aggregated them into monthly totals. It recovers the aggregated grain—not the original grain.

Pivot then unpivot
WITH wide AS (
    SELECT product,
           SUM(revenue) FILTER (WHERE sale_month = DATE '2025-01-01') AS jan_revenue,
           SUM(revenue) FILTER (WHERE sale_month = DATE '2025-02-01') AS feb_revenue,
           SUM(revenue) FILTER (WHERE sale_month = DATE '2025-03-01') AS mar_revenue
    FROM sales
    GROUP BY product
)
SELECT w.product, v.sale_month, v.revenue
FROM wide AS w
CROSS JOIN LATERAL (
  VALUES
    (DATE '2025-01-01', w.jan_revenue),
    (DATE '2025-02-01', w.feb_revenue),
    (DATE '2025-03-01', w.mar_revenue)
) AS v(sale_month, revenue)
ORDER BY w.product, v.sale_month;

NULL policy

Decide whether an empty pivot cell means zero observed events, no measurement, or unknown. Those meanings are analytically different. The unpivot step can preserve null cells or explicitly remove them.

Schema design decision

Static categories are easy; dynamic categories change the output schema

Conditional aggregation works best when the desired columns are known: January, February, March; Q1, Q2, Q3; or a stable set of diagnoses. First inspect the categories:

Discover current categories
SELECT DISTINCT diagnosis
FROM admissions
ORDER BY diagnosis;

SELECT DISTINCT product
FROM sales
ORDER BY product;

If categories change often, a long result is usually more robust because new categories become new rows rather than requiring new SQL columns. Application code or a BI tool can generate the presentation matrix at render time.

Optional PostgreSQL feature: the supplied tablefunc extension provides crosstab() for pivot tables, but extension availability and the required output-column definition make it better suited to selected server-side reporting scenarios than to the core pattern taught here.
Static diagnosis columns
SELECT DATE_TRUNC('month', admit_time)::date AS admit_month,
       COUNT(*) FILTER (WHERE diagnosis = 'Pneumonia') AS pneumonia,
       COUNT(*) FILTER (WHERE diagnosis = 'Fracture') AS fracture,
       COUNT(*) FILTER (WHERE diagnosis = 'Flu') AS flu
FROM admissions
GROUP BY 1
ORDER BY 1;

  2. a wide product table with Jan, Feb, and Mar revenue columns for a scorecard.

Assessment and closure

Can you reshape data without changing its meaning?

Recognition

  1. What is the grain of a long product-month revenue table?
  2. Why does a pivot often require an aggregate?
  3. When is NULL preferable to zero in a pivot cell?
  4. How does FILTER differ stylistically from SUM(CASE ...)?
  5. Why can an unpivot require explicit casts?
  6. What information is lost when transaction rows are summed before pivoting?

Applied challenge

Return one row per product with January, February, and March revenue. Preserve NULL when there is no observation for a product-month. Then explain why the result has fewer rows than the source.

Key takeaways

  • Long and wide are shapes, not quality levels.
  • State the output grain before reshaping.
  • Conditional aggregation is the core PostgreSQL pivot pattern taught in this course.
  • FILTER can make category-specific aggregates easier to read.
  • UNION ALL and lateral VALUES are practical unpivot patterns.
  • Aggregation inside a pivot may permanently remove detail.
  • NULL and zero carry different meanings.
  • Validate totals and row counts after reshaping.
  • Prefer long form when categories evolve; use fixed wide schemas for stable reporting needs.
