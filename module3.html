Safe SQL habit

Read the request → preview target rows → execute the smallest correct statement → inspect the result → commit or reset.

Learning Objectives

By the end of this module, you will be able to:

  1. Distinguish data definition, query, manipulation, and transaction-control commands.
  2. Use SELECT to retrieve chosen columns, aliases, and calculated expressions.
  3. Filter rows with comparison, range, membership, pattern, logical, and null predicates.
  4. Organize result sets with DISTINCT, ORDER BY, and LIMIT.
  5. Add, modify, and remove rows with INSERT, UPDATE, and DELETE.
  6. Use RETURNING, stable keys, transactions, and preflight queries to make DML safer.
  7. Explain when MERGE supports synchronization and why its matching condition requires careful testing.
  8. Query JSONB fields and use INSERT INTO ... SELECT as a bridge to data-pipeline workflows.
  9. Run PostgreSQL-compatible SQL in the embedded lab and interpret rows, affected-row counts, and errors.

The Five-Step Execution Workflow

1. DefineState the exact rows and columns needed.
2. PreviewUse SELECT to confirm the target.
3. ProtectUse keys, WHERE, and a transaction.
4. ExecuteRun the smallest correct statement.
5. VerifyInspect RETURNING or query again.

SQL Language Map

Place each command in the data workflow before learning its syntax.

SQL is declarative: you describe the intended result or change, and PostgreSQL chooses an execution plan. Courses often separate SQL into the following working categories.

DDL

Define structure

CREATE, ALTER, DROP, TRUNCATE

Creates and changes database objects.

DQL

Read data

SELECT

Retrieves rows and derives a result set.

DML

Change rows

INSERT, UPDATE, DELETE, MERGE

Adds, modifies, removes, or synchronizes rows.

Transaction control

Accept or undo

BEGIN, COMMIT, ROLLBACK

Defines the all-or-nothing boundary for related changes.

Terminology note: “DQL” is a useful teaching label for retrieval. Some references include SELECT within a broader definition of DML. The important distinction in this module is whether a statement only returns a result or changes stored rows.

From SQL Text to a Result

SQL statement→ Parser→ Planner→ Executor→ Rows or row changes
Connection to Module 2: DDL creates the protected schema. DQL and DML then operate within its data types, keys, checks, and foreign-key rules.

Query Data with SELECT

Choose the columns and expressions that should appear in a result set.

Core Pattern

SELECT result columns FROM source table WHERE row condition ORDER BY sort keys LIMIT row count

Select Chosen Columns

List columns explicitly when you know what the report or analysis requires. This makes the output contract visible and avoids retrieving unused data.

SELECT mrn, full_name, age
FROM patients
ORDER BY age DESC;

Good default

SELECT mrn, full_name, age documents exactly what the query returns.

Use * deliberately

SELECT * is convenient for exploration, but production reports can change unexpectedly when the table schema changes.

Aliases and Calculated Expressions

An alias labels a result column; it does not rename the stored column. Expressions can derive values without modifying the underlying rows.

SELECT mrn,
       full_name AS patient,
       age,
       age >= 65 AS is_senior
FROM patients
ORDER BY age DESC;
Do not estimate birth year as current_year - age for authoritative use. The result can be off by one because it ignores whether the birthday has occurred. Store a birth date when precise age calculations matter.

Filter and Order Result Sets

Use predicates to keep only relevant rows, then make the output deterministic and readable.

Filter by Multiple Conditions

SELECT mrn, full_name, age, gender
FROM patients
WHERE gender = 'Female'
  AND age BETWEEN 30 AND 60
ORDER BY age;

Text Search with ILIKE

LIKE is case-sensitive in PostgreSQL under common collations; ILIKE provides case-insensitive pattern matching.

SELECT mrn, full_name
FROM patients
WHERE full_name ILIKE 'c%';

NULL Requires Its Own Predicate

NULL represents an absent or unknown value. Use IS NULL, not = NULL.

SELECT admission_id, patient_id, diagnosis, admission_date, discharge_date
FROM admissions
WHERE discharge_date IS NULL
ORDER BY admission_date;

Sort, Limit, and Remove Duplicate Result Rows

SELECT admission_id, patient_id, diagnosis, admission_date
FROM admissions
ORDER BY admission_date DESC
LIMIT 3;
SELECT DISTINCT specialty
FROM doctors
ORDER BY specialty;

Simplified Logical Processing Order

SQL is written beginning with SELECT, but the clauses are conceptually resolved in a different order.

1. FROM
2. WHERE
3. SELECT
4. DISTINCT
5. ORDER BY
6. LIMIT

Change Data Safely

Treat every write as a controlled, reviewable operation rather than a one-line shortcut.

The DML Safety Workflow

1PreviewSELECT the target rows.
2IdentifyPrefer a primary or unique key.
3ProtectUse a transaction when appropriate.
4ReturnInspect changed rows with RETURNING.
5VerifyCommit or roll back deliberately.

INSERT: Add Rows

Always name the target columns. PostgreSQL's RETURNING clause immediately shows the stored row, including generated identity values.

INSERT INTO patients (mrn, full_name, age, gender)
VALUES ('MRN1010', 'Ivy Carter', 50, 'Female')
RETURNING patient_id, mrn, full_name, age, gender;

UPDATE: Modify Existing Rows

Run the same predicate in a SELECT first. Use a stable key where possible; names may not be unique and can change.

SELECT patient_id, mrn, full_name, age
FROM patients
WHERE mrn = 'MRN1003';

UPDATE patients
SET age = 35
WHERE mrn = 'MRN1003'
RETURNING patient_id, mrn, full_name, age;

DELETE: Remove Rows Deliberately

A physical delete is appropriate for disposable test rows and some governed retention workflows. Many operational systems instead mark a row inactive so history remains available.

Soft delete

Preserve the row while removing it from active workflows.

UPDATE patients
SET is_active = false
WHERE mrn = 'MRN1004'
RETURNING patient_id, mrn, full_name, is_active;

Hard-delete a disposable row

Create and remove a test row that has no dependent records.

INSERT INTO patients (mrn, full_name, age, gender)
VALUES ('MRN9001', 'Temporary Test', 40, 'Unknown');

DELETE FROM patients
WHERE mrn = 'MRN9001'
RETURNING patient_id, mrn, full_name;

Let Constraints Protect Related Data

David Lee has an admission. The foreign key uses ON DELETE RESTRICT, so deleting the patient directly should fail rather than create an orphan admission.

-- Expected result: a foreign-key error protects related admissions.
DELETE FROM patients
WHERE mrn = 'MRN1004';
Never teach or run an unrestricted bulk write casually: UPDATE patients SET age = age + 1; and DELETE FROM patients; affect every row. Such statements require an explicit, reviewed reason and a recovery plan.

Transactions and MERGE

Group related work into an all-or-nothing unit and synchronize datasets with explicit matching rules.

Transactions: Test Before You Keep the Change

BEGIN opens a transaction. COMMIT makes the work durable; ROLLBACK discards it. The example below changes Carol's age, inspects it, rolls back, and verifies that the original value remains.

BEGIN;

UPDATE patients
SET age = 35
WHERE mrn = 'MRN1003'
RETURNING patient_id, mrn, full_name, age;

SELECT mrn, full_name, age
FROM patients
WHERE mrn = 'MRN1003';

ROLLBACK;

SELECT mrn, full_name, age
FROM patients
WHERE mrn = 'MRN1003';
Correct control flow: A transaction ends when you issue COMMIT or ROLLBACK. Do not place COMMIT after a ROLLBACK as if both could apply to the same transaction.

ACID in One View

Atomicity

The transaction's changes succeed together or are undone together.

Consistency

Constraints and rules must still hold when the transaction completes.

Isolation

Concurrent work is controlled so intermediate states do not corrupt one another.

Durability

Committed changes survive normal failures in a persistent server database.

MERGE compares a source dataset with a target table. A matching row can be updated; a nonmatching row can be inserted. PostgreSQL introduced MERGE in version 15.

The clinic example uses the unique MRN as the match key. It updates Bob Smith and inserts Grace Hall.

DROP TABLE IF EXISTS incoming_patients;

CREATE TEMP TABLE incoming_patients (
    mrn varchar(12),
    full_name varchar(100),
    age smallint,
    gender varchar(20)
);

INSERT INTO incoming_patients VALUES
('MRN1002', 'Bob Smith', 68, 'Male'),
('MRN1007', 'Grace Hall', 55, 'Female');

MERGE INTO patients AS target
USING incoming_patients AS source
ON target.mrn = source.mrn
WHEN MATCHED THEN
    UPDATE SET full_name = source.full_name,
               age = source.age,
               gender = source.gender
WHEN NOT MATCHED THEN
    INSERT (mrn, full_name, age, gender)
    VALUES (source.mrn, source.full_name, source.age, source.gender);

SELECT mrn, full_name, age, gender
FROM patients
WHERE mrn IN ('MRN1002', 'MRN1007')
ORDER BY mrn;
MERGE safety: The ON condition defines identity for the operation. Test the source for duplicates and preview the match logic before changing a production target.

JSONB and Data-Pipeline Patterns

See how PostgreSQL bridges relational tables, semi-structured fields, and repeatable loading steps.

Query JSONB Fields

The ->> operator extracts a JSON value as text. Cast the text when a boolean or numeric comparison is required.

SELECT patient_id,
       note->>'symptom' AS symptom,
       note->>'severity' AS severity,
       (note->>'follow_up')::boolean AS follow_up
FROM clinical_notes
WHERE note->>'severity' IN ('moderate', 'severe')
ORDER BY patient_id;

Load a Derived Table with INSERT INTO ... SELECT

This pattern reads rows from one relation and inserts the query result into another. It appears in staging, ETL/ELT, archive, and reporting workflows.

CREATE TABLE IF NOT EXISTS senior_patients (
    patient_id integer PRIMARY KEY,
    mrn varchar(12) NOT NULL,
    full_name varchar(100) NOT NULL,
    age smallint NOT NULL
);

TRUNCATE senior_patients;

INSERT INTO senior_patients (patient_id, mrn, full_name, age)
SELECT patient_id, mrn, full_name, age
FROM patients
WHERE age >= 65;

SELECT *
FROM senior_patients
ORDER BY age DESC;

In operational systems, DML keeps current rows accurate. In data pipelines, SQL also moves and reshapes data between raw, staging, curated, and reporting layers. Data warehouses rely heavily on aggregation and joins; lakehouse platforms extend familiar SQL patterns to files and table formats.

Modules 4 through 8 develop the aggregation, logic, join, subquery, string, and date skills needed for those workflows. This module focuses on reliable single-table querying and row changes.

Key Takeaways

1. A clear result specification comes before SQL syntax.
2. WHERE is both an analytical filter and a critical safety boundary for DML.
3. Stable keys, RETURNING, and verification queries make row changes reviewable.
4. Transactions let related changes succeed together or be discarded together.
5. Constraints are not obstacles: a rejected write can be evidence that the schema is protecting data integrity.
