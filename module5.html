Reasoning with SQL Logic

Build accurate decision rules with Boolean operators, three-valued logic, NULL-safe expressions, and PostgreSQL CASE.

Essential Question
How can SQL express business rules accurately when conditions overlap and missing values make ordinary comparisons uncertain?

Logic habit

Define the rule → identify possible NULLs → group conditions → order outcomes → test boundaries → inspect excluded rows.

Start Here

Move from simple filters to explainable rules that remain correct when values are missing.

Learning Objectives

By the end of this module, you will be able to:

  1. Compose conditions with AND, OR, and NOT, and use parentheses to make precedence explicit.
  2. Explain SQL's TRUE/FALSE/UNKNOWN model and predict how a WHERE clause treats UNKNOWN.
  3. Test and compare missing values with IS NULL, IS NOT NULL, IS DISTINCT FROM, and Boolean predicates.
  4. Use COALESCE and NULLIF to create fallbacks, normalize blank text, and prevent division by zero.
  5. Build searched and simple CASE expressions with non-overlapping boundaries and meaningful NULL branches.
  6. Combine these tools in a reproducible PostgreSQL workflow and interpret both successful results and errors.

The Six-Step Logic Workflow

1. DefineState the rule in plain language.
2. Inspect NULLsList fields that can be unknown.
3. GroupAdd parentheses around related tests.
4. OrderPut specific CASE branches first.
5. TestInclude edges, blanks, and NULLs.
6. ValidateCompare results with the written rule.

Boolean Logic and Operator Precedence

Combine tests deliberately; do not rely on a reader remembering precedence rules.

AND

Returns TRUE only when every connected condition is TRUE.

Effect: usually narrows a cohort.

OR

Returns TRUE when at least one connected condition is TRUE.

Effect: usually broadens a cohort.

NOT

Negates a Boolean expression, but NOT UNKNOWN remains UNKNOWN.

Effect: excludes a condition only when its truth state is known.

PostgreSQL Precedence

1
NOTEvaluated first among the three logical operators.
2
ANDEvaluated before OR.
3
OREvaluated last.
Parentheses are part of the documentation. Even when the default precedence produces the intended answer, parentheses show which conditions belong to the same business rule and make future edits safer.
PostgreSQL
SELECT patient_id, patient_name, age, diagnosis
FROM patient_case
WHERE active IS TRUE
  AND (age >= 65 OR diagnosis IN ('Diabetes', 'Kidney Disease'))
ORDER BY patient_id;

NULL and SQL's Three-Valued Logic

A condition can be TRUE, FALSE, or UNKNOWN; WHERE retains only TRUE rows.

NULL is a marker for a missing, unknown, or inapplicable value. It is not zero, an empty string, a space, or Boolean FALSE. Because the value is unknown, ordinary comparisons involving NULL normally produce UNKNOWN.

TRUEThe row satisfies the condition.
FALSEThe row does not satisfy the condition.
UNKNOWNThe available data cannot establish TRUE or FALSE.
Selected three-valued logic outcomes
ExpressionResultReason
TRUE AND UNKNOWNUNKNOWNThe unknown side could still be FALSE.
FALSE AND UNKNOWNFALSEOne FALSE is enough to make the conjunction false.
TRUE OR UNKNOWNTRUEOne TRUE is enough to make the disjunction true.
FALSE OR UNKNOWNUNKNOWNThe unknown side could still be TRUE.
NOT UNKNOWNUNKNOWNNegating an unknown state does not reveal its value.

Incorrect

WHERE email_address = NULL

The comparison is UNKNOWN for every row, including rows whose email is NULL.

Correct

WHERE email_address IS NULL

IS NULL performs an explicit missing-value test and returns TRUE or FALSE.

NULL-Handling Tools

Choose the tool that matches the task: test, compare, substitute, or normalize.

Normalize Before Falling Back

A blank string is a real string in PostgreSQL. Combining BTRIM, NULLIF, and COALESCE lets the query treat empty and whitespace-only contact fields as unavailable before selecting a fallback.

PostgreSQL
SELECT patient_id,
       patient_name,
       COALESCE(
           NULLIF(BTRIM(email_address), ''),
           NULLIF(BTRIM(mobile_phone), ''),
           NULLIF(BTRIM(home_phone), ''),
           'No contact provided'
       ) AS preferred_contact
FROM patient_info
ORDER BY patient_id;
Do not substitute blindly. COALESCE(bill_amount, 0) asserts that a missing bill means zero. That may be appropriate in one workflow and seriously misleading in another. The fallback should reflect a documented domain rule.

NULLIF for Safe Ratios

NULLIF(bill_amount, 0) turns a zero denominator into NULL, allowing the ratio to return NULL instead of raising a division-by-zero error. The result means “not computable,” which is different from zero percent.

Conditional Transformation with CASE

Translate ordered business rules into derived labels without modifying stored values.

1. EvaluateCheck WHEN clauses from top to bottom.
2. StopUse the first condition that is TRUE.
3. ReturnProduce its THEN expression.
4. DefaultUse ELSE, or NULL when ELSE is absent.

Searched CASE

Each WHEN contains a complete Boolean condition. Use it for ranges, compound rules, and NULL tests.

CASE WHEN condition THEN result ... END

Simple CASE

One expression is compared with a list of exact values. Use it for direct code-to-label mappings.

CASE expression WHEN value THEN result ... END

Boundary-Safe Billing Tiers

Test missing values first, then arrange numeric thresholds from most specific or highest to lowest. This avoids treating an unknown bill as low value and keeps interval boundaries unambiguous.

PostgreSQL
SELECT patient_id,
       bill_amount,
       CASE
           WHEN bill_amount IS NULL THEN 'Unknown'
           WHEN bill_amount >= 10000 THEN 'High-Value'
           WHEN bill_amount >= 5000 THEN 'Standard'
           ELSE 'Low-Value'
       END AS billing_tier
FROM patient_billing
ORDER BY patient_id;
First match wins. If WHEN age >= 18 appears before WHEN age >= 65, every senior matches the adult branch and the senior branch can never run.

Reusable Patterns and Common Traps

Most logic bugs are syntactically valid; they return the wrong cohort without raising an error.

Logic mistakes that PostgreSQL may execute successfully
TrapWhy it failsSafer pattern
a OR b AND cAND binds before OR, which may not match the prose rule.(a OR b) AND c when that is the intended grouping.
column = NULLThe comparison is UNKNOWN, not TRUE.column IS NULL.
value NOT IN (..., NULL)Non-matches can become UNKNOWN because one list comparison is unknown.Remove NULLs from the list and handle missing values explicitly.
status <> 'Paid'Rows with NULL status are excluded as UNKNOWN.status IS DISTINCT FROM 'Paid' when NULL should count as different.
Broad CASE branch before a narrow branchThe narrow branch becomes unreachable.Order the most specific conditions first.
ELSE 'Low' for nullable measuresUnknown values are silently reclassified as low.Add an explicit WHEN measure IS NULL branch.

NOT IN with NULL

Because no ordinary value can be proven different from an unknown list element, the predicate can return UNKNOWN for every apparent non-match.

NULL-Safe Inequality

IS DISTINCT FROM supplies a definite TRUE/FALSE answer and can intentionally include rows whose status is missing.

Applied Clinic Workflow

Combine Boolean grouping, explicit NULL policy, and ordered CASE outcomes in reproducible reports.

Case 1: High-Risk Outreach with Missing Email

Rule: include active patients who explicitly consented, have Diabetes or Kidney Disease, and lack a usable email address. UNKNOWN consent is not the same as consent.

PostgreSQL
SELECT patient_id,
       patient_name,
       diagnosis,
       consent_to_contact,
       email_address
FROM patient_case
WHERE active IS TRUE
  AND consent_to_contact IS TRUE
  AND diagnosis IN ('Diabetes', 'Kidney Disease')
  AND NULLIF(BTRIM(email_address), '') IS NULL
ORDER BY patient_id;

Case 2: Standardized Billing Output

Rule: select the first usable contact method and classify the bill, but preserve missing bills as “Needs review.” This separates presentation defaults from data-quality meaning.

Case 3: Length-of-Stay Categories

PostgreSQL subtracts one date from another to return an integer number of days. Because the task concerns completed stays, filter out rows without a discharge date before calculating the category.

PostgreSQL
SELECT admission_id,
       patient_id,
       admission_date,
       discharge_date,
       discharge_date - admission_date AS length_of_stay_days,
       CASE
           WHEN discharge_date - admission_date < 5 THEN 'Short'
           WHEN discharge_date - admission_date <= 10 THEN 'Medium'
           ELSE 'Long'
       END AS stay_category
FROM admissions
WHERE discharge_date IS NOT NULL
ORDER BY admission_id;

Assessment Tasks

  3. SQL coding: Using admissions, calculate each completed admission's length of stay in days and categorize it as Short (< 5 days), Medium (5–10 days), or Long (> 10 days). Exclude rows without a discharge date.
  4. Application scenario: Using August 11, 2026 as the reproducible report date, return admissions from the preceding 30 days with a Pneumonia or Flu diagnosis. Show the patient's name and age and create a diagnosis category that distinguishes high-risk respiratory cases from other respiratory cases.
  5. NULL-aware filtering: Return active patients with no usable email, but exclude anyone whose consent is explicitly FALSE. Preserve UNKNOWN consent for review.
  6. Applied rule: Complete the outreach-priority starter. Your CASE must distinguish inactive or explicit refusal, urgent outreach, routine outreach, and records requiring review.

Concept: NULL represents missing or unknown data, whereas '' is a known zero-length text value. Test them with IS NULL and = '', respectively. NULLIF(BTRIM(column_name), '') converts empty or whitespace-only text to NULL for consistent handling.

Prediction: TRUE AND UNKNOWN is UNKNOWN; FALSE OR UNKNOWN remains UNKNOWN. Because WHERE keeps only TRUE, the row is excluded.

Recent Respiratory Report Solution

PostgreSQL
SELECT a.admission_id,
       p.patient_name,
       p.age,
       a.admission_date,
       a.diagnosis,
       CASE
           WHEN a.diagnosis IN ('Pneumonia', 'Flu')
                AND p.age >= 60
               THEN 'High-Risk Respiratory'
           WHEN a.diagnosis IN ('Pneumonia', 'Flu')
               THEN 'Respiratory'
           ELSE 'Other'
       END AS diagnosis_category
FROM admissions AS a
JOIN patient_info AS p USING (patient_id)
WHERE a.admission_date BETWEEN DATE '2026-08-11' - 30
                           AND DATE '2026-08-11'
  AND a.diagnosis IN ('Pneumonia', 'Flu')
ORDER BY a.admission_date;

Outreach-Priority Solution

PostgreSQL
SELECT patient_id,
       patient_name,
       active,
       consent_to_contact,
       severity,
       email_address,
       CASE
           WHEN active IS FALSE OR consent_to_contact IS FALSE
               THEN 'Do not contact'
           WHEN active IS TRUE
                AND consent_to_contact IS TRUE
                AND severity = 'High'
                AND NULLIF(BTRIM(email_address), '') IS NULL
               THEN 'Urgent'
           WHEN active IS TRUE
                AND consent_to_contact IS TRUE
               THEN 'Routine'
           ELSE 'Review'
       END AS outreach_priority
FROM patient_case
ORDER BY patient_id;

Key Takeaways

UNKNOWN is a real logic state.

WHERE excludes FALSE and UNKNOWN, so missing data can silently change a cohort.

Parentheses communicate intent.

They protect mixed AND/OR rules from precedence mistakes and later edits.

Fallbacks encode assumptions.

Use COALESCE only when the substitute has a defensible domain meaning.

CASE is ordered.

The first TRUE branch wins; test NULL and narrow conditions deliberately.

Glossary

Boolean expression

An expression evaluated as TRUE, FALSE, or UNKNOWN.

UNKNOWN

The truth state produced when available values cannot establish TRUE or FALSE.

NULL-safe comparison

A comparison such as IS DISTINCT FROM that always returns TRUE or FALSE.

Searched CASE

A CASE expression whose WHEN clauses contain complete conditions.
