Slide 1: Big picture

Welcome to Module 6, Joining Data in PostgreSQL. Up to this point, we have often worked with one table at a time. Real analytical questions usually require information that is stored across several related tables.

[pause=0.7]

In this module, the important question is not simply, how do I write a JOIN? The more important question is, what should one output row represent, which rows must remain even when no match exists, and can either side match more than once?

[pause=0.7]

We will work with INNER, LEFT, RIGHT, and FULL OUTER joins. We will also compare ON and WHERE, use self joins and cross joins, and spend extra time on cardinality because row multiplication is one of the most common causes of incorrect analytical results.

[pause=0.7]

As you work through the examples, run the SQL directly in the browser. On code slides, you can also use Copy and paste the same query into the pgAdmin Query Tool. The goal is to learn a repeatable reasoning process, not only join syntax.

[pause=1.0]

Slide 2: Learning objectives

By the end of this module, you should be able to choose a join type based on the question rather than by habit. You should be able to explain what rows are preserved, what rows require a match, and where NULL values can appear after an outer join.

[pause=0.7]

You will also practice writing explicit join conditions with table aliases. When two tables contain a column with the same name, aliases make it clear which table the column comes from.

[pause=0.7]

A major learning goal is protecting the grain. Grain means what one row in the result represents. A patient table may have one row per patient, while an admissions table may have several rows for the same patient. When those tables are joined, repeated patient rows may be completely correct.

[pause=0.7]

Finally, you should be able to validate a join. A query running without an error does not prove that the result is analytically correct. We will check counts, distinct identifiers, unmatched rows, and a few known records.

[pause=1.0]

Slide 3: Join decision workflow

Here is the workflow we will use throughout Module 6.

[pause=0.7]

First, define the grain. Ask what one output row should mean. One patient? One admission? One lab test? One department?

[pause=0.7]

Second, identify the two row sets you are combining. Third, define the matching rule. Most often that is a key such as patient ID, but sometimes the relationship uses another identifier.

[pause=0.7]

Fourth, decide which unmatched rows must remain. If every patient must remain even when that patient has no admission, that immediately points toward a LEFT JOIN with patients on the left.

[pause=0.7]

Fifth, predict cardinality. Can one patient match several admissions? Can one patient also match several labs? This prediction tells you whether rows may expand.

[pause=0.7]

Finally, validate. Compare the actual result with the number and type of rows you expected. This reasoning sequence is much safer than starting by typing JOIN and hoping the result looks reasonable.

[pause=1.0]

Slide 4: Practice schema

The examples use a small synthetic healthcare database. The patients table has one row per patient. Admissions, lab results, and prescriptions are child tables, so one patient can have zero, one, or many rows in each of those tables.

[pause=0.7]

Medical staff belongs to departments, and admissions can point to an attending staff member. This gives us several realistic join paths.

[pause=0.7]

The data also includes useful edge cases. At least one patient has no admission or lab activity, and the staging table contains a patient ID that does not exist in the patient master table. Those records help us see what outer joins preserve.

[pause=0.7]

Keep the relationships in mind while reading every query. If the patients table contains one row per patient but admissions contains many rows per patient, a patient-to-admission join naturally changes the grain from patient to admission detail. That is not automatically a duplicate problem. It is a consequence of the relationship.

Slide 5: Join mental model

A useful way to understand joins is to separate matching from preservation.

[pause=0.7]

The ON condition decides whether a row from one table matches a row from another table. For example, an admission matches a patient when the patient IDs are equal.

[pause=0.7]

The join type answers a different question. If no match exists, should that unmatched row disappear, or should it remain with NULL values from the missing side?

[pause=0.7]

This distinction helps explain why the same ON condition can produce different outputs under INNER JOIN and LEFT JOIN.

[pause=0.7]

Also remember that SQL joins combine rows, not just unique IDs. If one patient has two admissions, there are two valid patient-admission combinations. The patient information will appear on both result rows because the grain is now admission detail.

[pause=0.7]

Before moving on, try to explain a join in plain language: compare these two row sets, match them using this rule, and preserve these unmatched rows.

[pause=1.0]

Slide 6: Row preservation map

This slide gives the four main row-preservation patterns.

[pause=0.7]

INNER JOIN keeps only row combinations where the match condition is true. If a patient has no admission, that patient is absent from a patient-to-admission INNER JOIN.

[pause=0.7]

LEFT JOIN keeps every row from the left table. When no right-side match exists, right-side columns become NULL.

[pause=0.7]

RIGHT JOIN is the mirror image. Every row from the right table is preserved, and unmatched left-side columns become NULL.

[pause=0.7]

FULL OUTER JOIN preserves unmatched rows from both sides. This is especially useful when reconciling a master table with an external staging source.

[pause=0.7]

Do not memorize these as shapes only. Read them as population rules. Ask, what population must remain complete? If the answer is all patients, put patients on the preserved side. That simple question often makes the join choice much easier.

[pause=1.0]

Slide 8: Aliases and grain

Aliases and grain solve two different kinds of confusion.

[pause=0.7]

Aliases make the SQL easier to read. Both patients and admissions contain patient ID. Writing p dot patient ID and a dot patient ID tells us exactly which table a column comes from. This becomes even more important when a query joins three or four tables.

[pause=0.7]

Grain helps us interpret repeated values. Suppose Alice has two admissions. Her patient name may appear on two rows after the join. That does not mean the join is wrong. It means the result is at admission grain.

[pause=0.7]

When you see repeated information after a join, do not immediately apply DISTINCT. First ask whether those rows represent different valid events. DISTINCT can hide a modeling problem instead of fixing it.

[pause=0.7]

A good habit is to write a short sentence before the query: one row in this result represents one admission with patient information. That sentence becomes your validation target.

[pause=1.0]

Slide 9: LEFT JOIN

A LEFT JOIN is often the most useful outer join in analytics because it lets us preserve a clearly defined population.

[pause=0.7]

Here, patients is on the left. That means every patient should remain in the output, even if no admission exists.

[pause=0.7]

Run the query. Look for a patient whose admission ID is missing. That NULL does not mean the join failed. It is the expected representation of an unmatched right-side row.

[pause=0.7]

Now compare this result mentally with the INNER JOIN from the previous slide. The ON condition is the same. The difference is preservation. INNER JOIN removes unmatched patients. LEFT JOIN keeps them.

[pause=0.7]

This distinction matters whenever your denominator is all customers, all students, all patients, or all products. If you accidentally use INNER JOIN, entities with no activity may disappear and your analysis can become biased.

[pause=0.7]

We begin with a LEFT JOIN because we want to preserve every patient. When a patient has no lab result, columns from lab results are NULL. We then filter for a right-side key, test ID, being NULL.

Slide 11: RIGHT JOIN

RIGHT JOIN is valid PostgreSQL syntax and it preserves every row from the right table.

[pause=0.7]

In this example, departments is on the right, so every department remains even if no medical staff member belongs to it. For an unmatched department, the staff columns will be NULL.

[pause=0.7]

Run the query and look for the department with no staff. That row demonstrates why the RIGHT JOIN was used.

[pause=0.7]

In practice, many analysts prefer LEFT JOIN because it reads naturally from left to right: put the population you want to preserve first, then join optional information to it. The same logic could be rewritten by placing departments first and using LEFT JOIN to medical staff.

[pause=0.7]

The important goal is not preferring one keyword. The important goal is making the preserved population obvious to the next person who reads the query.

FULL OUTER JOIN is especially helpful for reconciliation.

[pause=0.7]

The patient master contains official patient rows, while the staging table represents imported data that may not be fully validated. We want to see matches, master records with no staging row, and staging rows with no master record.

[pause=0.7]

When you use FULL OUTER JOIN, be deliberate about keys in the SELECT and ORDER BY clauses. COALESCE is useful here because the patient ID may come from either side when one side is unmatched.

Slide 13: Outer join comparison

Join selection becomes easier when you translate the business question into a preservation rule.

[pause=0.7]

If the question is only about patients who have admissions, requiring a match is appropriate, so INNER JOIN fits.

[pause=0.7]

If the question says every patient, whether or not an admission exists, then the patient population must be preserved. Put patients on the left and use LEFT JOIN.

[pause=0.7]

If the question says every department, including empty departments, preserve departments. You can do that with RIGHT JOIN as written in the earlier example, or more commonly by moving departments to the left and using LEFT JOIN.

[pause=0.7]

If you need to compare two sources and see unmatched rows from both, FULL OUTER JOIN is a natural choice.

[pause=0.7]

Notice that we are choosing the join from the words every, only matched, and unmatched from both sides. That is much more reliable than choosing a join because it is the one you remember best.

[pause=1.0]

Slide 14: ON vs WHERE

This is one of the most important slides in the module.

[pause=0.7]

ON and WHERE are not interchangeable in an outer join.

[pause=0.7]

The ON condition defines matching. If we put a condition about lab test name inside ON, we are saying only glucose lab rows are eligible to match each patient. Patients without glucose results can still remain because the LEFT JOIN preserves them.

[pause=0.7]

WHERE is evaluated on the joined result. If we filter where the right-side lab test name equals Glucose, unmatched patients have NULL on that right-side column. NULL does not satisfy the equality condition, so those patients are removed.

[pause=0.7]

That means a LEFT JOIN followed by the wrong WHERE condition can behave like an INNER JOIN for that part of the logic.

[pause=0.7]

A useful question is: does this condition describe which right-side rows may match, or does it describe which final result rows I want to keep?

[pause=1.0]

Slide 16: WHERE trap

This query looks very similar to the previous one, but the meaning changes because the glucose condition moved from ON to WHERE.

[pause=0.7]

The LEFT JOIN first preserves patients and creates NULL-extended lab columns for patients with no matching lab row. Then WHERE asks whether the lab test name equals Glucose.

[pause=0.7]

For unmatched patients, the test name is NULL. That condition is not true, so those rows are filtered out.

[pause=0.7]

Run this query and compare the row count with the previous slide. You should see only patients who actually have glucose tests.

[pause=0.7]

This is a common source of bugs because the SQL still runs successfully. There is no syntax error to warn you.

[pause=0.7]

A strong debugging method is to run both versions side by side and ask which population the business question requires. If the requirement says all patients, the previous ON-filter version is the appropriate pattern.

Slide 17: USING

PostgreSQL offers USING as a convenient alternative to ON when both tables share the same join-key name.

[pause=0.7]

In this query, both patients and admissions contain patient ID. Writing USING patient ID tells PostgreSQL to match the columns with that name and return a single join-key column in the result.

[pause=0.7]

Run the query and compare its result with the earlier INNER JOIN. The relationship is the same.

[pause=0.7]

USING can make a simple join shorter and easier to read, but ON is more flexible. Use ON when the key names differ, when you need more than one matching condition, or when the relationship uses an expression.

[pause=0.7]

The goal is clarity. Do not force USING into a query when it makes the relationship less obvious. Whichever syntax you choose, you should still be able to explain the matching rule in one sentence.

Slide 18: SELF JOIN

A self join is not a special JOIN keyword. It is a regular join where the same table is referenced twice with different aliases.

[pause=0.7]

Here, medical staff is called s one on one side and s two on the other. We match rows that belong to the same department.

[pause=0.7]

The second condition, staff ID from s one is less than staff ID from s two, is very important. Without it, we could produce both Alice-Bob and Bob-Alice, and we could even match a row to itself.

[pause=0.7]

Slide 20: CROSS JOIN

CROSS JOIN intentionally creates every possible pair between two row sets.

[pause=0.7]

In this example, we combine selected departments with appointment slots. If we have two departments and three time slots, we expect six combinations.

[pause=0.7]

Run the query and verify that each selected department appears once for each slot.

[pause=0.7]

CROSS JOIN is useful for generating scenario grids, schedules, calendars, test cases, or completeness frameworks. But it must be used deliberately.

[pause=0.7]

Unlike an ordinary join, there is no ON condition restricting matches. That means result size can grow very quickly.

[pause=0.7]

Before running a cross join on large tables, estimate the number of combinations. Multiply the left row count by the right row count. If one side has ten thousand rows and the other has ten thousand rows, the result can reach one hundred million combinations before any later filtering.

[pause=1.0]

Slide 21: Cross join growth

Cross joins make cardinality especially visible because the multiplication is direct.

[pause=0.7]

Two rows crossed with three rows create six result rows. One hundred by one hundred creates ten thousand. Ten thousand by ten thousand creates one hundred million.

[pause=0.7]

This does not mean CROSS JOIN is bad. It means the result size should be intentional.

[pause=0.7]

For example, building every department and every appointment slot can be exactly what you need to find missing schedule assignments. But crossing two large transaction tables would usually be a serious mistake.

[pause=0.7]

The same multiplication idea appears less obviously in ordinary joins when both sides can have several matches for the same key. That is why understanding cardinality is essential before we move into multi-table analytical joins.

[pause=0.7]

Whenever a result suddenly contains far more rows than expected, ask whether you have accidentally created combinations between multiple detail rows.

[pause=1.0]

Slide 22: Cardinality

Cardinality describes how many rows can match a key.

[pause=0.7]

A one-to-one join is simple because each key can match at most once on both sides.

[pause=0.7]

In a one-to-many join, one patient can match several admissions. The patient row repeats once for each matching admission. That is normal and often exactly what we want.

[pause=0.7]

The danger appears when we join several one-to-many child tables at the same time using only the parent key. Suppose one patient has two admissions, two lab tests, and two prescriptions. The join can create two times two times two, or eight, combinations.

[pause=0.7]

Those eight rows are not eight new business events. They are combinations of existing detail rows.

[pause=0.7]

Before you aggregate a multi-table join, predict this behavior. If your target output is one row per patient, consider summarizing each child table to patient grain first.

[pause=1.0]

Slide 23: Row multiplication

This runnable example makes row multiplication visible.

[pause=0.7]

We join patients to admissions, lab results, and prescriptions, all by patient ID. Each of those child tables can contain multiple rows for one patient.

[pause=0.7]

Run the query and focus on a patient with multiple records in several child tables. The joined row count can be much larger than the individual event counts.

[pause=0.7]

Notice the use of COUNT DISTINCT for admission ID, test ID, and prescription ID. Those distinct counts recover the number of original events, while COUNT star counts the combinations created by the join.

[pause=0.7]

This is why COUNT star after a multi-child join can be misleading. It may be counting the shape of the join rather than the business events you intended to measure.

[pause=0.7]

The first question after seeing an unexpectedly large count should be: what is the grain of the joined rows, and which relationships are multiplying one another?

[pause=1.0]

Slide 24: COUNT trap

COUNT star is not wrong. It counts rows exactly as requested. The problem is that the joined row may not represent the event you think it represents.

[pause=0.7]

After joining several one-to-many tables, one row can represent a combination of an admission, a lab test, and a prescription. Counting those rows does not directly count any one of those event types.

[pause=0.7]

COUNT DISTINCT on an event identifier can protect a simple count. For example, counting distinct admission IDs can recover admission count even after other detail tables are joined.

[pause=0.7]

However, pre-aggregating is often easier to reason about when the final grain is one row per patient. You can summarize admissions to one patient row, summarize labs to one patient row, and then join those summaries.

[pause=0.7]

The safest approach is to name the measure explicitly: admissions, lab tests, prescriptions, patients, or joined combinations. Then choose the counting method that matches that meaning.

[pause=1.0]

Slide 26: Validation checklist

A join should be validated before its result is used for reporting or analysis.

[pause=0.7]

Start with row counts. How many rows were in each input, and how many rows are in the output?

[pause=0.7]

Then count distinct keys. If the final grain should be one row per patient, compare total rows with distinct patient IDs. If those numbers differ, investigate why.

[pause=0.7]

Inspect keys with unusually many matches. A patient with many admissions or labs is useful for understanding whether multiplication is expected.

[pause=0.7]

Also spot-check at least two known cases: one entity with multiple related rows and one entity with no related row.

[pause=0.7]

Finally, write the grain sentence. For example: one row represents one patient with summarized activity counts. If the query output cannot be explained with a clear grain sentence, the join logic may still be ambiguous.

[pause=0.7]

These checks are simple, but they catch a large share of real-world join errors.

Slide 28: Protect target grain

A correct join key must match the level of the relationship.

[pause=0.7]

Suppose your target result is one row per admission. You already have patients joined to admissions correctly.

[pause=0.7]

Now imagine adding lab results by patient ID only. If that patient has several admissions and several lab tests, every admission can pair with every lab for that patient. The admission grain is destroyed.

[pause=0.7]

The deeper question is whether a lab belongs to the patient generally, to one admission, or to a more specific encounter. The database design should tell you.

[pause=0.7]

This is why knowing that two tables both contain patient ID is not enough evidence that joining them only on patient ID is analytically correct.

[pause=0.7]

Before adding another table, restate the target grain and ask whether the new table is at the same level. If not, aggregate it, filter it, or use a more specific relationship key.

Slide 34: Assessment concepts

Before the coding exercises, check whether you can explain the core ideas in your own words.

[pause=0.7]

First, why can a LEFT JOIN followed by a WHERE condition on the right table remove unmatched left rows? Your explanation should mention NULL-extended values and final filtering.

[pause=0.7]

Second, can you choose the join type from the population rule? Only matched records points toward INNER. Every patient points toward LEFT when patients are on the left. Full reconciliation points toward FULL OUTER.

[pause=0.7]

Third, can you explain row multiplication without calling the extra rows duplicates? Multiple admissions, labs, and prescriptions create combinations when joined at patient ID.

[pause=0.7]

Finally, can you design a one-row-per-patient result without inflated counts? The safe pattern is to summarize each child table to patient grain before joining it to the patient master.

Slide 35: Assessment coding strategy

The requirement is one row per patient with admission count, lab count, and prescription count. We must also preserve patients with no activity.

[pause=0.7]

Slide 43: Summary

Let's summarize the major ideas from Module 6.

[pause=0.7]

Start with grain. Decide what one result row should represent before writing a join.

[pause=0.7]

Then choose preservation. INNER JOIN keeps only matches. LEFT and RIGHT preserve one designated side. FULL OUTER JOIN preserves unmatched rows from both sources.

[pause=0.7]

Remember that ON controls matching, while WHERE filters the joined result. This distinction is especially important with outer joins.

[pause=0.7]

Cardinality explains why rows repeat or multiply. One-to-many repetition can be completely correct, but several one-to-many child tables joined together can create combinations that inflate counts.

[pause=0.7]

When your target is one row per patient or one row per department, pre-aggregating child tables is often the clearest solution.

[pause=0.7]

Finally, validate. Compare row counts, distinct keys, unmatched cases, and known examples.

[pause=0.7]

If you keep one habit from this module, let it be this: define the grain, predict the matches, run the join, and verify the result before trusting it.
