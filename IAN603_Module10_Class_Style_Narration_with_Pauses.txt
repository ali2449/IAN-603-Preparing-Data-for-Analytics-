Slide 1: Start

Welcome to Module 10, Reshaping Data in PostgreSQL.

[pause=0.7]

Reshaping changes structure, not the underlying facts.

[pause=0.7]

We will move between long and wide forms, pivot categories into columns, unpivot columns back into rows, preserve meaningful NULL values, and protect the intended analytical grain.

[pause=0.7]

The most important habit in this module is to say what one output row represents before you write the reshape query.

[pause=1.0]

Slide 2: Reshaping changes structure

Long and wide are not quality levels.

[pause=0.7]

They are different ways to arrange information.

[pause=0.7]

Long data usually stores categories as row values.

[pause=0.7]

Wide data turns selected category values into columns.

[pause=0.7]

The dangerous part is that many pivots also aggregate.

[pause=0.7]

When several source rows map to one pivot cell, detail may be permanently removed.

[pause=1.0]

Slide 3: Learning goals

By the end of this module, you should be able to identify long and wide structures, pivot and unpivot data in PostgreSQL, and explain the grain of each result.

[pause=0.7]

You should also be able to detect when a reshape changes more than structure because aggregation or a join has altered the facts.

[pause=0.7]

Finally, you should be able to choose a shape based on what happens next: visualization, reporting, or modeling.

[pause=1.0]

Slide 6: Long form

In long form, the month is stored as a value in a column.

[pause=0.7]

Laptop January and Laptop February occupy different rows.

[pause=0.7]

This shape is flexible because a new month can simply become another row.

[pause=0.7]

Long form is common for time-series analysis, plotting, grouping, and tidy analytical workflows.

[pause=1.0]

Slide 7: Wide form

In wide form, January and February are separate columns.

[pause=0.7]

Now one row represents a product rather than a product-month.

[pause=0.7]

This can be convenient for scorecards, matrices, and fixed reports.

[pause=0.7]

The same business relationship is being displayed differently, but the row grain has changed.

[pause=1.0]

Slide 8: Same facts, different shape

These two tables represent the same simplified information.

[pause=0.7]

The long table has one product-month per row.

[pause=0.7]

The wide table has one product per row.

[pause=0.7]

Before reshaping, state both grains clearly.

[pause=0.7]

That makes it easier to identify what has changed and whether any information has been aggregated away.

Slide 9: What is grain?

Grain means what one row represents.

[pause=0.7]

A sales fact table may have one row per transaction.

[pause=0.7]

After grouping, the grain may become one product-month.

[pause=0.7]

After pivoting months into columns, the grain may become one product.

[pause=0.7]

If you cannot state the row grain, it is difficult to know whether a reshape is correct.

[pause=1.0]

Slide 10: State grain before SQL

Before writing a pivot, complete one sentence: one output row represents what?

[pause=0.7]

Once the row meaning is clear, identify which category values should become columns.

[pause=0.7]

Then identify the measure that belongs in each cell.

[pause=0.7]

Finally ask whether several source rows can map to the same cell.

[pause=0.7]

If they can, you need an aggregation rule.

[pause=1.0]

Slide 11: Prefer long form when

Long form is often the more flexible analytical shape.

[pause=0.7]

If categories change frequently, new values simply appear in rows.

[pause=0.7]

Long form also works naturally with trend charts, filtering, grouping, and many modeling workflows.

[pause=0.7]

It avoids changing the schema every time a new category appears.

[pause=1.0]

Slide 12: Prefer wide form when

Wide form is useful when categories are stable and users want side-by-side comparison.

[pause=0.7]

A scorecard with January, February, and March columns is easy to scan.

[pause=0.7]

A grade matrix can place courses in fixed columns.

[pause=0.7]

But wide schemas become harder to maintain when categories change frequently.

[pause=1.0]

Slide 13: Reshaping is not always only reshaping

A pivot often requires aggregation.

[pause=0.7]

If only one source row maps to each output cell, the reshape can preserve that value directly.

[pause=0.7]

But if multiple source rows map to one cell, PostgreSQL needs an aggregate such as SUM, COUNT, MAX, or AVG.

[pause=0.7]

That aggregation changes the level of detail, so it must be chosen deliberately.

[pause=1.0]

Slide 15: Pivot mental model

A pivot can be planned with four decisions.

[pause=0.7]

First, define the output row grain.

[pause=0.7]

Second, identify the category values that should become columns.

[pause=0.7]

Third, choose the measure.

[pause=0.7]

Fourth, choose the aggregate needed to fill each cell.

[pause=0.7]

For the diagnosis example, one output row is one month, the categories are diagnoses, and the measure is admission count.

[pause=1.0]

Slide 16: Conditional aggregation

PostgreSQL does not require a special PIVOT keyword for the core patterns taught here.

[pause=0.7]

You can use conditional aggregation.

[pause=0.7]

One common form is SUM with CASE.

[pause=0.7]

PostgreSQL also supports FILTER on aggregate functions, which can be very readable.

[pause=0.7]

Both approaches use the same underlying idea: one grouped output row with category-specific aggregate columns.

[pause=1.0]

Slide 18: Read the CASE pivot

In the CASE pivot, each output measure has a different condition.

[pause=0.7]

The GROUP BY defines one output row per month.

[pause=0.7]

Inside that month, each SUM looks only at rows belonging to its diagnosis category.

[pause=0.7]

Slide 19: Pivot with FILTER

PostgreSQL FILTER attaches a condition directly to an aggregate.

[pause=0.7]

[pause=0.7]

The query is often easier to scan because the aggregate and its condition appear together.

[pause=0.8]

[pause=0.8]

The output should express the same business meaning.

[pause=1.0]

Slide 20: CASE vs FILTER

CASE and FILTER are two styles for conditional aggregation.

[pause=0.7]

CASE is broadly portable and flexible.

[pause=0.7]

FILTER is particularly readable in PostgreSQL when you want category-specific counts or sums.

[pause=0.7]

Choose the form that is clear for the environment you are using.

[pause=0.7]

The output grain and aggregate meaning matter more than the stylistic choice.

[pause=1.0]

Slide 23: NULL and zero are different

An empty pivot cell should not automatically become zero.

[pause=0.7]

NULL may mean no observation was recorded.

[pause=0.7]

Zero may mean the observation exists and its measured value is zero.

[pause=0.7]

Those are different facts.

[pause=0.7]

Before using ELSE zero or COALESCE, decide what an absent source row means for the analytical question.

[pause=1.0]

Slide 25: Validate pivot totals

Slide 27: Unpivot mental model

Unpivoting converts repeated measure columns into rows.

[pause=0.7]

The wide source has one product row with several month columns.

[pause=0.7]

The long result will have a month column and a revenue column.

[pause=0.7]

Slide 28: Method 1: UNION ALL

UNION ALL is a straightforward unpivot pattern.

[pause=0.7]

Write one SELECT for each source column.

[pause=0.7]

Give each SELECT the same output structure.

[pause=0.7]

Then stack the rows with UNION ALL.

[pause=0.7]

This is verbose but very beginner-friendly because each source column is visible in its own SELECT.

[pause=1.0]

Slide 30: Method 2: LATERAL VALUES

PostgreSQL offers a compact unpivot pattern with CROSS JOIN LATERAL and VALUES.

For each monthly sales row, VALUES creates several month-revenue pairs.

[pause=0.7]

[pause=0.7]

This is often cleaner than repeating full SELECT statements.

Slide 32: UNION ALL vs LATERAL

Both methods are useful.

[pause=0.7]

UNION ALL is explicit and easy to read when there are only a few columns.

[pause=0.7]

LATERAL VALUES is compact when many columns follow the same repeated structure.

[pause=0.7]

The correct choice is the one that keeps the transformation clear and maintainable.

Slide 34: Common type requirement

Slide 35: Preserve or drop NULL cells

Unpivoting raises a NULL-policy question.

[pause=0.7]

You can preserve rows whose value is NULL.

[pause=0.7]

That keeps the category present and marks the measurement missing.

[pause=0.7]

Or you can drop NULL rows after unpivoting.

[pause=0.7]

The right choice depends on whether missingness itself matters to the analysis.

[pause=1.0]

Slide 37: Round trip

A reshape round trip is not automatically reversible.

[pause=0.7]

If the pivot aggregated transaction rows to monthly totals, unpivoting can only recover those monthly totals.

[pause=0.7]

It cannot recreate the original transaction IDs or individual amounts.

[pause=0.7]

The grain that survives is the aggregated grain.

[pause=1.0]

Slide 38: Round-trip SQL

This query first creates a wide product-level table with month totals.

[pause=0.8]

Then it unpivots the wide columns into product-month rows.

[pause=0.7]

The result is long again, but it is not the original transaction table.

[pause=0.7]

It is one row per product-month total.

[pause=0.7]

That is the key distinction between reshaping and recovering detail.

[pause=1.0]

Slide 39: Reversible vs lossy

A reshape is more reversible when each source value maps cleanly to one output cell and category labels are preserved.

[pause=0.7]

It becomes lossy when several rows are aggregated into one cell.

[pause=0.7]

Dropping NULL rows can also remove missingness information.

[pause=0.7]

Collapsing categories can remove distinctions.

[pause=0.7]

Always identify which information survives the transformation.

[pause=1.0]

Slide 40: Grain is the safeguard

The seeded sales table intentionally contains multiple Laptop transactions in January.

[pause=0.7]

A product by month pivot has only one Laptop January cell.

[pause=0.7]

That means the two transaction rows must be combined.

[pause=0.7]

If the measure is revenue, SUM is a reasonable choice.

[pause=0.7]

But the transaction-level detail is no longer present in that cell.

Slide 43: Join before pivot carefully

Reshaping often happens after joins.

[pause=0.7]

The danger is that a join can multiply fact rows.

[pause=0.7]

If you join a patient dimension to admissions, the admission grain can remain intact.

[pause=0.7]

But joining admissions to another one-to-many child table can create repeated admission combinations.

[pause=0.7]

Always check cardinality before pivoting joined data.

[pause=1.0]

Slide 45: One-to-many multiplication risk

The important question is whether the join preserves the measure's fact grain.

[pause=0.7]

A many-to-one lookup often preserves the fact rows.

[pause=0.7]

A broad join between two fact-like tables can multiply them.

[pause=0.7]

If rows are already duplicated before the pivot, the pivot aggregates inflated facts.

[pause=0.7]

Check row counts and key relationships first.

[pause=1.0]

Slide 46: Pre-aggregate before reshaping

Pre-aggregation can help control grain.

[pause=0.7]

First summarize the fact table to the level you actually need.

[pause=0.7]

Then perform later joins or pivots from that stable grain.

[pause=0.7]

This separates fact aggregation from presentation reshaping and can make the query easier to verify.

Slide 48: Dynamic categories

Wide pivot columns are part of the schema.

[pause=0.7]

If the categories are stable, that is manageable.

[pause=0.7]

[pause=0.7]

Long form handles dynamic categories more naturally because new categories become new rows.

[pause=0.7]

Often a BI tool can create the presentation matrix from long data.

Slide 54: Long vs wide downstream

Reshaping should be driven by the downstream consumer.

[pause=0.7]
