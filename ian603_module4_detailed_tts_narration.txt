Slide 1: Start

Welcome to Module 4, Aggregating Data with PostgreSQL. In the previous module, we focused mainly on individual rows: how to retrieve them, filter them, and change them safely. In this module, we move into analytical SQL. Instead of asking only, which rows do I need, we will often ask, what do these rows mean as a group?

This is where aggregate functions become useful. COUNT can tell us how many rows or values we have. SUM can give us totals. AVG can give us averages, while MIN and MAX help us find the smallest and largest values. We will combine those functions with GROUP BY so that one large table can become a meaningful summary report.

The most important idea in this module is grain. Grain means what one output row represents. Before writing GROUP BY, try to say the result in plain language. For example, one row per diagnosis, one row per sales category, or one row per department. Once that is clear, the SQL becomes much easier to design.

We will also compare WHERE and HAVING, build conditional metrics with CASE and FILTER, create subtotal reports with ROLLUP, CUBE, and GROUPING SETS, and finish with window functions that add analytical context without collapsing the detail rows.

As you work, keep one habit in mind: start with the question, define the grain, calculate the measures, apply the right filters, and then validate the result against the detailed data.


Slide 2: Big picture

This slide shows the transition from Module 3 to Module 4. In Module 3, most of our questions returned individual records. For example, we could retrieve one patient row, filter admissions, or update one record. Module 4 asks us to summarize many rows into information that is easier to interpret.

Think about a sales table with hundreds or thousands of transactions. A decision-maker may not want to read every transaction. They may want total revenue by category, average sale price, or the number of unique products sold. Aggregation converts the detailed rows into that higher-level view.

The workflow on this slide is very important. We still begin with detail. Then we decide the grain of the output. Next, we choose the measure, such as a count, total, or average. After that, we decide whether any source rows should be filtered before grouping and whether any summary groups should be filtered after grouping. Finally, we validate the result.

That last step matters because an aggregate can look reasonable even when the grouping or filtering logic is wrong. A useful habit is to compare the summary back to the source rows, especially when building a new report.

So the main idea is simple: do not start with GROUP BY just because you want a summary. Start with the question and define what one result row should mean.


Slide 3: Learning path

Here is the learning path for Module 4. We are going to build the ideas gradually so that each new concept connects to something you already understand.

First, we summarize. You will work with COUNT, SUM, AVG, MIN, and MAX. These functions take several input rows and calculate a summary value.

Second, we group. GROUP BY lets us create a separate summary for each category or combination of categories. For example, instead of one total for the whole sales table, we can calculate one total per product category.

Third, we filter. WHERE and HAVING both remove data, but they work at different stages. WHERE removes source rows before aggregation. HAVING removes groups after the aggregates have been calculated. Understanding that difference will make many analytical queries much easier to reason about.

Finally, we extend the analysis. We will build conditional metrics, create multiple levels of totals, and use window functions for ranking, averages, and running totals without losing detail rows.

The coding progression is the same beginner-friendly pattern we used earlier: run a complete example, change one piece, complete a partially written query, and then write a short query yourself. The goal is not memorization. The goal is to understand the reasoning behind the query.

The admissions table contains healthcare-style records such as patients, diagnoses, admission times, and discharge times. We will use it for counts, length-of-stay calculations, and conditional diagnosis metrics.

Finally, the grades table contains student, course, grade, and semester information. It becomes part of the assignment exercises near the end of the module.

Slide 5: Five-step workflow

This five-step workflow is the foundation for the entire module. If you follow these steps, aggregate queries become much easier to design and debug.

Step one is ask. What decision question are we answering? Maybe we want to know which sales categories generated the most revenue, or which diagnoses appear most often.

Step two is set the grain. This is the most important step. Ask yourself: what does one output row represent? One row per category? One row per diagnosis? One row per department and month? If that sentence is not clear, it is too early to write GROUP BY.

Step three is measure. Decide what calculation belongs in each row. That could be COUNT, SUM, AVG, MIN, MAX, or more than one of them.

Step four is filter. Decide which individual rows should be removed before grouping and which completed groups should be removed afterward. That is where WHERE and HAVING come in.

Step five is validate. Compare the summary with the detailed data. Check totals, row counts, and a few example groups.

Notice that syntax comes after reasoning. A strong SQL habit is to define the analytical meaning first and then translate that meaning into SQL.


Slide 6: Summary functions

Aggregate functions take a set of rows and turn that set into one summary value. The five functions on this slide are among the most common.

COUNT answers questions about how many rows or values exist. SUM adds numeric values together. AVG calculates the arithmetic mean. MIN returns the smallest value, and MAX returns the largest value.

One important point is that GROUP BY is not required every time you use an aggregate. If you run an aggregate over an entire table without GROUP BY, PostgreSQL can return one summary row for the whole table. For example, SELECT COUNT star FROM sales returns one number representing the number of sale rows.

GROUP BY becomes useful when you want several summaries, one for each group. For example, total revenue by category creates one result row per category.

Also remember that the type of measure should match the question. Counting rows is different from summing quantity. Average price answers a different question from total revenue. SQL will calculate exactly what you request, even if the measure is not meaningful for the decision question.

So before choosing a function, ask: what quantity am I trying to describe?


Slide 7: COUNT meanings

COUNT looks simple, but there are several forms, and they answer different questions.

COUNT star counts input rows. It does not care whether a particular column is NULL. If a row exists in the input set, COUNT star includes it.

COUNT of a column counts only the rows where that particular column is not NULL. In the admissions example, COUNT discharge_time can be interpreted as the number of admissions that have a recorded discharge time. Rows with a missing discharge time are ignored by that expression.

COUNT DISTINCT column goes one step further. It removes duplicate non-NULL values before counting. COUNT DISTINCT subject_id therefore tells us how many different patients appear in the admissions table, not how many admission rows exist.

Run the example and compare the three numbers. Ask what population each number represents. All admissions, completed admissions, and unique patients are related, but they are not the same metric.

This distinction is important in real analysis. A report can be wrong even when the SQL runs successfully if the analyst chooses the wrong form of COUNT. Whenever you see COUNT, try to finish the sentence: I am counting what, exactly?


Slide 8: Aggregate example

This example shows several aggregate functions in one query. That is common in analytical SQL because one source table can support several useful measures at the same time.

COUNT star gives us the number of sales rows. SUM quantity adds all units sold. AVG price calculates the average price across the rows. MIN price finds the lowest price and MAX price finds the highest price.

Notice that average price is rounded to two decimal places for presentation. The ROUND function does not change the stored prices. It only formats the calculated result to a more convenient precision.

Run the query and compare the measures. A row count and a unit count are not the same thing. One sale row could contain a quantity greater than one. Similarly, average price does not tell us total revenue. Revenue usually requires multiplying quantity by price and then summing that expression.

This is a good example of why analysts should label output columns clearly. Names such as sale_rows, units_sold, average_price, lowest_price, and highest_price tell another reader what each number means.

When designing a summary, choose measures that directly answer the business or research question rather than adding aggregates simply because they are available.


Slide 9: NULL and averages

NULL values can change the population that contributes to an aggregate, so we need to think carefully about them.

In this example, we calculate average completed length of stay. An ongoing admission has no discharge time yet. Because the discharge time is missing, there is no completed stay duration to calculate for that row.

The WHERE clause removes rows where discharge_time is NULL. For the remaining rows, PostgreSQL subtracts admit_time from discharge_time, converts the interval into seconds, changes that to days, and then AVG calculates the mean stay length. The result is rounded to two decimal places.

The query also returns COUNT discharge_time as completed_admissions. This is useful because an average is much easier to interpret when we know how many observations contributed to it.

A key point is that AVG ignores NULL expressions, but relying on that behavior without thinking can hide data-quality or population issues. It is often better to make the intended population explicit with WHERE and to report the sample size beside the average.

Whenever you calculate an average, ask two questions: which rows are included, and how many observations actually contributed to the mean?


Slide 10: GROUP BY grain

GROUP BY defines the grain of the summary result. Grain is simply what one output row represents.

At detail grain, one row might represent one admission. If you are returning individual admission records, no grouping is needed.

At category grain, one row could represent one diagnosis. Then GROUP BY diagnosis tells PostgreSQL to place rows with the same diagnosis into the same group before calculating aggregate values.

A multi-column grain is more detailed. If we group by subject_id and diagnosis, one output row represents one patient-and-diagnosis combination.

This is why adding a GROUP BY column usually increases the number of result rows. You are dividing the source data into smaller groups.

A useful beginner rule is that any selected column that is not inside an aggregate function usually belongs in GROUP BY. PostgreSQL enforces this rule because it needs to know which single value should represent each group.

Before writing the query, try saying the grain aloud. If you can clearly say, one row per diagnosis, or one row per patient and diagnosis, then you have a strong starting point for choosing the GROUP BY columns.


Slide 11: GROUP BY example

This query creates one summary row for each diagnosis. That sentence tells us the grain before we even read the SQL.

The SELECT list contains diagnosis, which is the grouping column, and COUNT star, which counts the admission rows inside each diagnosis group. The alias admission_count gives the measure a clear name.

GROUP BY diagnosis tells PostgreSQL to collect rows that share the same diagnosis. Then COUNT star is calculated separately for each group.

The ORDER BY clause sorts by admission_count descending so the most frequent diagnosis appears first. Diagnosis is used as a secondary sort so groups with the same count still have a predictable order.

Run the query and look at the result. Each diagnosis should appear once, even if several source rows had that diagnosis. That is the key effect of grouping: many detail rows become one summary row for the defined grain.

If you are ever unsure about a grouped query, temporarily inspect the detail rows for one category. Count them manually and compare with the aggregate result. That validation technique is simple and very effective.


Slide 12: Multi-column grouping

Now we add a second grouping column. The result grain changes from one row per diagnosis to one row per patient-and-diagnosis combination.

The SELECT list contains subject_id and diagnosis, and both columns also appear in GROUP BY. COUNT star then tells us how many admission rows exist for each specific combination.

Imagine that two different patients both have the same diagnosis. When we grouped only by diagnosis, those rows contributed to one shared diagnosis group. After adding subject_id, those rows are separated into different patient-level groups.

This is why grouping columns define detail. More grouping columns usually produce a more detailed summary, while fewer grouping columns produce a more aggregated summary.

Run the query and compare it mentally with the previous slide. The source table did not change. Only the analytical grain changed.

When building a report, be deliberate about this choice. One row per diagnosis answers a population-level question. One row per patient and diagnosis answers a more detailed question. Neither is automatically better. The correct grain depends on what the report is supposed to represent.


Slide 13: Useful grouping error

This slide intentionally shows a grouping error because PostgreSQL is protecting us from an ambiguous result.

The query asks for diagnosis, subject_id, and COUNT star, but it groups only by diagnosis. That creates a problem. If one diagnosis group contains several different subject IDs, which single subject_id should PostgreSQL display for the whole group?

There is no correct answer unless we define one. That is why PostgreSQL returns an error instead of choosing an arbitrary value.

The general rule is that a selected expression should either define the group, be derived consistently from the grouping columns, or be calculated with an aggregate function. In a beginner query, the simplest rule is: selected non-aggregate columns belong in GROUP BY.

Run the example and read the error message. Error messages are useful teaching tools. They often tell you exactly which column is causing the ambiguity.

There are two possible ways to fix this query, depending on the intended grain. If we want one row per diagnosis, remove subject_id from SELECT. If we want one row per patient and diagnosis, add subject_id to GROUP BY. The right fix comes from the question, not from syntax alone.


Slide 14: WHERE vs HAVING

WHERE and HAVING both filter data, but they work at different stages of an aggregate query.

WHERE filters individual source rows before GROUP BY happens. For example, WHERE price is greater than or equal to twenty-five means that lower-priced sale rows never enter the groups.

HAVING filters completed groups after aggregation. For example, HAVING SUM quantity greater than ten means PostgreSQL first creates the category groups, calculates total quantity for each group, and then removes groups that do not meet the threshold.

A simple way to remember the difference is: WHERE asks which rows should participate; HAVING asks which summary groups should remain.

At the same query level, WHERE normally cannot test SUM, COUNT, or AVG because those aggregate values do not exist yet. HAVING can test them because grouping has already occurred.

Sometimes a condition could technically be written in HAVING even though it belongs in WHERE. That is usually less clear and can do unnecessary work. Row-level conditions belong in WHERE whenever possible.

When you see a filtering requirement, ask whether it describes an individual source row or a calculated group. That question usually tells you whether to use WHERE or HAVING.


Slide 15: Complete aggregation pattern

This slide presents the logical flow of a complete aggregation query. The written order of SQL starts with SELECT, but it is often easier to reason about the query in the order shown here.

FROM identifies the source data. WHERE removes source rows that should not participate. GROUP BY forms the groups. HAVING filters those completed groups. SELECT produces the final columns and aggregate values. ORDER BY arranges the final result.

This order explains many SQL rules. For example, WHERE cannot refer to a same-level aggregate such as SUM quantity because the groups have not been created yet when WHERE is evaluated. HAVING can use SUM quantity because it runs after grouping.

This order also helps with performance and clarity. If a row does not belong in the analysis at all, filter it in WHERE before the database spends effort grouping it.

When a grouped query becomes confusing, rewrite the problem as a sequence: source, row filter, grain, group filter, output, sort. You can even write those words as comments before filling in the SQL.

Analytical SQL becomes much easier when you think of it as a pipeline rather than one large statement.


Slide 16: WHERE HAVING example

This example puts WHERE, GROUP BY, HAVING, and ORDER BY together in one realistic pattern.

The goal is to calculate category-level sales summaries, but only from rows where price is at least twenty-five. That row-level requirement belongs in WHERE, so lower-priced rows are removed before the groups are created.

Next, GROUP BY category defines the grain as one row per category. SUM quantity calculates total units sold, and SUM of quantity times price calculates category revenue. ROUND makes the revenue easier to display.

HAVING SUM quantity greater than ten then removes category groups that do not have enough total quantity. Notice that this condition is about a calculated group value, so HAVING is the correct place.

Finally, ORDER BY category_revenue descending puts the highest qualifying revenue first.

Run the query and read it in stages. Ask which rows enter the calculation, what one output row represents, what measures are calculated, and which completed groups remain.

This pattern appears constantly in reporting. If you understand this slide well, you have a strong foundation for many real analytical SQL tasks.


Slide 17: Conditional aggregation

Conditional aggregation lets one query calculate several metrics from the same set of source rows.

The main idea is that a condition controls which rows contribute to each aggregate. For example, from the same admissions table we might calculate one count for pneumonia and another count for fractures.

There are two common approaches in this module. CASE is highly flexible and works across many SQL systems. We can place a CASE expression inside SUM, COUNT, or another aggregate and map matching rows to a useful value.

PostgreSQL also supports FILTER. FILTER places a WHERE-like condition directly on an aggregate function. It is often very readable when we want several independent counts or sums in the same SELECT list.

Both approaches are useful. CASE is more portable and can handle complex mappings. FILTER is concise and expressive in PostgreSQL.

The important concept is not the exact syntax. It is that one grouped row can contain several measures that each look at a different subset of the same underlying rows.

This is extremely useful for dashboards and feature tables because it avoids writing separate queries for every category or condition.


Slide 18: CASE example

This query demonstrates conditional aggregation with CASE.

The grain is one row per subject_id, so GROUP BY subject_id appears near the end of the statement. Inside each patient group, the first SUM contains a CASE expression that checks whether diagnosis equals Pneumonia. Matching rows contribute one, while all other rows contribute zero. Adding those ones and zeros gives the pneumonia count.

The second SUM repeats the same idea for Fracture.

This pattern may look unusual at first, but it is very logical. We are converting a condition into numbers and then summing the numbers. One means this row belongs to the metric; zero means it does not.

Run the query and inspect a few patient rows. A patient can have zero, one, or more admissions of each type depending on the data.

CASE is especially useful when you need more than a simple yes-or-no filter. For example, CASE can map categories to different weights or values before aggregation.

For now, focus on the pattern: condition, one if true, zero if false, then SUM within the group. That pattern transfers to many SQL systems.


Slide 19: FILTER example

This slide calculates the same kind of metrics using PostgreSQL FILTER syntax.

The grain is still one row per subject_id. The first expression begins with COUNT star, but FILTER tells PostgreSQL to count only rows where diagnosis equals Pneumonia. The second expression counts only rows where diagnosis equals Fracture.

Compared with the CASE version, the condition is visually separated from the aggregate. Many people find that easier to read when the goal is a simple filtered count, sum, or average.

Run the query and compare the result with the CASE example. For this problem, the numbers should match because both statements express the same analytical logic.

FILTER is very useful when one result row needs several related measures. For example, you could count completed and open admissions, sum online and in-store revenue, or average values for several categories in one grouped query.

Remember that FILTER is a PostgreSQL feature and is not supported in exactly the same way by every SQL engine. The broader idea of conditional aggregation is portable even when the syntax changes.


Slide 20: CASE vs FILTER

CASE and FILTER can often solve the same conditional aggregation problem, but they have different strengths.

Use CASE when portability matters or when you need flexible value mapping. CASE works in many SQL products and can return different values for different conditions. It is a general expression, not only an aggregate feature.

Use FILTER when you are working in PostgreSQL and want a concise condition attached directly to an aggregate. FILTER is especially clean when you have several independent metrics in one SELECT list.

For example, COUNT star FILTER where diagnosis equals Pneumonia is immediately readable as count the rows that meet this condition.

The course goal is not to choose one winner. You should be able to recognize both patterns and understand that they are different ways to express conditional metrics.

When moving SQL between systems, CASE is often the safer option because it is broadly supported. When staying in PostgreSQL, FILTER can make a report easier to read.

As always, choose the form that makes the analytical meaning clearest for the people who will maintain or review the query.


Slide 21: Advanced grouping

So far, each GROUP BY query produced one specific grain. Advanced grouping features let one query return several summary grains together.

GROUPING SETS is the most explicit. You list exactly which grouping combinations you want. This is useful when a report needs selected summary levels and you do not want every possible combination.

ROLLUP is designed for hierarchical summaries. With category and product, it can produce detail by category and product, subtotals by category, and a grand total. That is a natural hierarchy: product belongs under category.

CUBE produces every grouping combination for the listed dimensions. With two dimensions, it gives detail by both, totals by the first, totals by the second, and the overall grand total.

These tools reduce the need to write several separate GROUP BY queries and combine them with UNION ALL.

The tradeoff is that the result contains rows with different grains. That means we must label subtotal and grand-total rows carefully so users can interpret them correctly.

In the next slides, pay attention not only to the SQL syntax but also to what each output row represents.


Slide 22: Grouping comparison

This comparison helps distinguish GROUPING SETS, ROLLUP, and CUBE.

GROUPING SETS returns only the combinations you explicitly list. If you request category totals, product totals, and a grand total, PostgreSQL returns exactly those levels.

ROLLUP of A and B follows a hierarchy. It produces A and B together, then A alone, then the empty grouping set, which represents the grand total. It does not automatically produce B alone because the hierarchy moves from detailed to broader levels from left to right.

CUBE of A and B returns every combination: A and B together, A alone, B alone, and the grand total.

A useful way to choose among them is to think about the report design. If the dimensions have a natural parent-child relationship, ROLLUP is often a good fit. If you want every cross-dimensional subtotal, CUBE may be appropriate. If the report needs a custom set of levels, GROUPING SETS gives you precise control.

These features can create more rows than beginners expect, so always inspect the grain of each result row and label subtotal rows clearly.


Slide 23: ROLLUP

ROLLUP creates hierarchical subtotals. In this example, category is the higher-level dimension and product is nested underneath it.

The query sums sales and groups by ROLLUP category, product. PostgreSQL first returns the most detailed groups, one for each category-and-product combination. It then produces a subtotal for each category, and finally a grand total across all categories and products.

Subtotal rows need special labels because PostgreSQL uses NULL-like placeholders in rolled-up columns. The GROUPING function tells us whether a column is missing because it was rolled up rather than because the source data actually contained NULL.

The CASE expressions use GROUPING to display labels such as All categories or All products. The grouping_code is also included so you can see which level each row represents.

Run the query and find three kinds of rows: detailed product rows, category subtotal rows, and the grand total.

ROLLUP is a good fit for reports with a hierarchy, such as region to store, category to product, or year to month. The order of columns matters because it defines the rollup path.


Slide 24: CUBE

CUBE goes beyond ROLLUP by returning every grouping combination for the listed dimensions.

With category and product, CUBE produces four analytical levels. First, category and product together. Second, category totals across all products. Third, product totals across all categories. Fourth, the grand total across everything.

That product-only subtotal is the important difference from the ROLLUP example. ROLLUP follows one hierarchy. CUBE explores all combinations.

The query again uses GROUPING inside CASE expressions so subtotal placeholders can be labeled clearly. The grouping_code helps identify which dimensions are active in each row.

Run the query and compare it with the previous slide. You should see more subtotal rows because CUBE adds the product-only level.

CUBE can be useful in multidimensional reporting, but it can grow quickly. With more dimensions, the number of grouping combinations increases substantially. That can make both the result and the computation larger.

Use CUBE when the report truly needs all combinations. If you only need a few specific summary levels, GROUPING SETS is usually more controlled.


Slide 25: GROUPING SETS

GROUPING SETS gives you direct control over which summary levels appear in the result.

In this query, we request three grouping sets: category alone, product alone, and the empty grouping set. The empty parentheses represent the grand total.

Notice what is not requested. We do not ask for category-and-product detail in this example, so PostgreSQL does not return that level. This is what makes GROUPING SETS flexible: you list only the grains that the report needs.

The CASE expressions again use GROUPING to label rolled-up columns. The result therefore contains category totals, product totals, and one overall total.

Run the query and identify the grain of each row. Some rows mean one category across all products. Some mean one product across all categories. The final row means all data.

GROUPING SETS is often a good option when a report has a specific layout that does not fit a simple hierarchy. It can replace multiple GROUP BY queries that would otherwise need to be combined.

The key skill is still grain awareness. One result set can now contain several grains, so labeling and interpretation become even more important.


Slide 26: GROUPING placeholders

Advanced grouping creates subtotal rows where grouped columns can appear as NULL. The challenge is that real source data can also contain genuine NULL values.

If we simply use COALESCE and replace every NULL with a label such as All products, we can accidentally confuse a real missing value with a subtotal placeholder.

GROUPING solves that problem. It tells us whether a column is absent because PostgreSQL rolled that dimension up for a subtotal.

With two grouping expressions, the grouping code can represent several cases. Code zero means both category and product participate in the grouping. Other codes indicate that one expression has been rolled up. Code three represents the grand total where both dimensions are rolled up.

You do not need to memorize every numeric code immediately. The important idea is that GROUPING gives you metadata about the summary level.

Whenever a subtotal report can contain real NULL values, use GROUPING rather than guessing based on NULL alone. That makes the report semantically correct and prevents misleading labels.

This is a good example of how analytical SQL is not only about calculation. It is also about making sure users can correctly interpret what each row means.


Slide 27: Window functions

Window functions are different from GROUP BY because they can add analytical information while keeping the detail rows.

GROUP BY usually collapses many input rows into one row per group. If we group employees by department, we lose the individual employee rows unless we do additional work.

A window function can calculate something such as department average salary and place that value beside every employee row. The detail remains visible.

The OVER clause defines the window. PARTITION BY creates groups for the calculation without collapsing the rows. ORDER BY inside OVER can define the sequence for ranking or running totals.

This makes window functions useful for rank, running totals, moving averages, comparisons with group averages, and many other analytical tasks.

A simple question can help you choose between GROUP BY and a window function. If you want one row per group, GROUP BY is often appropriate. If you want to keep each original row and add group-level context, a window function is often the better tool.

The next examples will make that difference visible.


Slide 28: Window rank

This query ranks employees by salary within each department.

The function is RANK, followed by an OVER clause. PARTITION BY department tells PostgreSQL to restart the ranking separately for each department. ORDER BY salary descending inside the window means the highest salary receives rank one.

Because this is a window function, the individual employee rows remain in the result. We are adding a department_rank column rather than collapsing employees into one department row.

Run the query and watch what happens when the department changes. The ranking should start again at one.

RANK also has a specific behavior with ties. If two employees have the same salary, they receive the same rank, and the next rank can be skipped. Later, you may also see ROW_NUMBER and DENSE_RANK, which handle ties differently.

Notice that there are two ORDER BY ideas in this query. One is inside OVER and defines how the rank is calculated. The final ORDER BY controls how the result rows are displayed.

Keeping those two purposes separate is important when working with window functions.


Slide 29: Window averages

This example shows one of the most useful window patterns: placing group and overall averages beside each detail row.

AVG salary OVER partition by department calculates a separate average for each department. Every employee in the same department receives the same department_average value.

AVG salary OVER with empty parentheses calculates one average across the entire result population. Because there is no PARTITION BY, every employee row receives the same company_average value.

The employee row itself is not removed. We still see name, department, and salary. That makes it easy to compare one employee's salary with both local and global context.

Run the query and choose one employee. Compare that person's salary to the department average and then to the company average.

This is a major difference from GROUP BY. A GROUP BY query could return one average row per department, but it would not automatically keep each employee row beside that average.

Window functions are very powerful for feature engineering and reporting because they let you add contextual measures without changing the detail grain.


Slide 30: Running totals

A running total is another classic use of window functions.

The row_revenue expression multiplies quantity by price for each sale row. The windowed SUM then adds revenue from the beginning of the ordered data through the current row.

ORDER BY sale_date and sale_id inside OVER defines the calculation sequence. The explicit ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW frame means start at the first row in the window and include everything through the current row.

As you move down the result, running_revenue should never reset because there is no PARTITION BY. Each new sale adds to the previous cumulative amount.

The final ORDER BY uses the same date and sale ID so the displayed rows follow the sequence used in the calculation.

Run the query and verify the first few rows manually. The first running total should equal the first row revenue. The second running total should equal the first plus the second, and so on.

Running totals are useful for cumulative sales, account balances, inventory movement, progress tracking, and many time-oriented analyses.


Slide 31: Execution order

Understanding logical execution order explains many SQL behaviors that otherwise feel like arbitrary rules.

The process begins with FROM and JOIN, which determine the source rows. WHERE filters those rows. GROUP BY creates groups. HAVING filters the groups. SELECT then produces the requested expressions. Window functions operate after the grouping and HAVING stage. ORDER BY arranges the final rows, and LIMIT can restrict how many are returned.

This order explains why WHERE cannot use a same-level aggregate. At the WHERE stage, SUM or COUNT for a group has not been created yet. HAVING can test those values because grouping has already happened.

It also explains why window functions can work with grouped results. They see the rows that remain after aggregation and HAVING at that query level.

You do not need to memorize this list perfectly on day one. Use it as a debugging tool. When SQL says a column or aggregate is not available where you placed it, ask whether that value exists yet in the logical processing order.

Thinking in stages is one of the best ways to become comfortable with more advanced SQL.


Slide 32: Portability

The analytical reasoning in this module transfers well across database systems, but the exact syntax may change.

For example, PostgreSQL can subtract timestamps directly to create an interval. Some other systems use functions such as DATEDIFF instead.

PostgreSQL supports FILTER for conditional aggregates. Other systems may not, so SUM with CASE is often a more portable replacement.

Support for ROLLUP, CUBE, GROUPING SETS, and even some window syntax can also vary by product and version.

The important lesson is to transfer the reasoning before transferring the syntax. The reasoning is: define the source population, filter rows, choose the grain, calculate measures, apply group thresholds, and sort the report.

When you move from PostgreSQL to another engine, consult that engine's documentation for the exact functions and syntax. Do not assume every database implements every feature in the same way.

If you understand the analytical structure of the query, adapting the syntax is usually much easier than trying to memorize separate solutions for every platform.


Slide 33: Guided practice 1

This guided practice checks whether you understand the three common COUNT patterns.

Before opening the answer, explain the difference in your own words.

COUNT star counts input rows. If a row exists in the query result before aggregation, it contributes to COUNT star regardless of whether some of its columns are NULL.

COUNT of a column counts only non-NULL values in that column. This makes it useful when the presence of a value has meaning, such as counting admissions with a recorded discharge time.

COUNT DISTINCT column counts unique non-NULL values. For example, if one patient has several admissions, COUNT DISTINCT subject_id counts that patient once.

The best way to remember these patterns is not by memorizing definitions. Ask what you want to count: rows, recorded values, or unique values.

Try giving your own example for each form. If you can explain why the three answers might be different on the same table, you understand the idea well enough to use it in a real query.


Slide 34: Guided practice 2

Next choose the measure. We want the number of admissions for each diagnosis, so COUNT star is appropriate.

Now think about the condition more than one admission. That condition describes a completed group count, not an individual source row. Therefore it belongs in HAVING, not WHERE.

Slide 45: Summary

Let us finish Module 4 by connecting the major ideas.

First, grain comes before GROUP BY syntax. Always know what one output row represents.

Second, NULL matters. COUNT star counts rows, while COUNT column counts non-NULL values. AVG and other aggregates can also be affected by missing values and by the population you choose.

Third, filtering happens at different stages. WHERE removes source rows before grouping. HAVING removes completed groups after aggregate values exist.

Fourth, conditional aggregation lets one grouped row contain several metrics. CASE is flexible and portable, while PostgreSQL FILTER is often concise and readable.

Fifth, GROUPING SETS, ROLLUP, and CUBE can place several summary grains in one result. GROUPING helps label subtotal rows correctly.

Finally, window functions add analytical context without collapsing the detail rows. You used them for ranking, group averages, company averages, and running totals.

The larger lesson is a workflow: ask a clear question, define the grain, choose meaningful measures, filter at the correct stage, and validate the result. Those habits will support the more advanced SQL topics that come next.
